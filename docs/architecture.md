# Architecture

## Kanban board

`.kanban/` holds one markdown file per task, named `000001_nice_thing.md`. The name has a zero-padded number and a slug of at most 4 words, or 5 for a supplied `shortName`. The type word is dropped from a name-derived slug. Each file has flat YAML frontmatter. The fields are name, priority, state, worktree, issuer, and complexity, plus optional `shortName` and `blockedBy`. `blockedBy` is a comma-joined list of task refs, optionally with the hold tokens `user` and `question`. The body has `# Summary`, `# Specs`, and `# Notes`. It has `# Open questions` when needed. A non-empty section is a question the user must answer. `kanban_update` clears the section only in a call that also passes `specs`, so an answer never disappears without landing in the Specs.

The complexity attribute is `trivial`, `simple`, `moderate`, or `complex`. It defaults to `moderate`. It selects the per-complexity LLM config and the reviewer pass cap.

The library writes task files. The orchestrator daemon commits them at creation in backlog and at done. Edits in between stay uncommitted and land in the done commit. A task deletion commits its own board snapshot.

States: backlog, to-do, doing, to-review, reviewing, to-merge, merging, to-live-test, live-testing, done.

## Orchestrator

`src/orchestrator.ts` is a non-LLM daemon. Start it with the `orchestrator_start` tool, or run `node src/orchestrator.ts --root <project>`. One daemon runs per project. Its lockfile is `.kanban/.orchestrator.lock`.

The daemon watches `.kanban/` and rescans every 10 s. The `orchestrator_poke` tool touches `.kanban/.poke` for an immediate scan. A poke scan bypasses the backlog quiet window. A poke is the PM's signal to schedule now. Under the `maxParallel` cap the orchestrator starts tasks by priority first, then by pipeline stage with the later stage first (live-test, merge, review, to-do), then by creation order.

- **backlog**: the daemon promotes tasks whose blockers are satisfied and whose `# Open questions` section is empty. A board-wide quiet window (`backlogIdleMinutes`, default 1) waits for the board to stay untouched. When a blocker reaches done, to-live-test, or live-testing, the daemon drops its ref. A `user` ref is a manual hold, not a task ref: it survives that drop, and only the PM removes it. A `question` ref is the answer hold: the daemon adds it when `# Open questions` is not empty, and removes it when the section is empty. A backlog task with a question keeps its state and takes the token, so it does not promote.
- **to-do**: for moderate and complex tasks, the daemon spawns a Splitter at the project root. When the Splitter leaves the task in to-do, the daemon creates the worktree `.worktrees/<type>/<num>-<short-slug>` and spawns a Developer. Simple and trivial tasks skip the Splitter and start with the worktree. A task held by the `user` or `question` ref never reaches the Splitter or the Developer: it keeps to-do. The daemon sets the task to doing before it starts the Developer.
- **doing**: the Developer implements the Specs in the worktree.
- **to-review**: the daemon spawns a Reviewer and moves the task to reviewing. After `reviewerCap.<complexity>` successful runs, the daemon force-advances the task to to-merge. A reviewer run counts one pass only when its state move landed. A reviewer run that ends without moving the task counts as a failed run and bounces to to-review, so reviewing never stays stuck. A trivial task has cap 0 by default and skips the reviewer. With `reviews: false` the daemon moves the task straight to to-merge.
- **reviewing**: the Reviewer fixes small mistakes and sets its own state. Approval goes to to-merge. More fixes go back to to-review. A Specs violation goes to to-do.
- **to-merge**: the merge queue. The daemon spawns one Merger in the task worktree and moves the task to merging. One merger runs project-wide. A merger that gives up does not park the task here: it keeps the task in merging, as below.
- **merging**: the Merger owns the whole merge. It aborts a stale rebase, clears the two context paths, rebases the branch onto the root checkout's current branch, and resolves each conflict: it keeps both sides where they fit, or its own side plus an open question that names the other task. It writes one `merge:` bullet per resolved hunk in the task notes, then runs the full `pnpm test` in its worktree. A failing suite sends the task back to to-do. On success it leaves the state at merging. On that clean exit the daemon proves the rebase finished and the branch sits on the base, then fast-forwards the root checkout to the branch and sets to-live-test. It strips a context symlink committed by mistake. A rebase left in progress or a branch off the base is a give-up: the daemon writes `.kanban/.logs/<slug>.merge-stuck` with the reason, the branch, and the base, keeps the task in merging, and blocks the whole merge lane until the PM repairs the root by hand. The PM report carries the recipe. The sweep moves the task to to-live-test after the root fast-forward.
- **to-live-test**: the merged commit is ready. The daemon spawns a Live-tester and moves the task to live-testing. With `liveTesting: false` the daemon moves a merged task straight to done.
- **live-testing**: the Live-tester runs the merged commit like a user.
- **done**: the daemon removes the worktree and the merged branch. It commits the task file. A `question` token on a done task does not reopen it.

A successful finish moves the developer to to-review. It moves the live-tester to done. A finish that leaves an open question moves the task to to-do instead: the sweep adds the `question` token, and the task waits for the PM's answer. A merger that fails the suite sends the task to to-do. A merger clean exit goes through the fast-forward proof, which sets to-live-test. The Reviewer sets its own state. A crash moves the task back one step. pi exits 0 when the final assistant response fails, so the daemon reads the run log too. A terminal error in that log counts as a crash and never as a successful review. A log that does not grow for `logStallMinutes` counts as a crash. After 5 respawns, the daemon waits `retryIdleMinutes` before the next spawn.

A task file with conflict markers stays untouched. The daemon spawns no agent and writes nothing for it until the merger or the user resolves the conflict.

On a sweep that moves tasks to done, the daemon queues one board report in `.kanban/.reports/`. The extension delivers it to the Project manager session. The report lists the done tasks, the promoted tasks, the live-test findings, and the PM instructions. The same flow carries three alerts: `## Waiting on an answer` for each task that gained the `question` token, `## Merge stuck` with the task, the reason, the branch and the repair recipe, and `## Root checkout detached` for a root that is not on a branch. The report carries the session id of its owner in the file name. The owner is the session that called `orchestrator_start`, or the last session that attached to the pipeline with it. Another root session never takes the report. With no live owner, the first root session to look takes it. Only a session at the repo root consumes reports.

### Board mirror to origin

The daemon mirrors the board to `refs/heads/meta/kanban` and pushes that ref to `origin`. The push is best effort. It needs SSH access to origin for the daemon user. Without it, the mirror stays local and a fresh clone cannot bootstrap from it.

## Web dashboard

Set `webUi.enabled: true` in the config to serve a dashboard at `http://<host>:<port>`, default `http://localhost:4242`. The board shows every task state as six stations: queue, work, review, merge, test, then done at the right edge. Each card carries the task number, a filled priority ruler, the name and, when the task is idle, its summary. The task detail dialog can block or unblock a task. A block adds the `user` hold, moves an active task back to its queue state, and stops its agent. A done or merging task shows no block button. A card names the hold token it carries: `question` waits for an answer, `user` is a manual hold. Both have a filter chip. Only a `user` hold sorts to the top and offers the unblock button, and the unblock never clears a `question` hold. A task in merging with a stuck marker names the pending root fast-forward. The page refreshes every 5 s. It refreshes every second while the open task has a live agent or doctor. The footer shows the serving hub's `pid`, checkout, and `commit`. The same data is at `GET /api/hub`.

Only a daemon rooted at a main checkout can win the hub election and serve the UI. A daemon in a linked worktree registers with the hub and stands down. This keeps old worktree code off the port. After an upgrade, kill old worktree daemons once: `pkill -f 'orchestrator.ts.*--root .*/\.worktrees'`. A daemon in a task worktree exits when its task is done or gone.
