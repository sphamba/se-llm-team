# Summary
Add an integration-test stage to the pipeline. When the orchestrator moves a task from live-testing to done, it creates or extends one integration-test task in the new state to-integration-test. That task promotes to integration-testing (one run at a time, counting as one maxParallel slot), runs a new integration-tester agent over the full suite on the merged base branch, reports findings, and ends at done. The board's last column must hold to-live-test, live-testing, to-integration-test, integration-testing and done.

# Specs
## Goal

Add an integration-test stage to the pipeline. After a task finishes its live test, the orchestrator opens or extends one integration-test task. That task runs the full suite on the merged base branch, reports findings, and ends at done. The stage is always on: no config toggle.

## States

- Add `to-integration-test` and `integration-testing` to `STATES` (src/kanban.ts:5), directly before `done`. The array order is the pipeline order and drives the UI layout.
- Add the new states to every state enumeration: `IN_PROGRESS` and the `listTasks` scope switch in src/kanban.ts, `WORKING_CAP_STATES` and the rescan dispatch in src/orchestrator/pipeline.ts, `WORKING_STATES` in src/orchestrator/liveness.ts. The `kanban_set_state` enum derives from `STATES`.

## Transition

- Add to `WORKING_STATES` (src/orchestrator/liveness.ts): `"integration-testing": { next: "to-integration-test", success: "done", role: "integration-tester" }`. A successful run ends the task at done. A crash bounces it back to to-integration-test.
- In the poll success branch (the `if (working.success)` block), after the `setState` call, run the integration-task hook only when the finished task was in `live-testing` and the target state is `done`. The hook keys on that exact transition, so an integration task that reaches done never creates another integration task, and a task the PM moves to done creates none.
- A failure in the hook is logged with `log(root, ...)`. It never blocks the done move and never loses the done state.

## Create or append

Read the board with `listAll(root)` at hook time, not from an earlier snapshot.

1. Find the tasks whose state is `to-integration-test`.
2. If exactly one exists, append to it. If more than one exists, append to the lowest task number and log the anomaly.
3. If none exists, create one.
4. If the target task left `to-integration-test` between the read and the write, create a new task instead of writing into a running one.
5. Skip the ref when a task in `to-integration-test` or `integration-testing` already names it. A task can reach done twice when a dead live-tester bounces it back to to-live-test.

Create with `createTask` (src/kanban.ts:421) and these fields:

| Field | Value |
| --- | --- |
| name | `test: integration of #<num>` |
| shortName | `integration-of-<num>` |
| priority | `low` |
| complexity | `simple` |
| state | `to-integration-test`, set right after creation |
| issuer | `auto` |
| blockedBy | never set |
| worktree | empty |
| Summary | `Integration test of the merged base branch after #<num>.` |
| Notes | `Generated by the orchestrator when #<num> reached done.` |
| Open questions | empty, so the task promotes |

Specs template for the created task:

```
Perform integration testing following the merge of:

- #<num> <name of the covered task>
  <the covered task's # Summary paragraph, indented under the bullet>

Run the project test script in the root checkout.
Report defects and coverage gaps in `# Open questions`.
Read the full task file of a covered ref when its summary is not enough.
Do not edit code. Do not commit. Do not create a task. Do not change task states.
```

Append rules:

- The name becomes `test: integration of #42, #43`, with the refs in ascending order and deduplicated.
- shortName, issuer, priority, complexity, the state and the file number never change.
- The Summary names the full set: `Integration test of the merged base branch after #42, #43.`
- The Specs gain one bullet for the new ref: its number, its name, and its `# Summary` paragraph indented under the bullet. Existing bullets stay unchanged.
- Use one task-file write path and re-read the task before the write. `updateTask` (src/kanban.ts:390) is the single writer.

## Scheduling

- Add a rescan branch for `to-integration-test`. Spawn only when no `integration-tester` is alive and one `maxParallel` slot is free. Use the same single-slot guard shape as `merging` (a global pid name plus the merger-style requeue on a dead run). Then spawn and set the state to `integration-testing` in the same step, like the live-tester spawn.
- Order the waiting tasks by priority, then by task number.
- The agent runs in the root checkout, the tree the merger merges into, with no worktree. Do not set the `worktree` attribute.
- The run counts as one slot in the existing `runningCount` over `WORKING_CAP_STATES`. `DEFAULT_MAX_PARALLEL = 0` keeps the lane unbounded except for the single-slot rule.

## Agent prompt

Create `agents/integration-tester.md`. Follow the style of `agents/live-tester.md`. The prompt must state:

- The role and that the task file is `SPECS.md` in the cwd.
- That the cwd is the root checkout and holds the accumulated merged state, not one branch.
- Run the project's test script from the cwd. In this repo that is `pnpm test`. Read `package.json` when the script name is unclear.
- That the covered refs are named in the task title and listed in `# Specs`, and that the full task file of a covered ref is read when its summary is not enough to judge cross-task behaviour.
- Report each defect and each coverage gap in a `# Open questions` section after `# Notes`, and append a short summary line to `# Notes`.
- A missing test script or a suite that cannot start is a finding, never a silent pass.
- No code edits, no commits, no branches, no task creation, no task-state changes.
- End the finish message with `An integration test of this task found <YOUR FINDINGS>`.
- Keep every tool call timeout under `{{logStallMinutes}}` minutes.

# Notes

Splitter note: no split. The task runs as one developer pass.

Why:

- The two new states are one enum at `src/kanban.ts:5`. Every layer derives from it: the orchestrator dispatch, the liveness table, the web UI layout and spinner, the role whitelists and the issuer validation. A piece with a state but no spawn, or a spawn but no prompt, leaves the daemon broken.
- `tests/webui/board.test.ts:90` pins `LAYOUT` deep-equal to today's four pairs plus the three-state tail, and `:91` feeds it a local `STATE_NAMES` literal (`:15`). A web UI piece that sets the tail constant to 5 before the two states exist fails those assertions. The tail change and the state change cannot pass `pnpm test` in two worktrees.
- `tests/webui/page.test.ts:379` pins `ROLE_CLS`. The role wiring in `src/orchestrator/log.ts`, `src/webui/logpane.ts`, `src/webui/payload.ts` and `src/webui/page.ts` is one contract, so it stays in one piece.
- The gate is the full `pnpm test`, and the live test drives a real pipeline. Each piece would need the other pieces to be green, so the pieces would need `blockedBy` order. A sequential split saves no wall clock and adds one review, one merge and one live test per piece.

Only the prose is separable: `docs/architecture.md`, `docs/agents-and-tools.md`, `README.md` and `skills/se-llm-team/SKILL.md`. It has no test and it restates facts from the code. A second task for that prose costs a full pipeline cycle, which is more than the prose work.

Durable guidance for future Splitters: a new pipeline stage is one transaction. The state enum, the transition, the spawn branch, the agent prompt, the role whitelists and the docs must land together, because the suite and the live test judge the pipeline as a whole. Split a stage task only when a piece owns its own states and behaviour end to end, for example a second stage that does not change the first.

Assumptions that shaped the checks:

1. The agent is a fake node script. It reads the `-p` prompt, records the role, the cwd, the task name and the argv, and then holds or exits on a mode file. The prompt text and the spawn cwd are real. No LLM runs and no `pnpm test` runs.
2. Each scenario has one throwaway git fixture under `/tmp/itest301-<tag>-XXXX`, with a local user identity and `commit.gpgsign false`. Task numbers start at 900001 and 950001, so no number can collide with a real board.
3. The single lane slot is held by writing the driver pid into `.kanban/.pids/integration-tester.pid`. This makes the waiting state observable before a sweep starts a run. It substitutes for a real busy lane.
4. A finished live test is the user action: a state rewrite to live-testing, a dead pid `999999`, and an exit file with `0`.
5. At the cap, the user frees the slot by rewriting the holder state to done. The driver never kills an agent to free a slot.
6. The fixture timings are rescan 1 s and poll 0.6 s, because the daemon takes `--poll-minutes` over the config file. The defaults are 10 s and 60 s. The follow-up probe uses the default 6 to 1 ratio (rescan 1 s, poll 6 s).
7. The hub is started directly with `startHub` on port 0, not by the daemon election, because the UI claims are markup, style and geometry. The daemon lanes run with `SE_LLM_TEAM_NO_WEBUI=1`.
