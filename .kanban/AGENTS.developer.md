# developer: role guidance

The spawn prompt owns the numbered steps, the state ban, and the stall window. This file gives the method and the repo facts. `SPECS.md` in the cwd is a symlink to the task file in the main checkout. Put task findings in `# Notes`.

## Contract

- Read `SPECS.md` once with the `read` tool and keep it. `# Specs` and `# Acceptance` are the contract, `# Context` is background. The Specs win over this file and the spawn prompt, including the trivial-task skip. When the Specs name a file, a suite, or a pin, do it. Do not open `SPECS.md` a second time, not even for the Acceptance section. You already have it.
- Decide each choice once, before the edit, then stop. The Acceptance check is the judge between two forms. Take a Specs fact that no check tests as given, and do not measure it or resolve it from the source. When a premise the Specs call proven conflicts with the evidence, check it with one command and move on. Do not mine older task files or git history for the author's intent.
- Change only what the Specs and the Acceptance require. No extra docs, comments, renames, or hardening, because each one adds a suite run and reviewer time. Record an unfixed risk in `# Notes` and do not fix it. Implement in the worktree and never change task states or edit the board.

## Orientation

- Resolve the board from the symlink, not from guessed `../` depth: `board=$(dirname "$(readlink -f SPECS.md)")`. A worktree sits deeper than the main checkout, so `../../.kanban` misses. Use the absolute path for the rest of the run.
- Budget about eight calls before the first edit. Read a named file once with a generous `limit` (the tool allows 2000 lines), not three thin slices, and grep once for the anchors. Never use `cat` or `sed` to read a file. When the Specs quote exact strings, one `grep -n` on those strings replaces the read. Read the one test file that pins the function you change, not the whole suite. If a question needs research beyond the repo, give it to one subagent with one question and one evidence standard, and keep working.

## Tests

- There is no build and no typecheck. A suite runs as `node tests/<area>/<file>.test.ts` or `node index.test.ts`. Areas: `tests/kanban`, `tests/orchestrator`, `tests/webui`, `tests/efficiency-analysis`, plus the loose `tests/*.test.ts`. `node scripts/test-changed.mjs` maps the changed and untracked files to suites. `pnpm test` is the last resort. `node --check` cannot parse TypeScript.
- Run one suite at a time. A suite that `# Acceptance` names always runs, even for a docs-only change. Without a named suite, such a change runs none. Do not run a green suite again unless the code changed, and a move of a tested block that changes no statement needs no rerun: check it with `git diff`.
- A pin exists or it does not. One `grep -rn "<exact string>" tests/` answers it, and empty output is a complete answer. Do not widen the pattern to `src/`, sweep for near-miss numbers, retry with another pattern, or read a suite to learn what it asserts. When no pin exists and the Specs name none, the change needs no test edit.
- Test-first: add the pin, run the suite, read the first red `Error` line (it prints the actual value), then implement until green. Model a new test on the nearest `// --- part` sibling. Copy exact strings from the output, never compose a long expected string by hand. A missing log or output file is a valid red state, so guard the read to fail with its own message, not with ENOENT. A `complexity: trivial` task skips red-first, but still adds any pin the Specs name.
- A change to a shared wrapper literal or an attribute ripples into every exact-HTML assert. Count them with `grep -c` on the literal, replace all in one scripted pass, then check the count on the new literal. Do not edit those asserts one by one, and do not rewrite them from hand.
- There is no DOM library. Tests hand-roll element stubs: `LogEl` in `tests/webui/logpane.test.ts`, and local docs plus `new Function` extraction in `tests/webui/page.test.ts`. Extend the stub in the file you already touch, do not add a dependency. A stub must carry every property the code path reads: `tagName`, `style`, `innerHTML`, `appendChild`, `children`, and both sibling getters with the right skip rules. Query selectors match on tag, class, attribute, and id.

## Edits and checks

- The `edit` tool takes `{oldText, newText}` hunks. Ranges must not overlap, and a failed batch applies nothing. Anchor each hunk on the shortest unique line copied from a read. For a large insertion, such as a test part or a function body, append with `cat >> file <<'EOF'`, never a long `newText`, then read the appended block back. Before a commit, read the staged diff for imports the edit made unused.
- After you add a module-level symbol, grep the import line of every consumer in the same breath as the edit: `grep -n 'from "./<module>.ts"' src/`. A missing import throws a `ReferenceError` that a bare `catch` can swallow. In `src/webui/payload.ts` that catch turns a failed render into the raw log window, so a payload test shows raw JSONL and no error. When output looks raw or unrendered, call the function directly on the same input (`node --input-type=module -e`), then check the import line. Do not blame caching, the barrel, or a second implementation.
- Check a fact once, where it is cheap, and decide there. A registry name is one grep of its declaration. A doc claim is one read of the paragraph. Do not recompute a documented total from the source, because a naive grep gives a wrong answer. A second lookup of the same fact is wasted work.
- Capture the exit code in the same command and print the output only on failure:
  ```
  out=$(node tests/x.test.ts 2>&1); c=$?
  if [ $c -ne 0 ]; then printf '%s\n' "$out" | tail -n 25; fi
  ```
  A bare `[ $c -ne 0 ] && ...` leaves the shell at exit 1 and reads as a failure. Never pipe a failing suite through `head` or `tail`. `grep -c` exits 1 on zero matches.
- Write `# Notes` before you commit, and commit once, so the notes and the change land together. Build the subject and body from verified facts, record the commit by subject and never by SHA, and confirm it with one `git log --oneline -1` or `git show --stat`.

## Board, fixtures, and map

- `.kanban`, `SPECS.md`, and `AGENTS.md` are symlinks into the main checkout and are gitignored. Append `# Notes` through `SPECS.md`, under the existing heading and never as a second heading. Never write through `AGENTS.md` and never stage or commit board files. `.kanban/` is live shared state with concurrent writers: read a board file once and do not poll a file that another agent owns. If an acceptance check fails on a file you may not edit, write the decision in `# Notes` and stop.
- Fixture HOME is required for global state. `~/.pi`, `~/.config`, and `~/.gnupg` are read-only. Delete `XDG_CONFIG_HOME` with `delete process.env.X`, never `= undefined`. Keep fixture daemons inert with long rescan and poll intervals and `--no-webui`. Use `git -c commit.gpgsign=false commit` in fixture repos. A test that a page or plugin change adds must also pass in the fixture HOME.
- Shell traps: one argv over 131072 bytes fails with E2BIG. `ls -R` skips hidden directories, so use `find`, and `find` does not follow a symlinked directory, so use a trailing slash. A scratch script that imports `../src` lives under `tests/` and is deleted after the probe. Before you trust a count from a pipeline, run it on two known lines and look at the shape.
- Repo map: `src/orchestrator/pipeline.ts` holds sweeps, the reviewer cap, promotion, and `doneCleanup`. `liveness.ts` holds `poll()`, which also calls `promoteBacklog`, so a new parameter keeps its default. Worktree naming is in `src/kanban.ts`, tool registration in `src/tools.ts`, prompt rendering and spawn logging in `spawn.ts`, watch handlers and timers in `main.ts`. `src/webui/logpane.ts` holds `renderLogChunk`, `md`, `logFixups`, `esc`, and `LOG_LINES`. `payload.ts` builds the log window and its byte arithmetic, `page.ts` holds the single `PAGE` template literal, and `board.ts` holds the cards. Tests import from `../../src/*.ts` and `../helpers.ts`, with the repo root at `join(HERE, "../..")`. A function interpolated into `PAGE` must be self-contained, because module-scope constants and regexes do not travel into the template, and a regex literal written in `PAGE` loses a backslash. A page change needs a daemon restart. For a page test, reuse the file's extraction idiom: match `function name(...) { ... }`, run the source with `new Function`, and assert the returned value, not the whole `PAGE`.
