# developer

Project-specific guidance for the developer role. Facts here are verified: trust them without re-probing. At wrap-up, record each durable lesson as one Project-facts bullet; editing this file is the recorded way to keep lessons.

## Task start

- Fire every start read and grep in one parallel block, no plan prose: all independent locate greps in one block, then all target reads (source files, test parts, helpers) in one parallel block, then the one design pass; never a plan-only thinking block between single tool calls. Read each touched file once, whole, in that batch; a truncated read is not whole, so one continuation read at its offset completes it before you edit that file. A file over the 50 KB read limit gets every slice in that same parallel block (offsets from the wc -l count already in hand), never a chunk-size deliberation and never sequential slice rounds (#274 read page.ts and its test in two sequential slice rounds each, four read blocks where two would do). Locate before you read: grep the selector, assert text or function name for offsets first, then one read per hit; no blind offset slices. One grep per symbol or topic, no re-greps with a narrower scope. Design-time boundaries (line spans, item ends, extraction rules) are read once from the exact lines, then closed; never re-derive span arithmetic from memory. Trust this file's recorded facts at design time: do not re-locate a helper or class rule it already names.
- Step 2 is the one design pass: state, functions, edit anchors, tests, check command, suite list, written once. The design settles the test home (a pid-sweep regression part lives in tests/orchestrator/sweep.test.ts, a spawn fixture part in spawn.test.ts) and the test-run scope. A settled design is never re-litigated in a later thinking block; thinking after it only diagnoses red runs (the first Error line) (#270 spent three design-ish passes, one truncated mid-sentence over test placement).
- Judge the diff size before the read set. A one-line or small fix (label, color, chip, condition) reads the one helper and its test plus one `cat` of the task file: no knowledge-base search, no extra source files, no caller sweeps beyond the grep that names the helper. A SPECS.md that names every mechanism skips the knowledge-pages search too. Colors: mirror the nearest existing pattern, edit the test first, then the source. One grep for the old value across src, tests and docs is the allowed extra sweep for any changed pin. Decide a new comment's placement inside the edit that writes its code, never a follow-up pass.
- Decide once, then act, in the thinking block where the question first arises. A settled verdict stays closed: irrelevant evidence never re-opens it. An ambiguous spec point gets one reading, the simplest that satisfies the acceptance criteria: implement, then record the choice under # Open questions. A mechanism the spec or this file names is a fact: implement against it, never re-derive it from source or re-read the barrel. An import list, boot shape or mapping table gets one decision: no include-then-drop reversals; a carve-and-migrate mapping is decided once, by the scenario block each hunk extends.
- Settle the task premise in the start block, before any source trace. One command pair (`git log --oneline HEAD..main` or `<base>..main`, plus merge-base) settles landed-vs-absent and ff-vs-merge for any task that reports a failure on main, or whose branch may predate a fix. A main commit above your base that names the symptom or the task slug is the fix already landed: fast-forward, run the scoped suite, note, stop — no source trace, no re-diagnosis (#273 spent ~20 blocks re-deriving a race that main's 747ab05 had already fixed, because this check came last). To find which branches hold a commit: one `git branch -a --contains <sha>`, never hypothesis churn. A blocked or verification-only task forms its verdict from evidence already in hand: the same command pair, and gather every grep (src anchors AND test-side artifacts) in the start block; empty results are the expected evidence and close the question. On a confirmed blocked task the deliverable is the blocker note: one baseline suite run or assert count, appended under # Notes, then stop. The scheduler race that spawned you early is not your scope: no pipeline.ts reading, no board history, no worktree timeline, never implement a sibling subtask's scope in the parent worktree.
- A revert-style removal plans the inverse of the adding commit in the first pass: one full `git show` of that commit (never `--stat` plus a second full show), one grep per removed symbol across src, tests and docs, then one edit batch that removes the source, its test pins and its incidental touches (a label fallback goes back with its test pin). The scoped red-then-green run is the whole proof: no live check, no daemon, no Playwright unless the criteria explicitly demand one. Removal adds exactly one Project-facts bullet ("dropped in #NNN, do not reintroduce").
- Test-first, and the failing-file run is step 1 on a bug task, before any source trace (the start batch may bundle it). Add the failing assertion first for behavior changes, run the suite once, then fix. The failing run is the before-proof; never re-verify pre-fix behavior by hand. A red run may fail at import or syntax time (missing export, duplicate declaration); that still proves the tests are new: fix the error, do not add stub exports to reshape the run.
- Pin shipped wording or bytes as a literal expected string, never a file read inside the test (circular), never a regex where a literal `includes` of the spec's value works. Derive every expected literal and computed list with a node one-liner that prints it; never hand-write it; one ls of the worktree settles the real layout first. A formula or geometry change gets its constants in one pass, expected strings from the same one-liner, rendered text extracted once, then one suite run; no repeated hand arithmetic in thinking.
- When spec numbers (line counts, ranges, a referenced file) disagree with the worktree, one validation closes it: confirm the named anchors and one `grep -c "assert\."` over the extracted slice, implement with the worktree's numbers, record the shift under # Open questions. Never re-probe git history for the mismatch or re-check the same numbers later. An assert-count parity check is one command pair, one block.

## Scope and process discipline

- Read each target file once, then edit. Edit anchors come from read output already in context, verbatim, leading whitespace included. Read output truncates long lines, so a long line (a console.log, a long string) is not literal: anchor each hunk on the shortest unique line at the change (an assert line, a heading, a one-statement line), never a long line quoted from an earlier read display, never text assembled from memory or built in thinking (#270 lost three edit calls this way). Grep every mid-file anchor for uniqueness (0 or 1 hits) before the call: a 2-hit match applies nothing and costs a retry round. On a match failure: one byte check of the exact lines (`cat -A`, or grep -n), then one retry; never re-read the whole file. An anchor goes stale when your own edits shifted lines: grep the enclosing symbol, read the small slice, copy it verbatim. Draft each edit once in the design pass (anchors and hunk order), then the edit call goes out: a thinking draft rewritten several times overflows and truncates (#274's test-edit draft did).
- edit calls take edits as an array of {oldText, newText} objects, never a JSON string. Hunks in one batch must not overlap or touch the same region: merge nearby changes into one hunk first; an overlap rejection applies nothing and costs a re-plan round. A failed batch applies nothing: keep batches small and re-apply every edit of the batch on the retry, or the loss surfaces as a swallowed error and a long hunt. An empty newText deletes the match; oldText equal to newText is a skip.
- Appends and SPECS.md bookkeeping: an end-of-file append (role-file bullet, SPECS notes, task body) goes through bash (`cat >>`, heredoc), never an edit anchored at the tail. SPECS task files carry # Summary, # Specs and # Notes (some add # Acceptance or # Open questions): append completed-work bullets under the existing # Notes, never a second Notes heading. A missing heading gets added with its content in one edit. Draft the notes text once, append once: no wording pass, no placement re-work, no pre- or post-append heading or byte check. Inside a list you hold from a fresh read, oldText ends at the last line you keep and newText repeats it unchanged before the addition. Completed-work facts go under # Notes; assumptions and open points under # Open questions. Task-body edits: deviation note under the affected requirement, delete answered open questions, mark confirmed assumptions, one edit call. Anchor every mid-file SPECS.md edit with unique surrounding sentence text, never a bare heading.
- Sweep completeness before an edit batch: one grep per field read, per old symbol, and per changed user-visible string or CSS rule text across src and the tests that pin it, and fix every hit in the first batch. A change that makes the daemon mutate existing files (gzip, sweep, rename, compact) sweeps every suite pin of the old path or extension. A function that turns async or splits into light + heavy sweeps every field of the old return shape and every old-name call site: convert all callers to await in one batch.
- New module-level symbols that tests import get `export` at declaration.
- A repo-specific sentence removed from agents/*.md or SKILL.md goes as one bullet into .kanban/AGENTS.<role>.md in the main checkout, under the closest section.
- Verification budget: the scoped suite plus one git diff prove an edit. Do not re-read the edited region, re-grep your own notes, re-check your own wording, or re-run a suite that already passed. To check something you wrote, one grep or read settles it; never re-parse your own escaped tool-call output in thinking. A temp file you wrote this session is trusted content: analyze it with one grep batch, never re-read it slice by slice. Exception: a batch that hooks one new call at several integration points gets one hook-count grep before the suite run.
- The scoped suite is the whole test scope, and it overrides any spec or global instruction that seems to demand a full suite or more checks: run it, state the deviation once in # Notes, move on. The scope decision closes at design time, names the exact files, and stays closed through the green run, no re-deliberation before or after (#270 re-litigated it after the design pass, #269 before it, #274 after green over page.test.ts vs the five webui files). Mapping (scripts/test-changed.mjs; scripts/test-changed.test.mjs asserts the table): src/orchestrator.ts, src/pid.ts and agents/*.md map to every orchestrator area file; src/kanban.ts maps orchestrator + kanban + webui; src/hub.ts maps orchestrator + webui; src/webui.ts and src/webui/** map webui, always all five group files (page.test.ts alone is never the whole webui scope); src/efficiency-analysis.ts maps efficiency-analysis; index.ts maps index + extension tests; .claude-plugin/, hooks/ and .mcp.json map plugin.test.ts; package.json maps everything. Any other src/orchestrator/* module (pipeline.ts, report.ts, board.ts, log.ts, liveness.ts, spawn.ts, backends.ts) is not in the table and falls back to the full test set: run the scoped area file directly instead. Do not grep other suites for imports of the changed file; a barrel re-export edit pulls no other suite. A live check runs only when the criteria name behavior the scoped suite cannot pin (removal chores never do).
- Skip hindsight_reflect and similar long remote calls mid-task: it timed out at 300 s with a 504 and no results. A remote call that times out is never retried; the verified facts live in this file.
- Wrap-up: one git log plus one git status is the whole wrap-up, closed once commit and notes are done; no re-reasoning block after the commit step. Pre-commit, one git status plus one diff --stat settle the change set. No suite rerun, no .kanban symlink re-derivation or ls verification; /tmp fixtures need no cleanup. Lesson recording is decisive, not weighed: if the run hit a failure or surprise this file does not already name, append one Project-facts bullet; otherwise append nothing and move on (#270 closed its wrap-up with a long weighing block and recorded no bullet). AGENTS.md and this file are shared across concurrent agents: a number that disagrees with your grep takes one verification grep, then one edit; record your own bullets with one bash append.
- Keep each bash call single-purpose and small; one oversized call truncates, hides the result, and forces a rerun. An untracked file in git status is usually not yours: check mtime or git log once, then move on. An inline categorizer (awk field splits) that misclassifies falls back to the plain count.
- Fix the acceptance battery before editing SKILL.md or plugin files: the greps plus the one suite that reads the real files (plugin.test.ts), run once before commit and once at the end; no mid-check re-derivations of match counts.
- Todo list: one item per requirement, not per edit; on a big task the design lives in the todo list, written once. One parallel block creates every item, and each status flip rides in the same block as the work call it brackets; a standalone todo-only block is a wasted block (#269 spent ~10 blocks on 11 todo calls; b758a31 spent 15 on 15: five separate creates and ten standalone flips). todo calls take the action field.

## Running and testing

- Tests are plain assert-style ESM scripts, no framework: run one file with `node tests/<area>/<file>.test.ts` (re-locate a part by its `// --- part` marker, not by line number), `pnpm test` for the full suite, `pnpm test:changed` for the scoped run. Suites live in the four area dirs (tests/orchestrator, tests/webui, tests/efficiency-analysis, tests/kanban) plus the root files index.test.ts, tests/extension.test.ts, tests/mcp.test.ts, tests/plugin.test.ts, tests/context-symlinks.test.ts, tests/tools.test.ts. package.json test is a glob loop, tolerant of not-yet-existing area dirs. There is no typecheck: `npx tsc` prints "This is not the tsc command you are looking for". The repo runs `.ts` directly through node, so the suites are the only check.
- Before you add a test block to an existing suite, grep that file once for every planned local name (stubs, variables, helpers) and every fs or helper use against the suite's import lines, before the first write: a reused name or a missing import each cost a red run, a diagnostic round and a rename. A new fixture log in an existing suite: grep the suite once for full-enumeration asserts (a deepEqual over an agents array) and place the new test after them. Runs sort newest-first by log mtime, so the fixture log written last lands first: no utimesSync backdate. A new orchestrator smoke part copies the nearest existing part's harness and notes the sweep order and log-index rules once.
- Order a new test's steps so each assert that reads state comes before the call that mutates it, and assert the positive path before any mixed mutation call (#269's tools.test.ts marked a second task before the unprocessed-scope assert and went red on an empty list).
- A fixture rewrite that must invalidate a cache changes what the cache keys on, not just the value: logStats and subagentLogs (src/webui/payload.ts) key on path + size + a head fingerprint of the first 4 KB. Pick rewrite values that change the head bytes or the byte length; check the cache key once before writing the test.
- Run suites separately, redirect full output to a file, and capture the exit code in the launch command itself (`setsid bash -c 'pnpm test > /tmp/o 2>&1; echo $? > /tmp/o.exit'`), from the first run: a rerun launched only to recover an exit code is banned, and a lost exit code is proved from the log alone (all asserts passed and no AssertionError or ELIFECYCLE line is a pass record). Slice the redirected file afterwards (grep "Error" with context, then the summary line; a grep narrowed to AssertionError misses crash types like ENOENT). Never pipe the live run through head or tail: a cut hides the summary line and forces a second full run. The first Error line in the redirected log is the whole red diagnosis. A green log needs no greps: the smoke lines and the assert summary are the pass record; runDaemon captures daemon stdout in-process, so a passing orchestrator smoke run's log holds no daemon lines, never grep a green log for them. In the webui area suites board, logpane and agentlog print nothing on success while page and hub print "all assertions passed": for the silent ones the exit code is the pass record.
- A background run gets no completion notification: sleep 60-120 s between log polls and do green-independent work meanwhile, draft and append the SPECS notes during the wait, the sleep call and the notes append in one block; only a success claim waits for the green result (#270 and #269 both slept idle with the notes unwritten). Do not run two suites at once: they share .pids, ports and fixture HOMEs.
- `grep -c` exits 1 on zero matches: a 0 count from a failure-shaped grep is a pass, not a broken command; append `|| true` when the count sits in a chained command.
- pnpm on the read-only worktree mount prints ERR_PNPM_STORE_DIR_OPEN_OPERATION_LOCK: benign noise, the suite still runs and passes. Never chase it or re-check whether it failed the run.
- A failure whose output ends parsing "hub error" as JSON means a hub route's handler threw: src/hub.ts:324 swallows every handler exception into that plain string. Write the minimal node probe of the payload functions first.
- PAGE (src/webui/page.ts) is one template literal served as the whole client. A regex written inside it loses its backslash: write `\\.` where the served string must hold `\.`, and asserts on served text match the built PAGE string, never the source-file bytes. Any assert that regex-extracts a value gets one node one-liner print against the real string before the first suite run; NaN in a failure message is the regex-missed signature. Exported helpers interpolate with `${fn}`: Function.prototype.toString strips the `export` keyword, so the served string stays valid.
- Suite-split layout facts. Webui: the five group files (tests/webui/hub, board, logpane, agentlog, page.test.ts) are the whole webui suite; tests/webui.test.ts is deleted, so extend the group file whose scenario block covers the change; line numbers drift, grep for the anchors. In tests/webui/ group files HERE is tests/webui: repo-root paths need join(HERE, "../.."), a src probe join(HERE, "../../src"), and src imports are ../../src/*.ts. Orchestrator: the 13 area files under tests/orchestrator/ (spawn, poll, promote, merge, log, hub, singleton, worktree, config, sweep, analysis, split, daemon) plus shared tests/helpers.ts, which exports HERE, fixture, mirrorSubjects, showTip, roleStub, argvStub, llmArgs, deadStub, runDaemon, waitFor, waitForAsync, freePort, runIdx, cleanupAll, killAll, daemons, cleaned, the XDG_CONFIG_HOME deletion and the exit handlers; externalCommit, taskContent and lingerAgent stay local to worktree.test.ts. In tests/orchestrator/* HERE is tests/orchestrator: src imports are ../../src/*.ts and helpers import ../helpers.ts; tests/helpers.ts sits at tests/, so its src imports are ../src/*.ts. tests/helpers.ts is imported by orchestrator and efficiency-analysis files only; webui and kanban group files are standalone by design (tests/efficiency-analysis/ has its own local helpers.ts for its JSONL fixtures). src/webui.ts is a re-export shim and does not re-export PRIORITY_RANK: import it from src/kanban.ts. docs/development.md carries the test-command list, so a suite move updates it in the same change.
- A suite split (mechanical transform of a big suite) is driven from a generator script, and every invariant is proven BEFORE any suite run: assert-count parity (`grep -c "assert\."` old vs new), each moved name greps 0 or 1 times in the emitted files (never 2), the emitted header never imports the file it lands in (a self-import breaks every emitted file), and one `node -e 'import("<file>")'` load check per emitted file. Import-time errors surface in that 1 s probe; caught at suite-run time they cost the multi-minute run.
- Parsing a suite for top-level items: column-0 declarations inside template literals are not top-level; track backtick parity per line. Identifier cross-checks: \b regexes over test text match template-literal interiors, `--flag` tokens and comment words; strip `--[\w-]+` tokens before matching and filter the warning list by the moved names only. Removing several spans from one text: collect the spans, sort descending, then splice, and stop a comment walkback at `// --- part` markers.
- Verbatim test lift (the sed recipe): trust the spec's line ranges, never hand-count them. One pass: extract each range once with `sed -n '<a>,<b>p' <old> > /tmp/range`, then the dependency checks in the same block: one identifier-count loop over the slice, each planned symbol against import lines and module exports, one grep per ambiguous hit (string literal vs real use), line-number greps for out-of-range identifiers the slice reads (copy their definitions in with the header), and one grep of src/hub.ts for unref/close when the boot starts a hub. For a standalone group file, copy the nearest existing group's boot plus the spec's boot lines; boot guards are plain `if (!x) throw`, never assert.*, when the count is pinned. Append with `cat`, close with the boot's process.on cleanup or the group's trailing teardown, then verify once: `grep -c "assert\."`, one run, one byte-identity diff per slice; never grep-derived line variables in shell arithmetic (an empty match builds a broken sed) and never hand-counted offsets. A referenced sibling group file may sit on an unmerged task branch: if its read fails with ENOENT, pull it with `git show <commit>:<path>` (hash from one `git log --all --oneline -- <path>`), never a second path guess.
- Post-carve hunk migration (the spec names the carve base and the split homes): diff base..HEAD is the whole work list; the verbatim lift recipe extracts and verifies each hunk. Home every hunk once in the design pass, by the scenario block it extends, then splice with one script (keep its non-unique-anchor abort before the first write). Settle imports in the same pass as the splice write: grep the moved blocks' fs, zlib and payload calls against the target file's import lines; barrel-internal helpers import from ../../src/webui/<module>.ts, not the barrel. Verify once: byte-identity diff per block and assert-count parity.
- log() (src/orchestrator/log.ts) echoes to stdout unless fd 1 is the log file itself (dev+ino check). The daemon harnesses (runDaemon, sEnv/sFlag, the hub and worktree parts) assert log() lines from the daemon's piped stdout, so never drop the non-TTY echo without moving those harnesses to read the log file first.
- The .pids janitor (janitorPids in src/orchestrator/pipeline.ts) sweeps .exit files by name shape and dead generic pid files, per file shape: `<slug>.pid` only when the slug is off the board (a board task's per-task pid stays; the poll consumes it in every state: exit code, armed reviewer marker, dead-streak clear), `<slug>.splitter.pid` only when its task left to-do (startTodo reads the dead file as the splitter-ran marker), `<slug>.<role>.<n>.analysis.pid` when dead; `merger.pid` is never swept. The keep set deliberately covers every board state: a stricter sweep races the liveness poll (poll.test.ts part B). Pinned by part AP in tests/orchestrator/sweep.test.ts (8 asserts). A new marker file in .pids must join its keep rules or the sweep deletes it within one sweep. Dead-pid fixtures are hand-written orphan pid files: rmSync of a tracked file does not stick, reconcileBoard restores mirror files. Paired guard: spawnRunAnalysis (src/orchestrator/spawn.ts) skips when the per-run `<slug>.<role>.<n>.analysis.exit` marker exists, or when the run already has its report or its doctor log, plain or gzipped, so a failed analysis spawns once; the to-merge sweep fires the per-run analysis before the merge pass.
- To make a spawned analysis fail deterministically end to end, hand-write the finished run's log as a corrupt .log.gz (the compactor pattern skips .gz and the runner's gunzip throws); chmod 000 on the plain log races the sweep's retro-compact.
- Commit messages state only verified facts. Diff old vs new output before claiming byte-identity or behavior parity; an overclaim forces a soft-reset re-commit.
- Analysis prompt builders live in src/efficiency-analysis.ts (splitAnswer, doctorPrompt). There is no src/orchestrator/prompts.ts.

## Test-harness waits

- A wait loop over spawned processes must sleep between checks (about 50 ms): a synchronous busy spin blocks node's event loop, the SIGCHLD reaper never runs, and the exited sh wrapper lingers as a zombie whose /proc entry keeps pidAlive true forever. Make the helper async and wait for the exit file AND a dead pid (both, not one: the wrapper writes the exit file about 35 ms after spawn but can still be alive across the test's next synchronous call).
- When such a wait misbehaves, suspect the reaper before the spawn. Confirm with one minimal isolated probe (spawn a stub, loop, watch /proc/<pid>/stat and cmdline), never by re-reading the spawn and pid code.

## Temp fixture scripts

- A temp orchestrator part lives in tests/ from the first write, never /tmp: relative `../src` imports break from /tmp with ERR_MODULE_NOT_FOUND. Temp scripts outside a package need the `.mjs` extension; when a fixture must keep a specific name (e.g. `orchestrator.ts` for cmdline matching), drop a `package.json` with `{"type": "module"}` next to it, else node loads the `.ts` as CJS.
- Write a temp fixture script complete on the first write: call shapes from the tests (setState takes a Task from getTask(root, file), not a file reference) and JSONL record shapes from the fixtures the tests build. A wrong call costs a TypeError, a signature grep, and a rerun.
- Never patch temp scripts with sed. Use the edit tool: sed clashes on `|` and `/` delimiters and can leave broken syntax that kills node.
- Verify a new fixture with find, not ls -R: ls -R does not list hidden dirs.
- chmod 555 on a directory does not block writes to a file that already exists inside it: to make a create-or-write fail in a test, delete the file first, then lock the directory.
- Worktree fixture doubts (index flags, history) settle with one command pair: `git -C <wt> ls-files -v` (S marks skip-worktree) plus `git -C <wt> log --oneline`.
- A temp splice or migration script with no src imports can live in /tmp. It is plain JS: no TS-only syntax (`as const`, type annotations) in a .mjs file. Run `node --check` before the first execution, and grep every edit anchor for uniqueness (0 or 1 hits) while authoring, so the script's own non-unique-anchor abort never fires.

## Stale-test triage

- A suite failure on prompt text: do not build a harness first. Read the assertion, then grep the prompt source (agents/*.md) for the asserted phrase. If the phrase is absent at HEAD, the test is stale: `git log -S'<phrase>' -- <file>` names the commit that dropped it; a one-line assertion fix ends it.
- Flake vs regression is a fixed protocol, in order, then closed: (1) one standalone run of the failing file, before any source trace; (2) one `git stash push` + run at HEAD + `git stash pop` cycle; (3) verdict, then no second stash cycle, no source read of the racing module, no hypothesis chain after the verdict (#269's triage spent ~30 blocks, 12 of them circular thinking, re-deriving liveness.ts counters after its HEAD run had already passed). An orchestrator part with no plausible link to the diff is a timing flake until HEAD proves otherwise; a one-sided pattern (fails with the diff, passes once at HEAD) with no plausible link is still a flake, so grep the diff's symbols against the failing file once, then settle it with the probe below.
- A reported-red test that reruns green (exit 0) is a race or a stale branch, never a live regression to re-diagnose by source reading. Settle it in one block with two one-command checks: the landed-on-main pair (`git log --oneline HEAD..main` plus merge-base) and the output-capturing probe (a temp tests/tmp-*.ts that reproduces the scenario, dumps the daemon or fixture output to a file, and prints the racing lines with their task slugs). #273 reran green and then burned ~12 blocks of reads over liveness.ts, pipeline.ts, helpers.ts and config.ts, while this file already named the fix (the cooldownB scoping) and the main log named 747ab05 in one command. A test that fails in the full suite but passes standalone is a load-dependent timing race: no further full runs, go straight to the probe; one probe run names the double-firing process (#269's probe named the second task's cooldown line in one run, after a dozen blocks of source reading had not). When the acceptance criterion is the suite, fixing that race is in scope: the criterion answers the scope question. Fix real test-race flakes at the root cause: gate the fixture write against the racing machinery (an openQuestions-backed task is never promoted).
- An assert that counts log lines by substring scopes each count to one task's lines (filter by the task slug prefix, the cooldownB helper pattern in poll.test.ts): sibling fixture tasks log the same phrases at cap+1 and inflate the count (the bare "respawn waits for the idle cooldown" count took the dead live-tester's line too, 2 !== 1; the slug-scoped fix landed on main as 747ab05, and un-scoping them re-opens that flake). Grep a new count assert's substring across the part's fixture tasks once at design time; a shared phrase gets the slug-scoped helper from the first write.

## Test recipes

- To intercept src module internals from a test (fs calls, hooks inside a function), spawn a child with `--require <preload.cjs>`: patches to `require("node:fs")` propagate to ESM named imports only when installed before the first import; an in-process patch never does (facade bindings resolve at first import). Patch the fs call the reader actually uses: payload.ts reads plain logs through openSync/readSync byte windows (a readFileSync stub no longer intercepts them), and readFileSync before it.
- Deterministic interleaving in orchestrator tests: drive `rescan(root, cfg)` and `poll(root, stallMinutes)` directly (import `rescan` from `../../src/orchestrator/pipeline.ts` in an area file, `poll`/`loadConfig` from the facade; temp HOME via mkdtempSync + loadConfig; `cfg.agent = <stub>`), instead of daemon timing races. A stub that Atomics.waits ~1 s keeps a spawned agent alive across the next synchronous call.
- Concurrency-cap tests (maxParallel pattern, b758a31): drive `loadConfig` + `rescan(root, cfg)` directly, no poll, and plant stable slot-holder tasks in the counted states; free a slot by setState of one holder to a non-counted state (the cap counts WORKING_CAP_STATES only), which frees a slot without removal side effects.
- Asserts on the meta/kanban mirror right after a done transition race the sweep: the fold-in commit that carries the new files can land one sweep after state turns done and the worktree clears, so gate the mirror read with the existing waitFor until the expected files appear on the mirror.
- Asserts on end-of-run state go before the call that clears that state: symlink/readlink asserts come before poll (clearContextSymlinks runs at run end); file-restored asserts after it.

## Environment and safety

- In a task worktree, `.kanban` is a symlink to the main checkout's board and SPECS.md is a symlink to `.kanban/<NNN>_<slug>.md`, your task's file: writing either edits the main checkout, and git in the worktree reports `.kanban/...` as "beyond a symbolic link" (never stage or commit those; the daemon commits board changes itself). Board files are untracked in the checked-out branch: the daemon mirrors them onto refs/heads/meta/kanban via git plumbing and pushes, so `git log -- .kanban/` prints nothing and board history is `git log meta/kanban --oneline -- <file>` (or `git log --all -- <file>`). The main checkout root also carries a SPECS.md symlink that rotates to the current active task's file; greps or tails on SPECS.md fail from any cwd other than a root, so run them from a root or through the resolved numbered path.
- Read-only HOME mounts: ~/.pi, ~/.config and ~/.gnupg are read-only bind mounts on this machine. Any test or close() flush that touches the real user config dir crashes (or pollutes it on normal machines): keep global-state tests on fixture HOMEs and close in-process hubs before restoring the real HOME. A worktree commit needs `git -c commit.gpgsign=false commit`, else "gpg failed to sign the data". Stage first: a bare commit with unstaged edits fails with "no changes added to commit".
- `process.env.X = undefined` sets the env to the string "undefined" in node: use `delete process.env.X` when restoring an unset variable, else later code resolves paths like undefined/se-llm-team and litters the cwd.
- Neutral shared paths: the global config, hub registry and hub lock live at $XDG_CONFIG_HOME/se-llm-team/ (else ~/.config/se-llm-team/), with the legacy ~/.pi/agent paths as read-only fallbacks; every temp-HOME test env must also set or delete XDG_CONFIG_HOME, since the real environment may set it and leak the production config into tests.
- Large argv: the kernel rejects a single argument over 131,072 bytes with E2BIG (MAX_ARG_STRLEN); node spawn reports it as a child 'error' event and the child never starts. The AGENTS.md injection cap (PROJECT_PROMPT_CAP, src/orchestrator/spawn.ts) is 131,000, covered by a real stub spawn in tests/orchestrator/spawn.test.ts.
- Daemons under test never touch the production webui. Smoke daemons start with `--no-webui` (or SE_LLM_TEAM_NO_WEBUI=1), because a smoke daemon reads the global config and binds the production webui port, wedging the real UI. Live-check daemons get the fixture its own per-root port in the project config, never the global one.
