# developer

Project-specific guidance for the developer role. Facts here are verified: trust them without re-probing. At wrap-up, record each durable lesson as one Project-facts bullet; editing this file is the recorded way to keep lessons.

## Task start

- Fire every start read and grep in one parallel block, no plan prose: batch greedily, all independent locate greps in one block, then all target reads (source slices, test parts, helpers) in one parallel block, then the one design pass; never a plan-only thinking block between single tool calls (#245, #247, #248; #266 spent 28 blocks before the first edit, eight of them plan-only thinking). Step 2 is the one design pass: state, functions, edit anchors, tests, check command, written once, never a second design pass (#264 burned six planning blocks re-drafting the same shape). Step 3 is edits and checks; thinking from there only diagnoses red runs (the first Error line), never re-designs. Locate before you read: grep the selector, assert text or function name for offsets first, then one read per hit; no blind offset slices (#238). On a mechanism task, read each touched source file once, whole, in the start batch: sed slices re-read across a run cost a tool block each and re-open a reader census that already closed (#267 read pipeline.ts in five slices, liveness.ts and spawn.ts twice each). One grep per symbol or topic, no re-greps with a narrower scope, even when a later block re-raises the question (#245, #249, #260, #252). Design-time boundaries (line spans, item ends, extraction rules) are read once from the exact lines, then closed; never re-derive span arithmetic from memory (#255). Trust this file's recorded facts at design time: do not re-locate a helper or class rule it already names (#252 re-grepped buildShell on the wrong file, then wrote the column selector against it wrong).
- Judge the diff size before the read set. A one-line or small fix (label, color, chip, condition) reads the one helper and its test plus one `cat` of the task file: no knowledge-base search, no extra source files, no caller sweeps beyond the grep that names the helper (#227, #226, #239). A SPECS.md that names every mechanism skips the knowledge-pages search too (#264 got empty snippets, #252 got unrelated pages). Colors: mirror the nearest existing pattern, edit the test first, then the source (#226, #240). One grep for the old value across src, tests and docs is the allowed extra sweep for any changed pin (#240, #244). Comments fall under "add nothing unrequested" (#239): decide a new comment's placement inside the edit that writes its code; never a follow-up pass to move or re-verify it (#266 spent four blocks on one comment line: misplaced edit, move, re-correct, re-read).
- Decide once, then act, in the thinking block where the question first arises. A settled verdict stays closed: irrelevant evidence never re-opens it, and a settled design is never re-litigated before re-reading the files (#252, #261, #255). An ambiguous or contradictory spec point gets one reading, the simplest that satisfies the acceptance criteria: implement, then record the choice as an assumption under # Open questions. A question re-opened twice is closed on the third pass by that same rule, with no more evidence gathering (#224, #228; #267 re-derived the janitor keep rules and their poll race across six thinking blocks, 86% of the run's thinking output in eight blocks: the one conservative keep rule, all board states keep their pid, closed it at once). A mechanism the spec or Project facts names (payload split, alive semantics, stats summing, a suite split layout) is a fact: implement against it, never re-derive it from source or re-read the barrel (#247, #251, #264). An import list, a boot shape or a mapping table gets one decision too: no include-then-drop reversals (#261, #255). A carve-and-migrate mapping is decided once, by the scenario block each hunk extends, then closed: no re-derivation, no re-reads of held files, no hedge-restarts (#256 blocks 9-27 cost about 12 of 64 blocks).
- A blocked or verification-only task forms its verdict in the start block from evidence already in hand: one command pair (`git log --oneline main..HEAD` plus merge-base) settles landed-vs-absent and ff-vs-merge in one block. Git log output is never re-parsed for duplicate or truncated lines: one exact rerun if it looks wrong, then close (#256). A verdict built on a stale base re-plans the run (#252). On a confirmed blocked task the deliverable is the blocker note: one grep for the named endpoint or export in src plus one baseline suite run or assert count, appended under # Notes, then stop. The scheduler race that spawned you early is not your scope: no pipeline.ts reading, no blockedBy greps, no board history, no worktree timeline, no implement-vs-report re-litigation, never implement a sibling subtask's scope in the parent worktree (#252: about 20 of 49 blocks).
- A revert-style removal plans the inverse of the adding commit in the first pass: one full `git show` of that commit (never `--stat` plus a second full show, #249), one grep per removed symbol across src, tests and docs, then one edit batch that removes the source, its test pins and its incidental touches (a label fallback goes back with its test pin). The scoped red-then-green run is the whole proof: no live check, no daemon, no Playwright unless the criteria explicitly demand one (#249). Removal adds exactly one Project-facts bullet ("dropped in #NNN, do not reintroduce"): requested cleanup, not an addition.
- Pin shipped wording or bytes as a literal expected string, never a file read inside the test (circular), never a regex where a literal `includes` of the spec's value works (#240). Derive every expected literal and every expected list of computed output with a node one-liner that prints it; never hand-write it; one ls of the worktree settles the real layout first (#250, #255). A formula or geometry change gets its constants in one pass, expected test strings from the same one-liner, rendered text extracted once, then one suite run; no repeated hand arithmetic in thinking (#228, #238).
- Test-first: add the failing assertion first for behavior changes, run the suite once, then fix. The failing run is the before-proof; never re-verify pre-fix behavior by hand afterwards (#227). A red run may fail at import or syntax time (missing export, duplicate declaration); that still proves the tests are new: fix the error, do not add stub exports to reshape the run (#230, #243).
- The test home is decided at design time, never deliberated: a janitor or pid-sweep regression part lives in tests/orchestrator/sweep.test.ts, a spawn fixture part in spawn.test.ts (#267 spent three thinking blocks on sweep.test.ts vs spawn.test.ts). A new orchestrator smoke part copies the nearest existing part's harness and notes the sweep order and log-index rules once (#229). After one failed full check run, write one minimal probe that varies every hypothesis in one script (see Live webui checks); never one check run per hypothesis or a hypothesis chain in thinking (#234, #247, #250, #251). Keep harness time small (#234: 60 of 155 blocks on wait helpers; #251: about 50 of 95 on one live check; #252: three blocks re-drafting fixture, routes and request counts).
- When spec numbers (line counts, ranges, a referenced file) disagree with the worktree, one validation closes it: confirm the named anchors and one `grep -c "assert\."` over the extracted slice, implement with the worktree's numbers, record the shift under # Open questions. Never re-probe git history for the mismatch or re-check the same numbers later (#261, #255). An assert-count parity check is one command pair (old vs new totals, one block): compute, then close; never re-cycle the totals in thinking (#254 re-cycled 558/562/739/797 across four thinking blocks).

## Scope and process discipline

- Read each target file once, then edit. Edit anchors come from read output already in context, an exact copy of the lines, leading whitespace included. Never re-read lines you hold (#237, #242). On a match failure: one byte check of the exact lines (`cat -A`), then one retry; never re-read the whole file (#231, #242). An anchor goes stale when your own edits shifted the lines: grep the enclosing symbol, read the small slice, copy it verbatim; never assemble oldText from memory, from strings built in thinking, or from a stale in-context copy (#247, #250, #260). Grep a mid-file anchor for uniqueness (0 or 1 hits) before the call: a 2-hit match applies nothing and costs a retry round (#254).
- edit calls take edits as an array of {oldText, newText} objects, never a JSON string (#237). Hunks in one batch must not overlap or touch the same region: merge nearby changes into one hunk before the call; an overlap rejection applies nothing and costs a re-plan round (#264). A failed batch applies nothing: keep batches small (#242) and re-apply every edit of the batch on the retry, or the loss surfaces as a swallowed error and a long hunt (#250). An empty newText deletes the match (#249); oldText equal to newText is a skip (#244).
- Appends and SPECS.md bookkeeping: an end-of-file append (role-file bullet, SPECS notes, task body) goes through bash (`cat >>`, heredoc, printf), never an edit anchored at the tail (#260). SPECS task files carry the template headings # Summary, # Specs and # Notes (some add # Acceptance or # Open questions): append completed-work bullets under the existing # Notes, never append a Notes heading line — a redundant ## Notes under the existing # Notes cost three cleanup blocks in #265 (blocks 18-21). A missing heading gets added with its content in one edit (#230). Draft the notes text once, append once: no wording pass, no placement re-work, no pre- or post-append heading or byte check (#261, #252, #256; #266 ran an od -c tail check before the SPECS append; #267 re-counted heredoc asserts in two blocks after the append and re-read its own role-file bullet in two more over a suspected typo). Inside a list you hold from a fresh read, oldText ends at the last line you keep and newText repeats it unchanged before the addition; never drop existing lines (#244). Completed-work facts go under # Notes; assumptions and open points under # Open questions. Task-body edits: deviation note under the affected requirement, delete answered open questions, mark confirmed assumptions, one edit call (#228). Anchor every mid-file SPECS.md edit with unique surrounding sentence text, never a bare heading.
- Sweep completeness before an edit batch: one grep per field read, per old symbol, and per changed user-visible string or CSS rule text across src and the tests that pin it, and fix every hit in the first batch. A page.ts CSS edit that adds a property to a pinned rule costs a red full-suite run plus a diagnosis round when the pin is not swept (#264). When a change makes the daemon mutate existing files (gzip, sweep, rename, compact), the same sweep covers every suite pin of the old path or extension (#250). When a function turns async or splits into light + heavy, the same sweep covers every field of the old return shape and every old-name call site: convert all callers to await in one batch (#248, #242, #244).
- New-code plumbing is checked in the pass that writes it: new module-level symbols that tests import get `export` at declaration (#250).
- A repo-specific sentence removed from agents/*.md or SKILL.md goes as one bullet into .kanban/AGENTS.<role>.md in the main checkout, under the closest section (#225).
- Verification budget: the scoped suite plus one git diff prove an edit. Do not re-read the edited region, re-grep your own notes, re-check your own wording, or re-run a suite that already passed (#228, #231). To check something you wrote, one grep or read settles it; never re-parse your own escaped tool-call output in thinking (#232, #243, #244). A temp file you wrote this session is trusted content: analyze it with one grep batch, never re-read it slice by slice (#260). Exception: a batch that hooks one new call at several integration points gets one hook-count grep before the suite run (#237).
- The scoped suite is the whole test scope, and it overrides any spec or global instruction that seems to demand a full suite or more checks: run the scoped suite, state the deviation once in # Notes, move on — the deliberation is the waste (#239; #265 blocks 14 and 22). The scope decision closes at design time from the scripts/test-changed.mjs mapping and stays closed through the green run: no re-deliberation before or after (#266 re-litigated it in two thinking blocks, one after the suite had already passed). The mapping: src/orchestrator.ts, src/pid.ts and agents/*.md map to every orchestrator area file; src/kanban.ts and src/hub.ts map the webui area, and shared src/hub.ts also pulls the multi-minute orchestrator suite (#242); test-changed.test.mjs asserts the table. Any other src/orchestrator/* module (pipeline.ts, log.ts, liveness.ts) is not in the table and falls back to the full test set: run the scoped area file directly instead (#266). Do not grep other suites for imports of the changed file (#238); a barrel re-export edit pulls no other suite (#249). A live check is not boilerplate: run one only when the criteria name behavior the scoped suite cannot pin (removal chores never do), and build its fixture from the recipes below (#243, #251).
- Skip hindsight_reflect and similar long remote calls mid-task: it timed out at 300 s with a 504 and no results (#244). A remote call that times out is never retried; the verified facts live in this file.
- Wrap-up: one git log plus one git status is the whole wrap-up, closed once commit and notes are done; no weighing whether a lesson bullet is worth recording, and no re-reasoning block after the commit step (#240, #265, #266). Pre-commit, one git status plus one diff --stat settle the change set; no second removed-lines diff re-deriving what a splice script's checks already proved (#256). No suite rerun, no .kanban symlink re-derivation or ls verification; /tmp fixtures need no cleanup (#231, #243, #244, #245). The commit step's own check is one git status with no thinking block around it; no second status after it (#240, #265 block 22). AGENTS.md and this file are shared across concurrent agents: a number that disagrees with your grep takes one verification grep, then one edit; record your own bullets with one bash append (#252 blocks 77-82).
- Keep each bash call single-purpose and small; one oversized call truncates, hides the result, and forces a rerun (#225, #228, #251). An untracked file in git status is usually not yours: check mtime or git log once, then move on (#226). An inline categorizer (awk field splits) that misclassifies is not re-tuned: fall back to the plain count, the simple inventory is enough (#267 mislabeled five analysis.pid files as other and re-derived the split by hand).
- Fix the acceptance battery before editing: the greps plus the one suite that reads the real files (plugin.test.ts for SKILL.md changes). Run it once before commit and once at the end; no mid-check re-derivations of match counts.
- Todo list: one item per requirement, not per edit; on a big task the design lives in the todo list, written once. Create all items in one block (parallel creates), and fold each status flip into the block with the work call it brackets; never a standalone todo-only block (#264 spent 17 of 68 blocks on todo calls; #252 spent 8 of 87 with five standalone flips). todo calls take the action field (#245).

## Running and testing

- Tests are plain assert-style ESM scripts, no framework: run one file with `node tests/<area>/<file>.test.ts` (every suite lives in an area dir since #254: orchestrator, webui, efficiency-analysis, kanban; 36 suites total), `pnpm test` for the suite, `pnpm test:changed` for the scoped run. package.json test is a glob loop over index.test.ts and tests/*/*.test.ts, tolerant of not-yet-existing area dirs (landed in 98e66b0 with the orchestrator split). There is no typecheck: `npx tsc` prints "This is not the tsc command you are looking for". The repo runs `.ts` directly through node, so the suites are the only check.
- Before you add a test block to an existing suite, grep that file once for every planned local name (stubs, variables, helpers) and every fs or helper use against the suite's import lines, before the first write: a reused name or a missing import each cost a red run, a diagnostic round and a rename (#243, #248, #250).
- A new fixture log in an existing suite: grep the suite once for full-enumeration asserts (a deepEqual over an agents array) and place the new test after them (#247). Runs sort newest-first by log mtime, so the fixture log written last lands first: no utimesSync backdate (#247).
- A fixture rewrite that must invalidate a cache changes what the cache keys on, not just the value: logStats and subagentLogs (src/webui/payload.ts) key on path + size + a head fingerprint of the first 4 KB (#250). Pick rewrite values that change the head bytes or the byte length; check the cache key once before writing the test (#245, #251).
- Run suites separately, redirect full output to a file in the same command (`node tests/x.test.ts > /tmp/o 2>&1`), and slice the file afterwards (grep "Error" with context, then the summary line; a grep narrowed to AssertionError misses crash types like ENOENT, #250). Never pipe the live run through head or tail: a cut hides the summary line and forces a second full run (#229, #232, #237). The first Error line in the redirected log is the whole red diagnosis (#242). A green log needs no greps: the smoke lines and the assert summary are the pass record. Daemon stdout is captured in-process by runDaemon, and waitFor prints it only when it times out, so a passing orchestrator smoke run's log holds no daemon lines; never grep a green log for them (#266 spent four blocks hunting daemon output that was never there; #267 doubted a captured exit 0 and grepped a green log for asserts across three blocks). A background run gets no completion notification: sleep 60-120 s between log polls and do other work meanwhile. Do not run two suites at once: they share .pids, ports and fixture HOMEs (#255).
- Capture the exit code in the launch command itself (`setsid bash -c 'pnpm test > /tmp/o 2>&1; echo $? > /tmp/o.exit'`), from the first run: a run launched bare cannot prove its exit code, and a rerun launched only to recover an exit code is banned (#254: one bare launch cost two extra multi-minute full-suite runs). A lost exit code is proved from the log alone: the last file reports all asserts passed and no AssertionError or ELIFECYCLE line is a pass record.
- `grep -c` exits 1 on zero matches: a 0 count from a failure-shaped grep is a pass, not a broken command; append `|| true` when the count sits in a chained command (#254 misread a green log as failed).
- pnpm on the read-only worktree mount prints ERR_PNPM_STORE_DIR_OPEN_OPERATION_LOCK: benign noise, the suite still runs and passes, and `npm_config_verify_deps_before_run=false` does not suppress it. Never chase it or re-check whether it failed the run (#254 re-checked it across the run).
- A failure whose output ends parsing "hub error" as JSON means a hub route's handler threw: src/hub.ts:324 swallows every handler exception into that plain string. Write the minimal node probe of the payload functions first (#250).
- PAGE (src/webui/page.ts) is one template literal served as the whole client. A regex written inside it loses its backslash: write `\\.` where the served string must hold `\.`, and asserts on served text match the built PAGE string, never the source-file bytes. Any assert that regex-extracts a value gets one node one-liner print against the real string before the first suite run; NaN in a failure message is the regex-missed signature (#237, #239). Exported helpers interpolate with `${fn}`: Function.prototype.toString strips the `export` keyword, so the served string stays valid (#244).
- Suite-split layout facts. Webui: the five group files (tests/webui/hub, board, logpane, agentlog, page.test.ts) are the whole webui suite since #256 (9673b45); tests/webui.test.ts is deleted, so extend the group file whose scenario block covers the change; union 797 asserts (hub 101, board 186, logpane 61, page 270, agentlog 179); line numbers drift, grep for the anchors (#261). In tests/webui/ group files HERE is tests/webui: repo-root paths need join(HERE, "../.."), a src probe join(HERE, "../../src"), and src imports are ../../src/*.ts (#259). Orchestrator: the 13 area files under tests/orchestrator/ plus shared tests/helpers.ts are the layout (inventory in Project facts). In tests/orchestrator/* HERE is tests/orchestrator: src imports are ../../src/*.ts and helpers import ../helpers.ts; tests/helpers.ts sits at tests/, so its src imports are ../src/*.ts. src/webui.ts is a re-export shim for ./webui/index.ts and does not re-export PRIORITY_RANK: import it from src/kanban.ts. Since #254 the suite is four area dirs only (orchestrator, webui, efficiency-analysis, kanban; the root suite files are deleted): tests/efficiency-analysis/ holds 203 asserts and a local helpers.ts for its JSONL fixtures, tests/kanban/ holds 179, and docs/development.md carries the test-command list, so a suite move updates it in the same change. tests/helpers.ts is imported by orchestrator and efficiency-analysis files only; webui and kanban group files are standalone by design, and a per-file one-line `const HERE` is not a copy-pasted helper block: settled, do not re-litigate (#254 re-asked it across four blocks).
- A suite split (mechanical transform of a big suite) is driven from a generator script, and every invariant is proven BEFORE any suite run: assert-count parity (`grep -c "assert\."` old vs new), each moved name greps 0 or 1 times in the emitted files (never 2), the emitted header never imports the file it lands in (a self-import breaks every emitted file), and one `node -e 'import("<file>")'` load check per emitted file. Import-time errors surface in that 1 s probe; caught at suite-run time they cost the multi-minute run (#255: three background runs, two broken by a duplicate createServer import, a helpers.ts self-import and a wrong ../../src depth).
- Parsing a suite for top-level items: column-0 declarations inside template literals are not top-level; track backtick parity per line (#255: 26 vs 21 helper items). Identifier cross-checks: \b regexes over test text match template-literal interiors, `--flag` tokens and comment words; strip `--[\w-]+` tokens before matching and filter the warning list by the moved names only, never triage the flood (#255: 621 warnings hid 5 real dependencies). Removing several spans from one text: collect the spans, sort descending, then splice, and stop a comment walkback at `// --- part` markers; verify each removal by grepping the emitted files for the moved name, never re-derive index arithmetic in thinking (#255).
- Verbatim test lift (the sed recipe): trust the spec's line ranges, never hand-count them. One pass: extract each range once with `sed -n '<a>,<b>p' <old> > /tmp/range`, then the dependency checks in the same block: one identifier-count loop over the slice, each planned symbol against import lines and module exports, one grep per ambiguous hit (string literal vs real use), line-number greps for out-of-range identifiers the slice reads (copy their definitions in with the header), and one grep of src/hub.ts for unref/close when the boot starts a hub. For a standalone group file, copy the nearest existing group's boot plus the spec's boot lines; boot guards are plain `if (!x) throw`, never assert.*, when the count is pinned. Append with `cat`, close with the boot's process.on cleanup or the group's trailing teardown, then verify once: `grep -c "assert\."`, one run, and one byte-identity diff per slice (`diff <(sed -n '<a>,<b>p' old) <(sed -n '<c>,<d>p' new)`); never grep-derived line variables in shell arithmetic (an empty match builds a broken sed) and never hand-counted offsets (#261). A referenced sibling group file may sit on an unmerged task branch: if its read fails with ENOENT, pull it with `git show <commit>:<path>` (hash from one `git log --all --oneline -- <path>`), never a second path guess (#261).
- Post-carve hunk migration (the spec names the carve base and the split homes): the diff base..HEAD is the whole work list; the verbatim lift recipe above extracts and verifies each hunk. Home every hunk once in the design pass, by the scenario block it extends, then splice with one script (keep its non-unique-anchor abort before the first write). Settle imports in the same pass as the splice write: grep the moved blocks' fs, zlib and payload calls against the target file's import lines; barrel-internal helpers import from ../../src/webui/<module>.ts, not the barrel. Verify once: byte-identity diff per block and assert-count parity (#256: 58 asserts moved, byte-verbatim, imports green first pass).
- log() (src/orchestrator/log.ts) echoes to stdout unless fd 1 is the log file itself (dev+ino check, #233). The daemon harnesses (runDaemon, sEnv/sFlag, the hub and worktree parts) assert log() lines from the daemon's piped stdout, so never drop the non-TTY echo without moving those harnesses to read the log file first.
- The .pids janitor (janitorPids in src/orchestrator/pipeline.ts) sweeps .exit files by name shape and, since #267, dead generic pid files, per file shape: `<slug>.pid` only when the slug is off the board (a board task's per-task pid stays; the poll consumes it in every state: exit code, armed reviewer marker, dead-streak clear), `<slug>.splitter.pid` only when its task left to-do (startTodo reads the dead file as the splitter-ran marker), `<slug>.<role>.<n>.analysis.pid` when dead; `merger.pid` is never swept. The keep set deliberately covers every board state: a stricter sweep races the liveness poll (poll.test.ts part B). Pinned by part AP in tests/orchestrator/sweep.test.ts (8 asserts: dead orphan pids swept, live, board and to-do pids kept). A new marker file in .pids must join its keep rules or the sweep deletes it within one sweep (#229). Dead-pid fixtures are hand-written orphan pid files: rmSync of a tracked file does not stick, reconcileBoard restores mirror files (#267). Paired guard: spawnRunAnalysis (src/orchestrator/spawn.ts) skips when the per-run `<slug>.<role>.<n>.analysis.exit` marker exists, or when the run already has its report or its doctor log, plain or gzipped (#250), so a failed analysis spawns once; the to-merge sweep fires the per-run analysis before the merge pass.
- To make a spawned analysis fail deterministically end to end, hand-write the finished run's log as a corrupt .log.gz (the compactor pattern skips .gz and the runner's gunzip throws); chmod 000 on the plain log races the sweep's retro-compact.
- Commit messages state only verified facts. Diff old vs new output before claiming byte-identity or behavior parity; an overclaim forces a soft-reset re-commit (#224).
- Analysis prompt builders live in src/efficiency-analysis.ts (splitAnswer, doctorPrompt). There is no src/orchestrator/prompts.ts (#228).

## Test-harness waits

- A wait loop over spawned processes must sleep between checks (about 50 ms): a synchronous busy spin blocks node's event loop, the SIGCHLD reaper never runs, and the exited sh wrapper lingers as a zombie whose /proc entry keeps pidAlive true forever (#234). Make the helper async and wait for the exit file AND a dead pid (both, not one: the wrapper writes the exit file about 35 ms after spawn but can still be alive across the test's next synchronous call).
- When such a wait misbehaves, suspect the reaper before the spawn. Confirm with one minimal isolated probe (spawn a stub, loop, watch /proc/<pid>/stat and cmdline), never by re-reading the spawn and pid code (#234 cycled three hypotheses, every one wrong).

## Temp fixture scripts

- A temp orchestrator part lives in tests/ from the first write, never /tmp: relative `../src` imports break from /tmp with ERR_MODULE_NOT_FOUND (#229). Temp scripts outside a package need the `.mjs` extension; when a fixture must keep a specific name (e.g. `orchestrator.ts` for cmdline matching), drop a `package.json` with `{"type": "module"}` next to it, else node loads the `.ts` as CJS.
- Write a temp fixture script complete on the first write: call shapes from the tests (setState takes a Task from getTask(root, file), not a file reference) and JSONL record shapes from the fixtures the tests build. A wrong call costs a TypeError, a signature grep, and a rerun (#226).
- Never patch temp scripts with sed. Use the edit tool: sed clashes on `|` and `/` delimiters and can leave broken syntax that kills node (#226).
- Verify a new fixture with find, not ls -R: ls -R does not list hidden dirs (#227).
- chmod 555 on a directory does not block writes to a file that already exists inside it: to make a create-or-write fail in a test, delete the file first, then lock the directory (#234).
- Worktree fixture doubts (index flags, history) settle with one command pair: `git -C <wt> ls-files -v` (S marks skip-worktree) plus `git -C <wt> log --oneline` (#234).
- A temp splice or migration script with no src imports can live in /tmp. It is plain JS: no TS-only syntax (`as const`, type annotations) in a .mjs file. Run `node --check` before the first execution, and grep every edit anchor for uniqueness (0 or 1 hits) while authoring, so the script's own non-unique-anchor abort never fires (#256: a TS syntax error and a 2-hit anchor cost two failed runs and two edit rounds).

## Stale-test triage

- A suite failure on prompt text: do not build a harness first. Read the assertion, then grep the prompt source (agents/*.md) for the asserted phrase. If the phrase is absent at HEAD, the test is stale: `git log -S'<phrase>' -- <file>` names the commit that dropped it; a one-line assertion fix ends it (#224: a stale agents/merger.md assertion cost 40% of a developer run).
- Flake vs regression: `git stash push`, run the failing suite at HEAD, `git stash pop`, before any hypothesis work. An orchestrator part with no plausible link to the diff is a timing flake until HEAD proves otherwise (#242). One rerun closes a confirmed flake. A test that fails in the full suite but passes standalone is a load-dependent timing race, not a regression: no further full runs, go straight to the race's root cause and gate it (#254: two acceptance runs failed on one mirror assert before the gate). When the acceptance criterion is the suite, fixing that race is in scope: the criterion answers the scope question, never re-litigate it (#254 asked three times). Fix real test-race flakes at the root cause: gate the fixture write against the racing machinery (an openQuestions-backed task is never promoted).

## Test recipes

## Environment and safety

- In a task worktree, `.kanban` is a symlink to the main checkout's board and SPECS.md is a symlink to `.kanban/<NNN>_<slug>.md`, your task's file: writing either edits the main checkout, and git in the worktree reports `.kanban/...` as "beyond a symbolic link" (never stage or commit those; the daemon commits board changes itself). Board files are untracked in the checked-out branch: the daemon mirrors them onto refs/heads/meta/kanban via git plumbing and pushes, so `git log -- .kanban/` prints nothing and board history is `git log meta/kanban --oneline -- <file>` (or `git log --all -- <file>`) (#252: three hypothesis cycles around the empty log). The main checkout root also carries a SPECS.md symlink that rotates to the current active task's file; greps or tails on SPECS.md fail from any cwd other than a root (there is none inside .kanban or .kanban/.logs), so run them from a root or through the resolved numbered path (#252).
- Read-only HOME mounts: ~/.pi, ~/.config and ~/.gnupg are read-only bind mounts on this machine. Any test or close() flush that touches the real user config dir crashes (or pollutes it on normal machines): keep global-state tests on fixture HOMEs and close in-process hubs before restoring the real HOME (#215). A worktree commit needs `git -c commit.gpgsign=false commit`, else "gpg failed to sign the data" (#215, #244). Stage first: a bare commit with unstaged edits fails with "no changes added to commit" (#248).
- `process.env.X = undefined` sets the env to the string "undefined" in node: use `delete process.env.X` when restoring an unset variable, else later code resolves paths like undefined/se-llm-team and litters the cwd (#215).
- Neutral shared paths (#215): the global config, hub registry and hub lock live at $XDG_CONFIG_HOME/se-llm-team/ (else ~/.config/se-llm-team/), with the legacy ~/.pi/agent paths as read-only fallbacks; every temp-HOME test env must also set or delete XDG_CONFIG_HOME, since the real environment may set it and leak the production config into tests.
- Large argv: the kernel rejects a single argument over 131,072 bytes with E2BIG (MAX_ARG_STRLEN); node spawn reports it as a child 'error' event and the child never starts (#213). The AGENTS.md injection cap (PROJECT_PROMPT_CAP, src/orchestrator/spawn.ts) is 131,000, covered by a real stub spawn in tests/orchestrator/spawn.test.ts (#214).
- Daemons under test never touch the production webui. Smoke daemons start with `--no-webui` (or SE_LLM_TEAM_NO_WEBUI=1), because a smoke daemon reads the global config and binds the production webui port, wedging the real UI. Live-check daemons get the fixture its own per-root port in the project config (see Live webui checks), never the global one.
