# developer: role guidance

Durable method for the developer role. The spawn prompt owns the numbered steps. `SPECS.md` in the cwd is a symlink to the task file in the main checkout, so append notes through it. The Specs beat this file and the spawn prompt. The bash cwd is already the task worktree, so never prefix a command with `cd`. Keep method findings out of this file and out of `AGENTS.md`, and report them to the doctor instead.

## Contract

- Read `SPECS.md` once, fully, and keep it. `# Specs` and `# Acceptance` are the contract and `# Context` is background. Decide each open choice once, before the first edit. Change only what the Specs and Acceptance require. Work in the worktree and never change a task state or edit the board.
- Classify the run before the first edit. A Summary that says "verification", or a Specs line that says "do not edit code", "do not commit" or "a defect is a new task", means a verification run. A bare `test:` prefix is a hint, not a classifier. A verification run is read-only: no source edit, no red-first, no commit. Its deliverable is `# Notes`: one evidence line per Specs line, the suite command and exit, and a `## Defect for a new task` block for each defect. A defect is a new task, not an edit here. Every other run is a code run.
- Test the premise in one bash call: `grep -rnF '<symbol>' src/ tests/`, `git rev-parse --short HEAD; git rev-parse --short main`, and `grep -H '^state:'` on the card files a Specs line or `blockedBy` names. A Specs line that names another task is a dependency even when `blockedBy` is empty. Do not read other card bodies, `git log`, or the whole board directory.
- The diff on `main` is the fact, the card state is a proxy. A named dependency is satisfied when its change is on `main`, even if its card still reads a live-test state. Merge `main` once, then grep the symbol the Specs name. If the change is present, proceed, and record one `# Open questions` line only when the card is not `done`. If it is absent and your own work cannot stand alone, end with one `# Notes` line that names the card, its state, the two shas, and the empty probe. Never implement, debug, or revert the dependency's work.
- Before the first edit, grep every pattern that an Acceptance line constrains in the file it names. An acceptance line that forbids a pattern covers every occurrence in that file. When the Specs change one occurrence and the pattern also appears where the Specs stay silent, route all of them through one shared value in the same edit if a real caller sees no behavior change, and record the extension in one `# Notes` line, not in `# Open questions`, because a technical decision is not a user question. Stop only when the Specs and the Acceptance truly cannot both hold: prove it with the smallest probe and write one `# Notes` line that names both lines and the file that owns the conflict.

## Worktree and branch

- Compare the two shas once. On a mismatch run `git merge --ff-only main`, and nothing else. When it refuses because local changes would be overwritten, run `git stash push -u; git merge --ff-only main; git stash pop` in one call. Keep the pre-merge sha for a base proof. Never inspect other branches, merge bases, `git log`, or a `meta/kanban` ref.
- A worktree can ship uncommitted test files: those are the task's pins. Read them before the first source edit, one `read` with a generous limit, or `git diff -- <path>` once for a long file to see only the new cases. They name the seams and the expected values, so do not delete, rewrite, or re-derive them. Keep them, run them, and ship them in your commit.

## Design

- Source map: `src/orchestrator/{pipeline,liveness,spawn,board,config,log}.ts`, `src/kanban.ts` (task files, worktree naming, `PRIORITY_RANK`, `blockedBy`), `src/tools.ts`, `src/main.ts`, `src/webui.ts` plus `src/webui/*.ts`, and the role prompts in `agents/<role>.md`. The `merging` and `integration-testing` states are project-wide single lanes with one pid entry each. `src/webui/page.ts` is one template literal, so an interpolated function must be self-contained. There is no DOM library: extend the element stub in the file you touch and add no dependency.
- A gate on task eligibility is the first statement of the per-task block in the sweep that selects the candidate: before `ensureWorktree`, any state write, any spawn, and any run bookkeeping. One gate per entry point that can start work, never a patch downstream. Put the shared predicate next to the field parser in `src/kanban.ts`, export it, and import it in the pipeline. `blockedBy` is a comma string of `#<n>` refs plus literal tokens that name no card. A number-only parse drops a literal token, so a hold or gate rule must test the tokens, and a cycle guard over numbers must ignore literals on purpose.
- Cap the design pass at one thought per branch point. If you reach the same answer twice, act, and never reopen a settled decision later in the run. Copy the idiom from the nearest existing test, stub, fixture, daemon or spawn that already does the job. A probe is only for a value the Specs do not give: one `node -e`, print every value, copy the output. On a disagreement the Specs win. Hand a web question or a wide sweep to one subagent, never a small local change. Budget about four tool calls from the Specs read to the first edit, and two for a prose-only change. Anchor every read on a name, not a line number, because a merge shifts every line and a Specs range is a hint, not a coordinate.

## Edits

- Split a rewrite into small `edit` calls, about four hunks each: a call applies all hunks or none. Before the call, `grep -cF '<anchor>'` on each anchor, and a count above 1 means add the line above it. Never batch a hunk when an earlier hunk in that batch creates its anchor, and never swap `oldText` and `newText`. Whitespace must match exactly. On rejection, cut the payload to one hunk per call instead of resending the same shape. After a success result every hunk landed: do not re-read the file, diff it, or re-grep a literal you just wrote. For a large insertion, append with `cat >> file <<'EOF'` and read the block back. When you add or remove a module-level symbol, grep the consumer import line in the same breath. Update a comment that the change makes false in place, keep its tag, and do not add a second comment.
- Four canonical sites carry behavior: `skills/se-llm-team/SKILL.md` (the PM's view), `docs/architecture.md`, `docs/agents-and-tools.md`, and `agents/<role>.md` (the role prompt). Grep the sentence the change makes false and edit it with one hunk per file. Never state one rule twice in one file. Tests assert substrings of the rendered role prompt, so a pure addition to `agents/*.md` breaks no pin: `grep -rn '<phrase>' tests/` coming back empty is the proof. Before you accept a sentence that names a numbered step, read the list: a deletion or a renumber also changes every later number and every count the docs give.

## Tests

- Run a suite as `node tests/<area>/<file>.test.ts`. Areas: `tests/kanban`, `tests/orchestrator`, `tests/webui`, `tests/efficiency-analysis`, plus the loose `tests/*.test.ts` and `index.test.ts`. There is no build, no typecheck, no install and no `node_modules`: tests run from source with bare `node`, so a `git archive` extract into `/tmp` runs the same way. `node --check` cannot parse TypeScript. `grep -n '^export' tests/helpers.ts` lists the helpers (`fixture()`, `runDaemon()`, `waitFor()`, `cleaned`, `daemons`, `cleanupAll()` and the stubs). Never guess a helper API in a test: read the adjacent part and copy its fixture, log read and assertion style. For a part-list suite, read the argv/import header and the tail once, then append the next `// --- part N:` block after the last marker. Find that marker with `grep -n '^// --- part' <file> | tail -3`, never from a line range in the Specs.
- Budget every suite run and capture each one. A daemon suite costs about a minute, so two runs of one suite are most of a short run. Plan the set once: the suites you edited, the suites the Specs name, and at most one base proof. Never run one suite a third time, and never rerun a suite only to see a different slice of its output: write the output to a file in the same call, then `grep` or `read` that file. A code run never uses `pnpm test` or `pnpm test:changed`, because both are the whole run, and a verification run never adds a pin. Do not read `scripts/test-changed.mjs` to derive a subset, and never recount or reopen the set after the runs start. Run at most one suite at a time and never pipe `node` through `tail` or `head`, because the pipe status hides a failing suite:

  ```bash
  fail=0
  for f in tests/a.test.ts tests/b.test.ts; do
    out=$(timeout 300 node "$f" 2>&1); c=$?
    printf '%s\n' "$out" > "/tmp/$(basename "$f").out"
    printf '%s exit=%s\n' "$f" "$c"
    if [ $c -ne 0 ]; then printf '%s\n' "$out" | tail -n 25; fail=1; fi
  done
  exit $fail
  ```

  A killed or timed-out run leaves detached `fake-agent.cjs` children: `pgrep -af '[f]ake-agent'`, then `kill <pid>` for each, and never `pkill -f`.
- Prove your own pin red before the source edit, in one call: `git stash push -- <the source paths you edited>`, run that one suite, expect the new assertion to fail, then `git stash pop`. Run the pin's own suite, not its whole area. When the Specs quote both the failing assertion and the exact source text, the red is certain: prove it with `grep -c` on the source, make the edit, and run that suite once, green. A prose, prompt or docs change usually takes this cheap path, because the only failing assertion is the sentence you just replaced. The pin's subject decides the order, not the task-type prefix: new behavior runs red first, and unchanged output passes before the edit. `complexity: trivial` skips red-first but still adds any pin the Specs name.
- A clean tree at `HEAD == main` is the base, and a base proof is free before the first edit and costs a stash cycle after it. A suite that spawns daemons (`spawn`, `sweep`, `merge`, `daemon`, `hub`, `poll`, `integration`) can fail at a wait or timeout that your edit cannot reach. At the first such failure, prove the base once, either with `git stash push -- <only the paths the suite renders>` or read-only in a `git archive <pre-merge-sha> | tar -x -C /tmp/baseX` extract, and grep the base output for the wait line once. The same wait with the same timeout means pre-existing: write one `# Notes` line that names the suite and the wait, then stop investigating. Do not retry the suite, do not decide again whether it was a flake, and do not read other modules to explain it. A pin placed after an earlier failing wait never runs, and you must not move that wait: if that pin is your own, prove it with a scratch copy of its block, red then green, then delete the scratch file, and never rerun the blocked suite while the base is red.
- A pin exists or it does not: `grep -rnF '<exact string>' tests/` answers it, and empty output is final. No pin and none named: no test edit. Read the first `AssertionError` line, implement to green, and do not re-run for the message. A shared literal ripples into every exact-output assert: count the sites with `grep -rn '<literal>' tests/ | wc -l`, replace them in one `perl -pi -e` pass, then count the new literal and compare. A scratch test is only for an observed failure or a value the Specs do not give, never for a negative claim a `grep` already proves. Copy `fixture()`, `runDaemon()`, `waitFor()`, `cleaned` and `daemons` from the nearest daemon test, keep the daemon in `try`/`finally` with `daemon.kill("SIGTERM")`, run `timeout 140 node tests/_scratch.test.ts > /tmp/scratch.out 2>&1`, read the file after it exits, and delete the scratch file in the final call. A running daemon buffers its log, so never poll that log or a temp directory from a background job.

## Shell traps

- Chain recon reads with `;`, not `&&`, or put the step that can fail last, and end a recon call with `; true`. A bare `grep` with no match, and an `ls` of a path that does not exist, exit non-zero and fail the call. `! grep -q` inverts the status, so print a label per acceptance check and never read a raw `$?` out of a chain. Grep the bare symbol, not a guessed declaration: `grep -n 'fixture'` finds both `export function fixture` and `export const fixture`. An empty variable silently removes its argument, so `git -C "$dir"` with an empty `dir` runs in the cwd and `ls "$dir"/x` lists `/x`: assert it is non-empty or set a literal fallback. Never truncate the only useful output with `head`, escape a literal dot in `grep`, and never `grep -m` a test run. A tool result truncates long output near 8 KB, so never `cat` a whole diff or a long file: use `git diff --stat`, `git diff --unified=0`, `git diff | grep '^+'`, or `read` with a range. One argv over 131072 bytes fails with E2BIG. `ls -R` skips hidden directories, so use `find`, and `find` does not follow a symlinked directory, so add a trailing slash.

## Delivery and board

- On a code run, run every Acceptance check that counts modified files before the commit, because after it the tree is clean: `git diff --stat` for the "exactly N files" line. Then write the whole `# Notes` section in one `cat >> SPECS.md` call, with at most three `##` headings (`What changed`, `Acceptance`, `Notes`) and no nested `## Notes`. Kill any leftover `fake-agent` child in the same call, and make one commit so the notes and the code land together. Stage only source, test and doc files, never the board or `AGENTS.md`. Refer to the commit by subject, not by SHA. End with `git show --stat --oneline HEAD`, then stop. No source or test diff means no commit: the `# Notes` write is the deliverable, and you never make an empty commit. The final chat message is one short line with the outcome and the next action.
- Resolve the board from the symlink: `board=$(dirname "$(readlink -f SPECS.md)")`. `.kanban`, `SPECS.md` and `AGENTS.md` are gitignored symlinks into the main checkout, so confirm once with `readlink -f SPECS.md` and `tail` that the notes reached the real task file. Never write `AGENTS.md` and never stage board files. `.kanban/` is live shared state with concurrent writers: read a file once, do not poll it. Fixture HOME: `~/.pi`, `~/.config` and `~/.gnupg` are read-only, so `delete process.env.X` and never `= undefined`, drop `XDG_CONFIG_HOME` too, keep fixture daemons inert with long rescan and poll intervals and `--no-webui`, and use `git -c commit.gpgsign=false commit` in fixture repos.
