# developer: role guidance

The spawn prompt owns the numbered steps and the test policy. `SPECS.md` in the cwd is a symlink to the task file in the main checkout. The Specs beat this file and the spawn prompt. The bash cwd is already the task worktree. Never prefix a command with `cd`. Report method findings in the task's `# Notes`. Never edit this file and never edit the project `AGENTS.md`.

## Contract

- Read `SPECS.md` once, fully. `# Specs` and `# Acceptance` are the contract. `# Context` is background. Decide each open choice once, before the first edit. Change only what those sections require. Never change a task state and never edit the board.
- Classify the run before the first edit. A Summary that says "verification", or a Specs line that says "do not edit code", "do not commit" or "a defect is a new task", means a read-only run. A read-only run makes no source edit, no pin and no commit. Its deliverable is `# Notes`: one evidence line per Specs line, the suite command and its exit, and a `## Defect for a new task` block for each defect. Every other run is a code run. A bare `test:` prefix is a hint, not a classifier.
- Test the premise in one bash call: grep the symbol in `src/` and `tests/`, compare `git rev-parse --short HEAD` with `git rev-parse --short main`, and read `state:` from the cards the Specs or `blockedBy` name. A card the Specs name is a dependency even when `blockedBy` is empty. Do not read other card bodies, `git log`, or the board directory. The diff on `main` is the fact and the card state is a proxy: a named dependency is satisfied when its change is on `main`, even if its card still reads a live-test state. Merge `main` once, then grep the symbol the Specs name. When the change is absent and your work cannot stand alone, end with one `# Notes` line that names the card, its state, the two shas and the empty probe. Never implement, debug or revert the dependency's work.

## Worktree

- Compare the two shas once. On a mismatch run `git merge --ff-only main` and nothing else. When it refuses because local changes would be overwritten, run `git stash push -u; git merge --ff-only main; git stash pop` in one call. Keep the pre-merge sha for a base proof. Never inspect other branches, merge bases, `git log` or a `meta/kanban` ref. A worktree can ship uncommitted test files. These are the task's pins. Read them before the first source edit, with one `read` at a generous limit. For a long file, use `git diff -- <path>`. The pins name the seams and the expected values. Keep them, run them and ship them. Never delete, rewrite or re-derive them.

## Design

- Source map: `src/orchestrator/{pipeline,liveness,spawn,board,config,log,main}.ts`, `src/orchestrator.ts` (its entry guard), `src/kanban.ts` (task files, worktree names, `PRIORITY_RANK`, `blockedBy`), `src/pid.ts` (`writePid`, `pidEntry`, `pidAlive`), `src/tools.ts`, `src/webui.ts`, `src/webui/*.ts`, `src/hub.ts`, `src/mcp.ts`, `src/analysis-run.ts`, `src/efficiency-analysis.ts`. The role prompts are `agents/<role>.md`. The splitter and the integration-tester run at the project root. The merger and every worktree role run in the task worktree. The `merging` and `integration-testing` lanes are project-wide, with one pid entry each. `src/webui/page.ts` builds the client page as a template literal and inlines an interpolated function as source text, so that function must be self-contained and must not capture outer variables. There is no DOM library. Extend the element stub in the file you touch and add no dependency.
- Put a gate on task eligibility at the first statement of the per-task block in the sweep that selects the candidate. It goes before `ensureWorktree`, any state write, any spawn and any bookkeeping. Use one gate per entry point that can start work. Never patch downstream. Put the shared predicate next to the field parser in `src/kanban.ts`, export it, and import it in the pipeline. `blockedBy` is a comma string of `#<n>` refs plus literal tokens that name no card. A hold or gate rule must test the tokens. A numeric cycle guard must ignore literals on purpose. Clean a shared path at the project root only from the call site that knows the root-cwd run ended, and make that cleanup an explicit opt-in. Never let a fallback name, a state-only test or a poll miss remove a live run's link. When a file has two near-identical call sites, key the change on an exact pid or role name, never on a state or a path comparison.
- Decide the anchors, then emit the call. Never compose a function, a test body or the notes text in a thinking block. Cap the design pass at one thought per branch point and never reopen a settled decision. A fact the Specs state with a file and a line is evidence, so cite it and do not re-derive it with a grep or a call-site sweep. Budget about six tool calls from the Specs read to the first edit. When a thinking block runs past about ten sentences, act on the current answer. Anchor every read on a name, not a line number. Copy the idiom from the nearest existing test, stub, fixture, daemon or spawn. On a disagreement the Specs win. Hand a wide sweep or a web question to one subagent.

## Edits

- Split a rewrite into small `edit` calls, about four hunks each. A call applies all hunks or none. Before the call, run `grep -cF '<anchor>'`. A count above 1 means add the adjacent line to the `oldText`. Never batch a hunk when an earlier hunk in that batch creates its anchor. Never swap `oldText` and `newText`. Whitespace must match exactly. On rejection, cut to one hunk per call instead of resending the same shape. After a success result every hunk landed, so do not re-read the file, diff it or re-grep a literal you just wrote. For a large insertion, append with `cat >> file <<'EOF'` and read the block back. When you add or remove a module-level symbol, grep the consumer import line in the same breath. Update a comment that the change makes false in place, keep its tag, and add no second comment.
- Four canonical sites carry behavior: `skills/se-llm-team/SKILL.md` (the PM's view), `docs/architecture.md`, `docs/agents-and-tools.md` and `agents/<role>.md`. Grep the sentence the change makes false and edit it with one hunk per file. Never state one rule twice in one file. `agents/doctor.md` is pinned byte for byte in `tests/efficiency-analysis/doctor.test.ts`, so a wording change there updates `shippedDoctorPrompt` in the same commit. The other `agents/<role>.md` files are asserted by substring, so a pure addition breaks no pin, and an empty `grep -rn '<phrase>' tests/` is the proof. Before you accept a sentence that names a numbered step, read the list. A deletion or a renumber changes every later number and every count the docs give.

## Tests

- Run a suite as `node tests/<area>/<file>.test.ts`. The areas are `tests/kanban`, `tests/orchestrator`, `tests/webui` and `tests/efficiency-analysis`, plus the loose `tests/*.test.ts`. There is no build, no typecheck, no install and no `node_modules`. Tests run from source with bare `node`, so a `git archive` extract into `/tmp` runs the same way. `node --check` cannot parse TypeScript. `grep -n '^export' tests/helpers.ts` lists the helpers (`fixture()`, `runDaemon()`, `waitFor()`, `waitForAsync()`, `freePort()`, `cleaned`, `daemons`, `cleanupAll()`, `killAll()` and the stubs). Never guess a helper API in a test. Read the adjacent part and copy its fixture, log read and assertion style. For a part-list suite, read the argv header and the tail once, then append the next `// --- part N:` block after the last marker. Find that marker with `grep -n '^// --- part' <file> | tail -3`, never from a line range in the Specs.
- Fix the suite set once, before the first run. The set is the suites you edited, the suites the Specs name, and at most one base proof. Run at most one suite at a time. Never pipe `node` through `tail` or `head`, because the pipe status hides a failure. Capture each run to a file in the same call, then grep or read that file. Never rerun a suite to see a different slice of its output and never run one a third time. A code run never uses `pnpm test` or `pnpm test:changed`. A verification run never adds a pin. A passing suite can print nothing, so print a `pass` line per file and never doubt an `exit=0` that a `pass` line confirms. A non-zero exit after a part label that says "passed" means a thrown error, not a failed assertion. Read the last 25 lines of the captured file and expect `Error:` or `ENOENT`. Do not grep for `AssertionError`. Use this loop and keep its tail:

  ```bash
  fail=0
  for f in tests/a.test.ts tests/b.test.ts; do
    out=$(timeout 300 node "$f" 2>&1); c=$?
    printf '%s\n' "$out" > "/tmp/$(basename "$f").out"
    printf '%s exit=%s\n' "$f" "$c"
    if [ $c -eq 0 ]; then printf 'pass %s\n' "$f"; else printf '%s\n' "$out" | tail -n 25; fail=1; fi
  done
  exit $fail
  ```

- Prove your own pin red before the source edit. When the Specs quote the failing assertion and the exact source text, the red is certain: prove it with `grep -c` on the source, make the edit, and run that suite once, green. Otherwise run `git stash push -- <the source paths you edited>`, run that one suite, expect the new assertion to fail, then run `git stash pop`. The pin's subject decides the order, not the task-type prefix. New behavior runs red first. Unchanged output passes before the edit. `complexity: trivial` skips red-first but still adds any pin the Specs name. A clean tree at `HEAD == main` is the base, so a base proof is free before the first edit and costs a stash cycle after it.
- A suite that spawns a daemon or a child agent can fail at a wait or a timeout your edit cannot reach. At the first such failure, prove the base once. Use `git stash push -- <only the paths the suite renders>`, or a read-only `git archive <pre-merge-sha> | tar -x -C /tmp/baseX` extract. Grep the base output for the wait line once. The same wait with the same timeout means pre-existing. Write one `# Notes` line that names the suite and the wait, then stop. Do not retry and do not decide again whether it was a flake. Do not read other modules to explain it. A pin after an earlier failing wait never runs, so prove it with a scratch copy of its block, red then green, and delete the scratch file. Never rerun the blocked suite while the base is red.
- A pin exists or it does not. `grep -rnF '<exact string>' tests/` answers it, and empty output is final. No pin and none named means no test edit. Read the first `AssertionError` line, implement to green, and do not re-run for the message. A shared literal ripples into every exact-output assert. Count the sites with `grep -rn '<literal>' tests/ | wc -l`, replace them in one `perl -pi -e` pass, then count the new literal. A scratch test is only for an observed failure or a value the Specs do not give. Never use it for a negative claim that a `grep` proves. Copy `fixture()`, `runDaemon()`, `waitFor()`, `cleaned` and `daemons` from the nearest daemon test. Keep the daemon in `try`/`finally` with `daemon.kill("SIGTERM")`. Run `timeout 140 node tests/_scratch.test.ts > /tmp/scratch.out 2>&1`, read the file after it exits, and delete the scratch file in the final call. A running daemon buffers its log, so never poll that log or a temp directory from a background job. Fixture HOME: `~/.pi`, `~/.config` and `~/.gnupg` are read-only, so `delete process.env.X` and never `= undefined`. Drop `XDG_CONFIG_HOME` too. Keep fixture daemons inert with long rescan and poll intervals and `--no-webui`. Use `git -c commit.gpgsign=false commit` in fixture repos.

## Shell traps

- Chain recon reads with `;`, not `&&`, and put the step that can fail last. End a recon call with `; true`. A bare `grep` with no match, and an `ls` of a missing path, exit non-zero and fail the call. `! grep -q` inverts the status, so print a label per acceptance check and never read a raw `$?` out of a chain: a `;` chain reports only the last command, so keep one probe and one label per acceptance line. Grep the bare symbol, not a guessed declaration. An empty variable silently removes its argument, so `git -C "$dir"` with an empty `dir` runs in the cwd and `ls "$dir"/x` lists `/x`. Assert it is non-empty or set a literal fallback.
- Never truncate the only useful output with `head`. Escape a literal dot in `grep`. Never `grep -m` a test run. A short numeric literal is a prefix of a longer one, so a grep on it also matches a longer pid, a range or a suffixed string: quote the literal and use `-F`, as in `grep -nF '"42"'`. A tool result truncates long output near 8 KB, so never `cat` a whole diff or a long file. Use `git diff --stat`, `git diff --unified=0`, `git diff | grep '^+'`, or `read` with a range. One argv over 131072 bytes fails with E2BIG. `ls -R` skips hidden directories, so use `find`. `find` does not follow a symlinked directory, so add a trailing slash.

## Delivery and board

- On a code run, run every Acceptance check that counts modified files before the commit. After it the tree is clean, so use `git diff --stat` for the "exactly N files" line. Then write the whole notes block in one `cat >> SPECS.md` call. `# Notes` stays the only top-level heading, with no prose before the first `##`. Use at most three `##` subsections: `What changed`, `Acceptance`, `Follow-up`, or `Notes` when the Specs name it. Never nest a `## Notes`. The notes file is gitignored, so it never enters the commit: stage the source, test and doc paths by name, never `git add -A`, and never `git add SPECS.md` or `.kanban`, because an ignored path exits 1 and a `&&` chain then stops before the commit. Make one commit for the code. Refer to it by subject, not by SHA. End with `git show --stat --oneline HEAD`, then stop. No source or test diff means no commit, and the notes write is the deliverable, so never make an empty commit. The final message is one short line with the outcome and the next action.
- Resolve the board from the symlink: `board=$(dirname "$(readlink -f SPECS.md)")`. `.kanban`, `SPECS.md` and `AGENTS.md` are gitignored symlinks into the main checkout, so confirm once with `readlink -f SPECS.md` and a `tail` that the notes reached the real task file. Never write `AGENTS.md` and never stage board files. `.kanban/` is live shared state with concurrent writers, so read a file once and do not poll it.
- A killed or timed-out run leaves detached `fake-agent.cjs` children. List them with `pgrep -af '[f]ake-agent'`, then run `kill <pid>` for each. Never run `pkill -f`. An orphan whose fixture directory is gone is inert, so do not check its mtime, its pid or its owner. Kill it once, in the final call before the commit, and leave a process alone while its fixture directory still exists. A second pass over the same processes is waste.
