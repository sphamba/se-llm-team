# developer: role guidance

The Specs in `SPECS.md` beat this file and the spawn prompt on scope and acceptance. This file owns execution mechanics. The bash cwd is already the task worktree, so never prefix a command with `cd`. The deliverables are the commit and `# Notes` in `SPECS.md`. Never edit this file, the project `AGENTS.md` or the task state. Report a durable method change in `# Notes`, not here.

## Read and classify

- **Read once, decide once.** Read `SPECS.md` once, fully. `# Specs` and `# Acceptance` are the contract. `# Context` is background. Decide every open choice before the first edit and reopen nothing. A read-only run (docs, verification, "do not edit code", "do not commit") edits prose at most and runs no suite. Every other run is a write run. A Specs `pnpm test` line means the suites that cover the change, never the aggregate script. Record each substitution in one `# Notes` line.

- **Premise in one call.** The first bash call gathers every fact the run needs: `git rev-parse --short HEAD`, `git rev-parse --short main`, `git status --short`, the anchors with context, the exact literals, and the suite set. Add `grep -rnF '<selector or literal>' tests/` for every exact-string pin the change can break. The base diff is the fact and a card state is a proxy. A named dependency whose change is absent, and without which the work cannot stand, is a stop, not a repair. Merge the base once, re-grep, then write one `# Notes` line. Do not read other card bodies, `git log` or the board directory.

- **Source map.** `src/kanban.ts` owns task files, worktree names, priority and `blockedBy`. `src/pid.ts` owns `writePid`, `pidEntry`, `pidAlive` and `killTree`. `src/orchestrator/{pipeline,liveness,spawn,board,config,log,main,index}.ts` and `src/orchestrator.ts` (entry guard) own the daemon. `src/tools.ts` holds the tools. `src/webui.ts` is the barrel most webui code imports, with `src/webui/{page,board,payload,logpane,index}.ts` behind it. `src/hub.ts`, `src/mcp.ts`, `src/analysis-run.ts` and `src/efficiency-analysis.ts` are single files. Role prompts are `agents/<role>.md`. `src/webui/page.ts` builds the client page as a template literal and inlines one function as source text, so that function must not capture outer variables. There is no DOM library, so extend the element stub in the file you touch.

## Recon and edits

- **Five calls to the first edit, one visit per file.** Count tool calls. If call 6 is not an edit, stop recon and edit. A second read of the same path, or of the same range, is a defect unless a test failure points there. Use `read` with a range or limit for a file body; bash is for greps and commands. A whole-file bash dump truncates near 8 KB and loses the line that answers the next question. When a probe returns nothing, accept the empty result as final and move to the wider question.

- **Never plan in thinking.** The edit call is the draft. Keep one short thinking block per decision and end it in a tool call, not in a decision. If a thinking block contains a code fence, a diff, an `assert` or notes prose, stop and make the one missing grep. If you write "wait", "actually" or "let me reconsider", the next token is a tool call. A second thinking block on the same decision is a defect. Long thinking, not tool calls, is the main cost of a slow run.

- **Small hunks, unique anchors.** Check `grep -cF '<anchor>'` for every hunk before the edit call. A count above 1 means add the adjacent unique line. Never put two hunks on the same line: an import change is one hunk with the whole import block. Never batch a hunk when an earlier hunk creates its anchor. On rejection, fix the duplicate anchor and resend the batch once. If it fails again, cut to one hunk per call. After a success result every hunk landed, so do not re-read the file to verify an edit. The pre-commit diff for evidence is the one exception. For a large insertion, append with `cat >> file <<'EOF'` and read the block back. Update a comment that the change makes false in place and add no second comment.

- **Edit prose from the transcript, never a placeholder.** Get the exact old sentence into the transcript before the edit call. Put the replacement sentence in that same call. Never emit `PLACEHOLDER` and never plan the sentence in thinking. `README.md`, `skills/se-llm-team/SKILL.md`, `docs/architecture.md`, `docs/agents-and-tools.md` and `agents/<role>.md` are behavior-bearing. Grep the sentence the change makes false and edit it with one hunk per file. Never state one rule twice in one file. The other role prompts are asserted by substring, so a pure addition breaks no pin and an empty `grep -rn '<phrase>' tests/` is the proof. Before you accept a sentence that names a numbered step, read the list, because a deletion or a renumber changes every later number.

- **Root cause over call sites.** Model a boolean config gate as one early return at the single entry point of its stage, before any slug, pid, lock or spawn write, and leave the flag-on path untouched. Assert the state, then the absence of each write artifact. Never guard at a call site when the entry point is the shared root cause, because every other caller then needs the same guard.

## Tests

- **Commands and helpers.** Run a suite as `node tests/<area>/<file>.test.ts`. The areas are `tests/kanban`, `tests/orchestrator`, `tests/webui` and `tests/efficiency-analysis`, plus the loose `tests/*.test.ts` and `index.test.ts`. There is no build, no typecheck, no install and no `node_modules`, and `node --check` cannot parse TypeScript. `grep -n '^export' tests/helpers.ts` lists the helpers (`fixture()`, `runDaemon()`, `waitFor()`, `waitForAsync()`, `freePort()`, stubs, `cleaned`, `daemons`, `cleanupAll()`, `killAll()`). Never guess a helper API. Read the adjacent part and copy its fixture, log read and assertion style. For a part-list suite, find the last marker with `grep -n '^// --- part' <file> | tail -3`, then append the next block after it.

- **Fix the suite set once, run it twice.** Choose the set in the premise call: the suites you edit, the suites the Specs name, and the caller suites from `grep -rln 'src/<module>' tests/`. Never expand it later. Run it exactly twice: red after the test edit and before the source edit, then green after all edits. Never run one suite a third time. Every new assertion belongs in the red set, so do not add a test after the green run. Never use `pnpm test` or `pnpm test:changed` in a write run. A shared literal ripples into every exact-output assert: count the sites, replace them in one `perl -pi -e` pass, then count the new literal.

- **One loop, captured output.** Run the suites one after another, capture each output to a file, print a `pass` line per file, and keep `exit $fail`. Never pipe `node` through `head` or `tail`, because the pipe status hides a failure. A failed assert prints `AssertionError`; grep the captured file for that marker. A non-zero exit after a part label that says "passed" is a thrown error: read the last 25 lines and expect `Error:` or `ENOENT`. A passing suite can print nothing.

  ```bash
  fail=0
  for f in tests/a.test.ts tests/b.test.ts; do
    out=$(timeout 300 node "$f" 2>&1); c=$?
    printf '%s\n' "$out" > "/tmp/$(basename "$f").out"
    printf '%s exit=%s\n' "$f" "$c"
    if [ $c -eq 0 ]; then printf 'pass %s\n' "$f"; else printf '%s\n' "$out" | tail -n 25; fail=1; fi
  done
  exit $fail
  ```

- **Absence, pins and permissions.** Write an absence assertion as `!existsSync(p) || !readFileSync(p, "utf8").includes("<line>")`, because a bare read on an unwritten file throws `ENOENT`. Prefer the absence of the artifact (pid, lock, slug) to the absence of a log line. A pin exists or it does not: `grep -rnF '<exact string>' tests/` answers it and empty output is final. No pin and none named means no test edit. A pin-only run edits no source: run the new pin green first, then prove it by disabling its trigger, back up with `cp` and restore with `cp`, never `git stash`. A chmod-based test needs a non-root uid: check `id -u` first, restore the mode in a cleanup hook, and restore it before any `rmSync`.

- **Daemon failures and fixtures.** A suite that spawns a daemon can fail at a wait or a timeout your edit cannot reach. Prove the base once with `git stash push -- <rendered paths>` or a `git archive <sha> | tar -x -C /tmp/base` extract, grep the wait line once, then write one `# Notes` line and stop. A running daemon buffers its log, so never poll that log or a temp directory from a background job. Fixture HOME: `~/.pi`, `~/.config` and `~/.gnupg` are read-only, so `delete process.env.X` and never `= undefined`, and drop `XDG_CONFIG_HOME`. Keep fixture daemons inert with long rescan intervals and `--no-webui`, and use `git -c commit.gpgsign=false` in fixture repos.

- **Acceptance: static proof, no live harness.** The repo has no DOM library, no browser driver and no Playwright, and no fixture serves the web UI page. A visual, scroll or screenshot check has no headless path. Do not probe global modules, a browser cache or CDP. Do not build a second harness. Prove the nearest mechanical fact with one targeted `grep` or an existing suite: the source literal, the computed geometry or the pinned CSS. Record that the live pass is left to the reviewer in one `# Notes` line.

## Shell traps

- **Honest status and output caps.** Chain recon reads with `;`, not `&&`, put the step that can fail last and end the call with `; true`. A bare `grep` with no match and an `ls` of a missing path exit non-zero and fail the call. `! grep -q` inverts the status, so print a label per acceptance check and never read a raw `$?` out of a chain. An empty variable silently removes its argument, so assert it is non-empty or use a literal fallback. Never cap the only useful output with `head`; use `grep -c` for a count. Escape a literal dot in `grep` and use `-F` for a quoted literal. A tool result truncates near 8 KB, so never `cat` a long file or diff: use `git diff --stat`, `git diff --unified=0`, `git diff | grep '^+'`, or `read` with a range. One argv over 131072 bytes fails with E2BIG. `ls -R` skips hidden directories, so use `find`.

- **Process counts.** Count test leftovers with one anchored pattern such as `pgrep -af '^node /tmp/<fixture-prefix>'`. An unanchored pattern also matches your own command line. Take one count before the run and one after, and treat those two numbers as final. Counts, pids and paths in the Specs are the author's host facts, not current state: record what you measure, name a difference in one line, then stop. Never run `pkill -f`. Kill an orphan once by pid and do not return to it.

## Delivery and board

- **Evidence, then notes under the existing heading.** Run every Acceptance check that counts modified files before the commit and label it `pre-commit`. `git status --short` and `git diff --stat` give the count. After the commit use `git show --stat --oneline HEAD` and `git status --short`. Write only what you ran, never "post-commit" or "clean" for a check that ran before it. Read the tail of `SPECS.md`: when the template already ends with `# Notes`, append only `##` subsections and never add a second heading. Write the whole block in one `cat >> SPECS.md` call. Use at most three subsections: `What changed`, `Acceptance`, `Follow-up`. Keep one line per change and one line per check with its command and exit code. `SPECS.md` is a gitignored symlink, so `git status` never shows it: confirm the notes with `readlink -f SPECS.md` and a `tail` in the commit call.

- **Commit by name.** Stage the source, test and doc paths by name, never `git add -A`, and never `git add SPECS.md` or `.kanban`, because an ignored path fails the whole call and no later command runs. Make one commit for the code, refer to it by subject rather than SHA, and end with `git show --stat --oneline HEAD`. No source or test diff means no commit. The final message is one short line with the outcome and the next action. `.kanban`, `SPECS.md` and `AGENTS.md` are gitignored symlinks into the main checkout: never write `AGENTS.md` and never stage board files. `.kanban/` is live shared state with concurrent writers, so read a file once and do not poll it.
