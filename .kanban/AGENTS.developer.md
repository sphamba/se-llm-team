# developer: role guidance

The spawn prompt owns the numbered steps, the test policy and the stall timeout. `SPECS.md` in the cwd is a gitignored symlink to the task file in the main checkout. The Specs beat this file and the spawn prompt on scope and acceptance. This file owns the execution mechanics: the recon budget, the suite command, commit hygiene and evidence labels. The bash cwd is already the task worktree, so never prefix a command with `cd`. The deliverables are the commit and `# Notes` in `SPECS.md`. Never edit this file, the project `AGENTS.md` or the task state. Report a durable method change in `# Notes`, not here.

## Read and classify

- **Read once, decide once.** Read `SPECS.md` once, fully. `# Specs` and `# Acceptance` are the contract. `# Context` is background. Decide each open choice before the first edit and never reopen it. A Summary that says "verification", or a Specs line that says "do not edit code", "do not commit" or "a defect is a new task", means a read-only run. A docs-only run edits prose, commits the doc and runs no suite. Every other run is a write run. When the Specs name a command or a doc that conflicts with this file, keep the Specs' deliverable and this file's mechanics: a Specs `pnpm test` line means the suites that cover the change, never the aggregate script. Record each substitution in one `# Notes` line.

- **Premise in one call.** The first bash call gathers every fact the run needs. Use one call, chain reads with `;`, and end with `; true`:

  ```bash
  git rev-parse --short HEAD; git rev-parse --short main; git status --short
  grep -n -C 8 '<anchor1>\|<anchor2>' src/<file>.ts
  grep -rnF '<changed selector or exact literal>' tests/
  grep -rln 'from ".*<module>"' tests/
  grep -n '^// --- part\|^function \|^const [a-z].* = (' tests/<area>/<file>.test.ts
  ```

  Add the exact doc sentence and the exact CSS rule the change touches. A CSS or page change usually breaks an exact-string pin: `grep -rnF '#selector' tests/` in this call, not after the first edit. The base diff is the fact and a card state is a proxy: a dependency is satisfied when its change is on the base, even if its card shows a live-test state. A named dependency whose change is absent, and without which the work cannot stand, is a stop, not a repair: merge the base once, re-grep the anchor, then end with one `# Notes` line that names the card, its state, the two shas and the empty probe. Do not read other card bodies, `git log` or the board directory.

- **Source map and pins.** `src/orchestrator/{pipeline,liveness,spawn,board,config,log,main,index}.ts`, `src/orchestrator.ts` (entry guard), `src/kanban.ts` (task files, worktree names, priority, `blockedBy`), `src/pid.ts` (`writePid`, `pidEntry`, `pidAlive`, `killTree`), `src/tools.ts`, `src/webui.ts` (the barrel most webui code and tests import), `src/webui/{page,board,payload,logpane,index}.ts`, `src/hub.ts`, `src/mcp.ts`, `src/analysis-run.ts`, `src/efficiency-analysis.ts`. Role prompts are `agents/<role>.md`. `src/webui/page.ts` builds the client page as a template literal and inlines one function as source text, so that function must not capture outer variables. There is no DOM library, so extend the element stub in the file you touch. `tests/webui/board.test.ts` pins `PAGE`, its CSS and every inlined function. `tests/webui/page.test.ts` pins served-page CSS that `board.test.ts` does not, including theme, role card and state rules. A CSS or page change usually updates and runs both files. `logpane.test.ts` pins `md` and `renderLogChunk`, `agentlog.test.ts` pins history and payloads. A rule-level pin quotes the whole block, so a change to that block updates the pin in the same commit. A Specs line that bounds the diff does not forbid a pin update: update the pin, run it, and name the extra file in `# Notes`.

## Recon and edits

- **Five calls to the first edit, one visit per file.** Count tool calls, not blocks or turns. Land the first edit within five tool calls. A second call on the same path is a defect: the first call was scoped wrong. A third recon turn on a one-file or docs change is also a defect. Ask one question per call and put independent calls in one block. Include every anchor the next call needs. When a probe returns nothing, do not repeat it with another pattern: move to the wider question or accept the empty result as final. Never plan or draft in a thinking block. The edit call is the draft. If a thinking block contains `assert`, a code fence, a diff or notes prose, stop and make the one missing grep. A thinking block ends in a tool call, not in a decision. If you write "wait", "actually" or "let me reconsider", the next token is a tool call. A second thinking block on the same decision is a defect. Long thinking, not tool calls, is the main cost of a slow run.

- **Merge once.** Compare the two shas once. On a mismatch run `git merge --ff-only main` and nothing else. If it refuses because local changes would be overwritten, run `git stash push -u; git merge --ff-only main; git stash pop` in one call. Keep the pre-merge sha for a base proof. Never inspect other branches or a `meta/kanban` ref. Uncommitted test files are the task's pins: read them before the first source edit with one `read` at a generous limit, or `git diff -- <path>` for a long file. The pins name the seams and the expected values. Keep them, run them and ship them. Never delete, rewrite or re-derive them.

- **Small hunks, unique anchors.** Split a rewrite into about four hunks per `edit` call. A call applies all hunks or none. Before the call, run `grep -cF '<anchor>'` for every hunk. A count above 1 means add the adjacent unique line. A dark-theme block and its media-query twin often share a tail, so anchor on the selector or the preceding comment. Never batch a hunk when an earlier hunk in that batch creates its anchor. On rejection, fix the duplicate anchor and resend the batch once. If it fails again, cut to one hunk per call. After a success result every hunk landed, so do not re-read the file to verify it. The pre-commit diff for evidence is the one exception. For a large insertion, append with `cat >> file <<'EOF'` and read the block back. Update a comment that the change makes false in place and add no second comment. When you add or remove a module-level symbol, grep the consumer import line in the same breath.

- **Edit prose from the transcript, never a placeholder.** Get the exact old sentence into the transcript before the edit call. Put the replacement sentence in that same call. Never emit a placeholder such as `PLACEHOLDER` and never plan the sentence in thinking. `README.md` (config, pipeline, fade view), `skills/se-llm-team/SKILL.md` (the PM view), `docs/architecture.md`, `docs/agents-and-tools.md` and `agents/<role>.md` are behavior-bearing. Grep the sentence the change makes false and edit it with one hunk per file. Never state one rule twice in one file. `agents/doctor.md` is pinned byte for byte in `tests/efficiency-analysis/doctor.test.ts`, so a wording change there updates `shippedDoctorPrompt` in the same commit. The other role prompts are asserted by substring, so a pure addition breaks no pin and an empty `grep -rn '<phrase>' tests/` is the proof. Before you accept a sentence that names a numbered step, read the list, because a deletion or a renumber changes every later number and every count in the docs.

- **Root cause over call sites.** Model a boolean config gate as one early return at the single entry point of its stage, before any slug, pid or spawn write, and leave the flag-on path untouched. The sweep re-runs on every scan, so the fix must hold on the next scan: assert the state, then the absence of each spawn artifact. Never guard at a call site when the entry point is the shared root cause, because every other caller then needs the same guard.

## Tests

- **Commands and parts.** Run a suite as `node tests/<area>/<file>.test.ts`. The areas are `tests/kanban`, `tests/orchestrator`, `tests/webui` and `tests/efficiency-analysis`, plus the loose `tests/*.test.ts` and `index.test.ts`. There is no build, no typecheck, no install and no `node_modules`, and `node --check` cannot parse TypeScript. `grep -n '^export' tests/helpers.ts` lists the helpers (`fixture()`, `runDaemon()`, `waitFor()`, `waitForAsync()`, `freePort()`, `roleStub`, `argvStub`, `deadStub`, `cleaned`, `daemons`, `cleanupAll()`, `killAll()`). Never guess a helper API. Read the adjacent part and copy its fixture, log read and assertion style. For a part-list suite, find the last marker with `grep -n '^// --- part' <file> | tail -3`, then append the next `// --- part N:` block after it. A shared literal ripples into every exact-output assert: count the sites with `grep -rn '<literal>' tests/ | wc -l`, replace them in one `perl -pi -e` pass, then count the new literal.

- **Two runs, one red set then one green set.** Fix the suite set at the premise call: the suites you edited, the suites the Specs name and the caller suites. Run the set exactly twice: once red after the test edit and before the source edit, then once green after all edits. Never run one suite green and then run it again inside the full loop. A write run never uses `pnpm test` or `pnpm test:changed`. Run the suites one after another with the loop below. Never pipe `node` through `tail` or `head`, because the pipe status hides a failure. Capture each run to a file in the same call, then grep or read that file. A failed assert prints `AssertionError`; grep the captured file for that marker, never for a guessed prose field. Never rerun a suite to see a different slice of its output and never run one a third time. A passing suite can print nothing, so print a `pass` line per file. Keep `exit $fail`: never end the loop with `exit 0`, because that makes the call status lie.

  ```bash
  fail=0
  for f in tests/a.test.ts tests/b.test.ts; do
    out=$(timeout 300 node "$f" 2>&1); c=$?
    printf '%s\n' "$out" > "/tmp/$(basename "$f").out"
    printf '%s exit=%s\n' "$f" "$c"
    if [ $c -eq 0 ]; then printf 'pass %s\n' "$f"; else printf '%s\n' "$out" | tail -n 25; fail=1; fi
  done
  exit $fail
  ```

- **Absence and pins.** A path under `<root>/.kanban/.logs/` (`logPath`, `armedPath`, `counterPath`, `pidPath`) exists only after a write, and a fixture that ends before that write leaves it absent. Write an absence assertion as `!existsSync(p) || !readFileSync(p, "utf8").includes("<line>")`. Prefer asserting the absence of the artifact (pid file, armed file, slug file) to the absence of a log line. A bare `readFileSync` on an unwritten file throws `ENOENT`, and the loop reports it as a thrown error after a part that otherwise passed. A non-zero exit after a part label that says "passed" means a thrown error, not a failed assertion: read the last 25 lines of the captured file and expect `Error:` or `ENOENT`. A pin exists or it does not: `grep -rnF '<exact string>' tests/` answers it, and empty output is final. No pin and none named means no test edit. A pin-only run edits no source, so run the new pin green first, then prove it by disabling its trigger. Back the file up with `cp` and restore with `cp`. Never `git stash` a test file that holds the new pin, because the stash removes the pin with the trigger. Bundle all red mutations in one call, run only the suites you mutated, restore, then run those suites once more green. Prove red before the source edit only when you change behavior. A scratch test is only for an observed failure or a value the Specs do not give.

- **Daemon failures and fixtures.** A suite that spawns a daemon or a child agent can fail at a wait or a timeout your edit cannot reach. At the first such failure prove the base once: `git stash push -- <only the paths the suite renders>`, or a read-only `git archive <pre-merge-sha> | tar -x -C /tmp/baseX` extract. Grep the base output for the wait line once. The same wait with the same timeout means pre-existing, so write one `# Notes` line that names the suite and the wait, then stop. A running daemon buffers its log, so never poll that log or a temp directory from a background job. Fixture HOME: `~/.pi`, `~/.config` and `~/.gnupg` are read-only, so `delete process.env.X` and never `= undefined`, and drop `XDG_CONFIG_HOME` too. Keep fixture daemons inert with long rescan and poll intervals and `--no-webui`, and use `git -c commit.gpgsign=false commit` in fixture repos.

- **Acceptance: static proof, no live harness.** The repo has no DOM library, no browser driver and no Playwright, and no test fixture serves the web UI page. A visual, scroll, layout or screenshot check has no headless path here. Do not probe global modules, a browser cache, a browser skill, CDP or a stub server. Do not build a second harness. Prove the nearest mechanical fact with one targeted `grep` or an existing suite: the source literal, the computed geometry or the pinned CSS. Record that the live pass is left to the reviewer in one `# Notes` line. If the Specs name a live check, this substitution is the answer, not a blocker.

## Shell traps

- **Honest status and output caps.** Chain recon reads with `;`, not `&&`, put the step that can fail last and end the call with `; true`. A bare `grep` with no match and an `ls` of a missing path exit non-zero and fail the call. `! grep -q` inverts the status, so print a label per acceptance check and never read a raw `$?` out of a chain, because a `;` chain reports only the last command. Grep the bare symbol, not a guessed declaration. An empty variable silently removes its argument, so `git -C "$dir"` with an empty `dir` runs in the cwd and `ls "$dir"/x` lists `/x`: assert it is non-empty or set a literal fallback. Never truncate the only useful output with `head`: a capped `| head -N` hides the line that answers the next question, so use `grep -c` for a count. Escape a literal dot in `grep` and never `grep -m` a test run. A short numeric literal is a prefix of a longer one, so quote it and use `-F`, as in `grep -nF '"42"'`. A tool result truncates long output near 8 KB, so never `cat` a whole diff or a long file: use `git diff --stat`, `git diff --unified=0`, `git diff | grep '^+'`, or `read` with a range. Split a recon call by question, not by file. One argv over 131072 bytes fails with E2BIG. `ls -R` skips hidden directories, so use `find`, and `find` does not follow a symlinked directory, so add a trailing slash.

- **Process counts.** Count test leftovers with one anchored pattern such as `pgrep -af '^node /tmp/<fixture-prefix>'`. An unanchored pattern also matches your own bash command line, and a bracketed pattern still matches the parent shell line. Take one count before the run and one after the run, and treat those two numbers as final. The counts, pids and leftover paths in the Specs are evidence from the author's host at write time, not current state: record what you measure and name a difference in one line, then never re-measure to reconcile it. Never run `pkill -f`. An orphan whose fixture directory is gone is inert, so kill it once by pid and do not return to it.

## Delivery and board

- **Evidence, then notes under the existing heading.** On a write run, run every Acceptance check that counts modified files before the commit and label it `pre-commit`. Before the commit, `git status --short` and `git diff --stat` give the modified-file count. After the commit use `git show --stat --oneline HEAD` and `git status --short` for the post-commit proof. Write only what you ran: never write "after commit", "post-commit" or "clean" for a check that ran before the commit. If the notes claim a post-commit suite run, rerun the suite after the commit or drop the claim. Read the tail of `SPECS.md` before you append. The task template may already end with an empty `# Notes`: when it does, append only `##` subsections under that heading and never add a second `# Notes`. Write the whole block in one `cat >> SPECS.md` call. Use at most three `##` subsections: `What changed`, `Acceptance`, `Follow-up`. A blocker for the user goes in one `## Follow-up` line. A real user question or a big assumption goes under `# Open questions` after it, and the spawn prompt owns that section. Do not create an empty `# Open questions`. Keep the block terse: one line per change, one line per check with its command and exit code, and the measured numbers. Do not write an apology for a proof you chose to skip. `SPECS.md` is a gitignored symlink, so `git status` never shows it and that is correct: confirm the notes with `readlink -f SPECS.md` and a `tail` in the commit call, and never pause on the missing status line.

- **Commit by name.** Stage the source, test and doc paths by name, never `git add -A`, and never `git add SPECS.md` or `.kanban`, because an ignored path fails the whole call and no later command runs. Make one commit for the code, refer to it by subject, not by SHA, and end with `git show --stat --oneline HEAD`, then stop. No source or test diff means no commit, and the notes write is the deliverable, so never make an empty commit. The final message is one short line with the outcome and the next action. Resolve the board from the symlink with `board=$(dirname "$(readlink -f SPECS.md)")`. `.kanban`, `SPECS.md` and `AGENTS.md` are gitignored symlinks into the main checkout. Never write `AGENTS.md` and never stage board files. `.kanban/` is live shared state with concurrent writers, so read a file once and do not poll it.
