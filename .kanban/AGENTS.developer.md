# developer: role guidance

Durable method for the developer role. The spawn prompt owns the numbered steps. `SPECS.md` in the cwd is a symlink to the task file in the main checkout. Put task findings in `# Notes`. Report durable method findings in `# Notes`, never in this file or `AGENTS.md`.

## Contract

- Read `SPECS.md` once, fully, and keep it. `# Specs` and `# Acceptance` are the contract, `# Context` is background. The Specs own the required outcome and beat this file and the spawn prompt. Their stated cause is a hypothesis until a failing run proves it. Copy a Specs value verbatim into the code and the pins. Decide each open choice once, before the first edit. Change only what the Specs and Acceptance require. Update a comment that the change makes false in place, keep its task tag, and do not add a second comment. Work in the worktree and never change task states or edit the board.
- A verification-only task changes no source. Its deliverable is the probe result plus one `# Notes` block. Do not look for a code change to make, and do not fix a blocker's contract.
- When two Specs or Acceptance lines cannot both hold, stop. Prove it with the smallest probe, write one `# Notes` line that names both lines and the file that owns the conflict, and end the run. Do not re-derive it later and do not move it to `# Open questions`.
- Never run `pnpm test` or `pnpm test:changed`, even when `# Acceptance` names `pnpm test`. The first is a shell loop over every suite and takes minutes. Run the suites the Specs name and write one `# Notes` line that the full suite is the live tester's gate.

## Orientation

- Your worktree keeps the base it was created with, so it can predate a blocker that merged later. Compare the two shas with separate calls: `git rev-parse --short HEAD` and `git rev-parse --short main`. `--short` takes one revision only, so `git rev-parse --short HEAD main` dies with `fatal: Needed a single revision`. On a mismatch run `git merge --ff-only main`, and nothing else. Never inspect other branches, merge bases, `git log --all`, or a `meta/kanban` ref.
- Budget 4 tool calls from the Specs read to the first edit: one `read` of the file you change, one `read` of the suite that pins it, one bash that greps the anchors (the helper source, the CSS neighbour, the `PAGE` interpolation point). At the budget, stop and write the smallest form that satisfies the Specs. `read` a whole file with a generous `limit`, and use `sed -n 'A,Bp'` only for a Specs-cited range. Never read a range twice: the edit anchor is in output you already hold. Never `cat` a whole file, and never run `pwd`, `git status`, or `git diff` for orientation. `cd` only for the repo root or the board.
- Cap the design pass at one thought per branch point. If you reach the same answer twice, stop thinking and act. For a test harness, stub, fixture, daemon, or spawn, copy the idiom from the nearest existing test that already does that job. A probe is only for a value the Specs do not give: one `node -e`, print every value, copy the output. If a probe and the Specs disagree, the Specs win. Hand a web question or a wide sweep to one subagent. Do not spawn one for a small, local change. Never spend a thought block listing hypotheses. Run the smallest command that falsifies one, or instrument the branch.
- Repo map: `src/orchestrator/pipeline.ts` (sweeps, caps, promotion, `doneCleanup`), `liveness.ts` (`poll()`, which also calls `promoteBacklog`), `src/kanban.ts` (task files, worktree naming, `PRIORITY_RANK`), `src/tools.ts` (registration), `spawn.ts` (prompt render, spawn log), `main.ts` (watch, timers), and `src/webui/{logpane,payload,page,board}.ts`. Tests import `../../src/*.ts` and `../helpers.ts`, with the repo root at `join(HERE, "../..")`. `tests/helpers.ts` exports `fixture()` (a git repo in a temp dir) and `roleStub`. `createTask` and `setState` write the task file as a daemon self-write, so a gate that ignores self-writes needs a raw `writeFileSync` in a test for an external edit. `PAGE` is one template literal, so a function interpolated into it must be self-contained: module constants and regexes do not travel in, and a regex literal written inside loses a backslash. For a page test, reuse the file's extraction idiom (`function name(...) { ... }` plus `new Function`) and assert the returned value. A page change needs a daemon restart for a visual check. There is no DOM library: extend the element stub in the file you touch and give it every property the code path reads (`tagName`, `style`, `innerHTML`, `appendChild`, `children`, both sibling getters). Do not add a dependency.

## Flakes

- A flaky assertion is a symptom, not a diagnosis. Reproduce it in the real suite before the first edit: loop the single suite N times in one foreground call, redirect each run to a file, and stop at the first failure. Keep that log. Do not accept the Specs' stated cause, a green single run, or an isolated probe as proof. The Specs own the required outcome, so keep the Acceptance green and write the corrected cause in `# Notes`.
- Debug a flake at the branch that decides the outcome. Add one temporary log line at every skip and return path, with the values that path reads, then loop until a failure. A summary line alone hides which file or branch was skipped. Do not build a standalone harness that reproduces the code in isolation: process state, earlier test parts, and self-writes are often the trigger. Remove every debug line and restore the source before commit, then confirm with `git diff --quiet -- <file>`.
- A wall-clock test must not depend on runner speed. `Date.now()` is integer milliseconds but a filesystem mtime has a sub-millisecond fraction, so a file written in the current millisecond can read as future to a `mtimeMs > Date.now()` guard. Pin `utimesSync` mtimes a safe margin in the past and make the window much larger than any plausible stall.
- One flaky assertion usually repeats in the same suite. Grep the exact assertion string, fix every occurrence in one pass, and write one `# Notes` line that names the shared cause. Do not spend thought blocks on per-occurrence scope when the Specs say to cover the same race.
- Prove a flake fix with repeated runs, not one green run. Capture every exit code, keep the full log of any failing run, and add CPU load if the bug is timing-related. Use the loop the Specs name as the gate and stop when it is green.

## Edits

- Split a rewrite across small `edit` calls, about four hunks each. A call applies all hunks or none, so one bad hunk discards the whole payload. Never put a hunk in a batch when an earlier hunk in that same batch creates its anchor: the tool matches the original file, not the file after the earlier hunk. Never swap `oldText` and `newText`. When a hunk is rejected, cut the payload on the retry instead of resending the same shape, and narrow to one hunk per call until it lands. Anchor each hunk on the shortest unique line from your read, and keep the whitespace exact. Do not spend a call on `cat -A` to re-check tab depth. Write every comment complete on the first pass. After a success result every hunk landed: do not re-read the file and do not run `git diff`. For a large insertion, append with `cat >> file <<'EOF'` and read the appended block back. When you add or remove a module-level symbol, grep the consumer import line in the same breath: `grep -rn 'from "./<module>.ts"' src/`.

## Tests

- Run a suite as `node tests/<area>/<file>.test.ts`. Areas: `tests/kanban`, `tests/orchestrator`, `tests/webui`, `tests/efficiency-analysis`, plus the loose `tests/*.test.ts` and `index.test.ts`. There is no build and no typecheck, and `node --check` cannot parse TypeScript. The pin's subject decides the order, not the task-type prefix: a pin for behavior that does not exist yet runs red first, even under a `refactor:` name, and a pin for output that must stay unchanged passes before the edit. `complexity: trivial` skips red-first but still adds any pin the Specs name.
- Run exactly the suites `# Acceptance` names plus the suite file you edited, in one foreground call. Capture the output in a variable and print `exit=`. Never pipe the `node` command, because `node f 2>&1 | tail` reports the pipe status and a failing suite shows `exit 0`. Never `grep -m` the output, because it cuts the assertion line. Read the first `AssertionError` line, implement to green, and do not re-run for the message. Green means done.

  ```
  fail=0
  for f in tests/a.test.ts tests/b.test.ts
  do
    out=$(node "$f" 2>&1)
    c=$?
    printf '%s exit=%s\n' "$f" "$c"
    if [ $c -ne 0 ]
    then
      printf '%s\n' "$out" | tail -n 25
      fail=1
    fi
  done
  exit $fail
  ```

- A suite that spawns daemons (`spawn`, `sweep`, `merge`, `daemon`, `hub`, `poll`) fails at a wait or timeout point that your edit cannot reach. That is not your regression. Prove it once: stash your edit, run that suite, restore the stash in the same call. Still red at the same wait, with the same timeout line, on the base commit means pre-existing. Write one `# Notes` line that names the suite, the wait, and that your own pin could not run, then finish the source fix. Do not read `pipeline.ts`, `liveness.ts`, `board.ts`, or `tests/helpers.ts` to explain it, do not chase the fixture directory after the run (cleanup and an exit hook delete it), and do not try to make a background daemon log readable. Run at most one suite at a time. A daemon test leaves detached `fake-agent.cjs` children behind when a run is killed or times out, and those children make the next run look flaky. Check with `pgrep -af fake-agent`, kill each pid with `kill <pid>`, then run the suite once, serially, with a generous timeout.

## Shell traps

- Chain recon reads on separate lines, not with `&&`. Put the step that can fail last. One failing probe at the head of an `&&` chain throws away every read behind it and costs a second identical call. A bare `grep` with no match exits 1 and fails the whole call, so end a recon call with `|| true`, and grep the bare symbol name, not a guessed declaration form: `grep -n 'export const fixture'` misses `export function fixture`. An empty variable silently removes its argument, so `git -C "$dir"` with an empty `dir` runs in the cwd and `ls "$dir"/x` lists `/x`: assert the variable is non-empty, or set it with a literal fallback. Never truncate the only useful output with `head`, and never trust a pipeline count you did not see on two known lines first. One argv over 131072 bytes fails with E2BIG. `ls -R` skips hidden directories, so use `find`, and `find` does not follow a symlinked directory, so add a trailing slash. Escape a literal dot in `grep` (`\.`), or it matches unrelated text. A running daemon buffers its log, so `grep` and `tail` on it return nothing until the process exits. Never background a suite to poll its log or its temp directory: capture with `> file 2>&1` in one foreground call and read the file after it exits. Never run `pkill -f <pattern>`: the pattern matches your own `bash -c` command line and kills the call with exit 143. Use `pgrep -af` and `kill <pid>`.

## Delivery and board

- Write `# Notes` before the commit, then make one commit so the notes and the code land together. Stage only source, test, and doc files, never the board or `AGENTS.md`. Refer to the commit by subject, not by SHA. End the same call with `git show --stat --oneline HEAD`, then stop. No source or test diff means no commit: the `# Notes` write is the deliverable. Do not read pipeline, liveness, or merger code to find permission for the end of the run, and do not make an empty commit.
- Resolve the board from the symlink: `board=$(dirname "$(readlink -f SPECS.md)")`. `.kanban`, `SPECS.md`, and `AGENTS.md` are gitignored symlinks into the main checkout. Append `# Notes` through `SPECS.md` with `cat >>`, under the existing `# Notes` heading. One `##` subheading there is enough. A second `#` heading is not. Never write `AGENTS.md`, and never stage board files. `.kanban/` is live shared state with concurrent writers, so read a file once and do not poll it. Fixture HOME is required for global state: `~/.pi`, `~/.config`, and `~/.gnupg` are read-only, delete with `delete process.env.X` and never `= undefined`, and drop `XDG_CONFIG_HOME` too so the hub lock resolves inside the temp HOME. Keep fixture daemons inert with long rescan and poll intervals and `--no-webui`, and use `git -c commit.gpgsign=false commit` in fixture repos.
