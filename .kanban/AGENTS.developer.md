# developer: role guidance

The spawn prompt owns the numbered steps, the state ban, and the stall window. This file gives the method and the repo facts. `SPECS.md` in the cwd is a symlink to the task file in the main checkout. Put task findings in `# Notes`.

## Contract

- Read `SPECS.md` once with the `read` tool and keep it. `# Specs` and `# Acceptance` are the contract. `# Context` is background. The Specs win over this file and the spawn prompt, including the trivial-task skip. When the Specs name a file, a suite, or a pin, do it. Do not open `SPECS.md` a second time to confirm a line you already read.
- Decide each choice once, before the edit, then stop. When the Change section offers two forms, the Acceptance check is the judge. Pick the shorter form that passes it and move to the edit. When a Specs line states a count, a path, or a fact that no check tests, take it as given. Do not measure it again, and do not resolve it from the source.
- When two Specs lines disagree, the `# Acceptance` checks are the arbiter. Choose the smallest behavior that passes them, write the choice and its reason as one `# Notes` line, and stop. Do not mine older task files or git history for the author's intent. If a premise the Specs call proven conflicts with the evidence, check it with one command and move on.
- Change only what the Specs and the Acceptance require. Do not add docs, comments, renames, or extra hardening. An unrequested one-line change becomes a second commit, a second suite run, and reviewer time. Record an unfixed risk in `# Notes` and do not fix it. Implement in the worktree and finish when the notes are written. Never change task states and never edit the board.

## Orientation

- Resolve the board from the symlink, not from guessed `../` depth: `board=$(dirname "$(readlink -f SPECS.md)")`. A worktree sits deeper than the main checkout, so `../../.kanban` and similar paths miss. Use the absolute path for the rest of the run.
- Recon is one batch per file, and about eight calls before the first edit. Read a named file once with `read` (offset and limit) and grep once for the anchors. Never use `cat` or `sed` to read a file, and do not return later for imports, a tail, or a second look at a table. When the Specs quote the exact strings, one `grep -n` on those strings usually replaces the read.
- When a question needs research beyond recon, delegate it to one subagent with one question and one evidence standard, and continue your own work while it runs. Call `get_subagent_result` only when no independent work is left, never as an idle wait. Spend at most one cheap command to check a claim that changes your code or notes.

## Tests

- There is no build and no typecheck. A suite runs as `node tests/<area>/<file>.test.ts` or `node index.test.ts`. Areas: `tests/kanban`, `tests/orchestrator`, `tests/webui`, `tests/efficiency-analysis`, plus the loose `tests/*.test.ts`. `node scripts/test-changed.mjs` maps the changed and untracked files to suites and runs them. `pnpm test` runs everything and is the last resort. `node --check` cannot parse TypeScript, so it is not a check.
- A suite that `# Acceptance` names always runs, even for a docs-only, markdown-only, or comment-only change. Without a named suite, such a change runs none: it cannot break one. Run one suite at a time, never two at once. An async orchestrator suite takes tens of seconds, so run it once per code change and do not run a green suite again unless the code changed.
- A pin exists or it does not. One `grep -rn "<exact string>" tests/` answers it, and empty output is a complete answer. Do not widen the pattern to `src/`, do not sweep for digits or near-miss numbers, do not retry with another pattern, and do not read a suite to see what it asserts. When no pin exists and the Specs name none, the change needs no test edit.
- Test-first: add the pin, run the suite, read the first red `Error` line (it prints the actual value), then implement until green. Model a new test on the nearest `// --- part` sibling. Copy exact strings from the output, never compose a long expected string by hand. A missing log or output file is a valid red state, so guard the read to fail with its own message, not with ENOENT. A `complexity: trivial` task skips red-first and new tests, but a pin that the Specs name is still required: add it with the change and run until green.

## Edits and checks

- The `edit` tool takes `{oldText, newText}` hunks. Ranges must not overlap, and a failed batch applies nothing. Anchor each hunk on the shortest unique line copied from a read. For a large insertion, such as a test part or a function body, append with `cat >> file <<'EOF'`, never a long `newText`. After an edit, read the hunk and run one `git diff -- <file>`. Before a commit, read the staged diff for imports that the edit made unused.
- Check a fact where it is cheap and decide there, before the edit, not as an audit after it. A registry name is one grep of its declaration. A doc claim is one read of the paragraph. When the fact is confirmed, edit once and stop checking. A second lookup of the same fact is wasted work. Do not recompute a documented total from the source, because a naive grep gives a wrong answer. The tool registry in `src/tools.ts` counts 2 or 14 tools by two cheap greps, and the real set is the 13 keys of `TOOLS`. If a number must be measured, anchor on the registry block with `awk '/export const TOOLS/,/^};/' src/tools.ts | grep -cE "^\t[a-z0-9_]+: \{"`.
- Capture the exit code in the same command and print the output only on failure:
  ```
  out=$(node tests/x.test.ts 2>&1); c=$?
  if [ $c -ne 0 ]; then printf '%s\n' "$out" | tail -n 25; fi
  ```
  A bare `[ $c -ne 0 ] && ...` leaves the shell at exit 1 and reads as a failure. Never pipe a failing suite through `head` or `tail`. `grep -c` exits 1 on zero matches.
- Write `# Notes` before you commit, and commit once. The notes and the change then land together. Build the commit subject and body from verified facts, record the commit by subject and never by SHA, and confirm it with one `git log --oneline -1` or `git show --stat`.

## Board and fixtures

- `.kanban`, `SPECS.md`, and `AGENTS.md` are symlinks into the main checkout and are gitignored. Append `# Notes` through `SPECS.md`, under the existing heading and never as a second heading. Never write through `AGENTS.md`. Never stage or commit board files, `SPECS.md`, or `AGENTS.md`. Task files have `# Summary`, `# Specs`, and `# Notes`, and sometimes `# Acceptance` or `# Open questions`. `.kanban/` is live shared state with concurrent writers: read a board file once and do not poll a file that another agent owns. If an acceptance check fails on a file that you may not edit, write the decision in `# Notes` and stop.
- Fixture HOME is required for global state. `~/.pi`, `~/.config`, and `~/.gnupg` are read-only. Delete `XDG_CONFIG_HOME` with `delete process.env.X`, never `= undefined`. Keep fixture daemons inert with long rescan and poll intervals and use `--no-webui`. Use `git -c commit.gpgsign=false commit` in fixture repos. A test that a page or plugin change adds must also pass in the fixture HOME, not only in yours.

## Traps and map

- Shell traps: one argv over 131072 bytes fails with E2BIG. `ls -R` skips hidden directories, so use `find`, and `find` does not follow a symlinked directory, so use a trailing slash. A scratch script that imports `../src` lives under `tests/`, never `/tmp`. `uniq -f` and `sort -k` count fields from the line start, so a label after leading punctuation does not land in the field you skip: use `grep -o "<label>" | wc -l` or `sed` instead. Before you trust a count from a pipeline, run it on two known lines and look at the shape.
- Orchestrator map and tests: sweeps, the reviewer cap, backlog promotion, and `doneCleanup` are in `src/orchestrator/pipeline.ts`. `poll()` is in `liveness.ts`, and it also calls `promoteBacklog`, so a new parameter must keep its default. Worktree naming is in `src/kanban.ts`, tool registration is in `src/tools.ts`, and prompt rendering and spawn logging are in `spawn.ts`. The watch handler, debounce, and timers are in `main.ts`. Tests import from `../../src/*.ts` and `../helpers.ts`, with the repo root at `join(HERE, "../..")`, and an imported module-level symbol needs `export`. A stub emits each snapshot once. Gate a post-spawn assert on the suite's `waitFor`, and sleep about 50 ms in a wait loop so the event loop reaps children. For a daemon fixture, use `runDaemon` with inert stubs, long intervals, `--no-webui`, and one teardown path. After `kill("SIGTERM")`, wait for the daemon `exit` event before `cleanupAll`, or leave the temp root. A cleanup while the child still writes fails with ENOTEMPTY.
- WebUI: `src/webui/page.ts` holds one `PAGE` template literal. It interpolates client helpers as source. A served function must be self-contained, because module-scope constants and regexes do not travel into `PAGE`. A regex literal written in `PAGE` loses a backslash. Asserts read the built `PAGE`, and a page change needs a daemon restart. For a page test, reuse the file's existing extraction idiom: match `function name(...) { ... }`, then run the source with `new Function`, and assert the returned value, not the whole `PAGE`.
