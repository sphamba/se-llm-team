# developer: role guidance

Durable method for the developer role. The spawn prompt owns the numbered steps. `SPECS.md` in the cwd is a symlink to the task file in the main checkout. Put task findings in `# Notes`, and put a method finding there too, never in this file or `AGENTS.md`. The Specs beat this file and the spawn prompt. The bash cwd is already the task worktree, so do not prefix commands with `cd`.

## Contract

- Read `SPECS.md` once, fully, and keep it. `# Specs` and `# Acceptance` are the contract, `# Context` is background. Decide each open choice once, before the first edit. Change only what the Specs and Acceptance require. Work in the worktree, and never change task states or edit the board.
- Classify the run before the first edit. A Summary that says "verification", or a Specs line that says "do not edit code", "do not commit" or "a defect is a new task", means a verification run. A bare `test:` prefix is a hint, not a classifier. A verification run is read-only: no source edit, no red-first, no commit. Its deliverable is `# Notes`: one evidence line per Specs line, the suite command and exit, and a `## Defect for a new task` block for each defect. Put a defect in `# Open questions` only when the Specs name that section. A defect is a new task, not an edit here. Every other run is a code run.
- Test the premise in one bash call: `grep -rnF '<symbol>' src/ tests/`, `git rev-parse --short HEAD; git rev-parse --short main`, and `grep -H '^state:'` on the card files a Specs line or `blockedBy` names. A Specs line that names another task is a dependency even when `blockedBy` is empty. Do not read other card bodies, `git log`, or the whole board directory.
- The diff on `main` is the fact, the card state is a proxy. A named dependency is satisfied when its change is on `main`, even if its card still reads a live-test state. Merge `main` once, then grep the symbol the Specs name. If the change is present, proceed, and record one `# Open questions` line when the card is not `done`. If it is absent and your own work cannot stand alone, end with one `# Notes` line that names the card, its state, the two shas, and the empty probe. Never implement, debug, or revert the dependency's work. When two Specs lines cannot both hold, stop, prove it with the smallest probe, and write one `# Notes` line that names both lines and the file that owns the conflict.

## Worktree and branch

- Compare the two shas once: `git rev-parse --short HEAD` and `git rev-parse --short main`. On a mismatch run `git merge --ff-only main`, and nothing else. When it refuses because local changes would be overwritten, run `git stash push -u; git merge --ff-only main; git stash pop` in one call. Keep the pre-merge sha for a base proof. Never inspect other branches, merge bases, `git log`, or a `meta/kanban` ref.
- A worktree can ship uncommitted test files: those are the task's pins. Read them before the first source edit, one `read` with a generous limit, or one `git diff -- <path>` for a long file to see only the new cases. They name the seams and the expected values, so do not delete, rewrite, or re-derive them. Keep them, run them, and ship them in your commit.

## Recon and design

- Source map: `src/orchestrator/pipeline.ts` (sweeps, caps, promotion, done cleanup), `liveness.ts` (`poll()`, `promoteBacklog`, the `LANES` table), `spawn.ts` (prompt render, context links, spawn log), `board.ts` (worktrees, git calls), `src/kanban.ts` (task files, names, `PRIORITY_RANK`, `blockedBy` parse and cycle guard), `src/tools.ts` (registration), `main.ts` (watch, timers), `src/webui.ts` and `src/webui/{index,logpane,payload,page,board}.ts`. The `merging` and `integration-testing` states are project-wide single lanes with one pid entry each, not one per task. `src/webui/page.ts` is one template literal, so an interpolated function must be self-contained. There is no DOM library, so extend the element stub in the file you touch and add no dependency.
- A gate on task eligibility is the first statement of the per-task block in the sweep that selects the candidate: before `ensureWorktree`, any state write, any spawn, and any run bookkeeping such as `consumeReviewerRun`. One gate per entry point that can start work, never a patch downstream. Put the shared predicate in `src/kanban.ts` next to the field parser, export it, and import it in the pipeline. `blockedBy` is a comma string of `#<n>` refs plus literal tokens that name no card. `blockedNums` parses each part with `parseInt` and drops `NaN`, so a literal token vanishes from every number-based check. A hold or gate rule must test the tokens, and a cycle guard over numbers must ignore literals on purpose.
- Budget about four tool calls from the Specs read to the first edit, and two for a prose-only change: the Specs read and one grep batch. One file, one read: a generous limit beats two ranges, and a second read of the same file means the first was too narrow. A Specs line that names a symbol is answered by that function alone, so read the function, not its callers and not the state machine around it. A doc-claim check is an Acceptance step, not recon: run it once, late. Anchor every read on a name, not a line number (`grep -n 'function sweepToMerge' <file>`), because a merge shifts every line and a Specs range is a hint, not a coordinate. A probe is only for a value the Specs do not give: one `node -e`, print every value, copy the output. On a disagreement the Specs win. Hand a web question or a wide sweep to one subagent, never a small local change. Cap the design pass at one thought per branch point: if you reach the same answer twice, act.

## Edits

- Split a rewrite into small `edit` calls, about four hunks each: a call applies all hunks or none. Before the call, `grep -cF '<anchor>'` on each anchor, and a count above 1 means add the line above it. Never batch a hunk when an earlier hunk in that batch creates its anchor, and never swap `oldText` and `newText`. Whitespace must match exactly. On rejection, cut the payload to one hunk per call instead of resending the same shape. After a success result every hunk landed: do not re-read the file, diff it, or re-grep a literal you just wrote. For a large insertion, append with `cat >> file <<'EOF'` and read the block back. When you add or remove a module-level symbol, grep the consumer import line in the same breath: `grep -rn 'from "./<module>.ts"' src/`. Update a comment that the change makes false in place, keep its tag, and do not add a second comment.
- Four canonical sites carry behavior: `skills/se-llm-team/SKILL.md` (the PM's view), `docs/architecture.md`, `docs/agents-and-tools.md`, and `agents/<role>.md` (the role prompt). Grep the sentence the change makes false and edit it with one hunk per file. Never count line numbers from the Specs, and never state one rule twice in one file. Tests assert substrings of the rendered role prompt, so a pure addition to `agents/*.md` breaks no pin: `grep -rn '<phrase>' tests/` coming back empty is the proof. Before you accept a sentence that names a numbered step, read the list: a deletion or a renumber also changes every later number and every count the docs give.

## Tests

- Run a suite as `node tests/<area>/<file>.test.ts`. Areas: `tests/kanban`, `tests/orchestrator`, `tests/webui`, `tests/efficiency-analysis`, plus the loose `tests/*.test.ts` and `index.test.ts`. There is no build and no typecheck, and `node --check` cannot parse TypeScript. `tests/helpers.ts` exports `fixture()`, `runDaemon()`, `waitFor()`, `roleStub`, `argvStub`, `deadStub`, `cleaned`, `daemons` and `cleanupAll()`, and `grep -n 'export' tests/helpers.ts` lists them all. `tests/orchestrator/integration.test.ts` is one numbered part list: read its argv/import header and its tail once, append the next `// --- part N:` block, and reuse its local `configFor(root, agent, maxParallel)` and `stopLane(root)`. A verification run adds no pin. The pin's subject decides the order, not the task-type prefix: behavior that does not exist yet runs red first, even under a `refactor:` name, and output that must stay unchanged passes before the edit. `complexity: trivial` skips red-first but still adds any pin the Specs name.
- Budget every suite run. A daemon suite costs about a minute, so two runs of one suite are most of a short run. Plan the set once, before the first run: the suites you edited, the suites the Specs name, and at most one base proof. Never run one suite a third time. A code run runs the suites it edited plus the suites the Specs name. A verification run runs the suites that cover the files the Specs name or the merged batch. Do not read `scripts/test-changed.mjs` to derive a subset: a changed test file runs, a mapped path runs its areas, an unknown path falls back to all suites, and a clean tree prints "no modifications, nothing to run". If the Specs name a test command, run it once and keep the output, even when it is the project script. `pnpm test` and `pnpm test:changed` are the whole run, so a code run never uses them. Never recount or re-open the set after the runs start.
- Before the first source edit, prove your own pin red in one call: `git stash push -- <the source paths you edited>`, run that one suite, expect the new assertion to fail, then `git stash pop`. Run the pin's own suite, not its whole area. When the Specs quote both the failing assertion and the exact source text, the red is certain: prove it with `grep -c` on the source, make the edit, and run that suite once, green. A prose, prompt or docs change usually takes this cheap path, because the only failing assertion is the sentence you just replaced. Then run the named suites in one foreground call, never piping `node` through `tail` or `head`, because the pipe status hides a failing suite:

  ```bash
  fail=0
  for f in tests/a.test.ts tests/b.test.ts; do
    out=$(node "$f" 2>&1); c=$?
    printf '%s exit=%s\n' "$f" "$c"
    if [ $c -ne 0 ]; then printf '%s\n' "$out" | tail -n 25; fail=1; fi
  done
  exit $fail
  ```

  Run at most one suite at a time, cheap suites first. A killed or timed-out run leaves detached `fake-agent.cjs` children: kill them in the next call with `pgrep -af '[f]ake-agent'` and `kill <pid>` for each, never `pkill -f`.
- A clean tree at `HEAD == main` is the base. Run a baseline before the first edit when the Acceptance names a daemon suite, because then it is free and a later red is unambiguously yours. After the edits, at the first wait, timeout or lifecycle red in a daemon suite, do not explain it. In one call, stash only the source paths you changed, run the same suite into a file with a timeout, pop the stash, print the exit: `git stash push -q -- <paths>; timeout 200 node <suite> > /tmp/base.out 2>&1; c=$?; git stash pop; echo exit=$c; grep -n '<wait line>' /tmp/base.out`. The same wait with the same timeout means pre-existing: write one `# Notes` line that names the suite and the wait, then stop. Only a green base permits a probe of your own diff, and then one call. Never read the failing suite, `pipeline.ts`, `liveness.ts`, `board.ts` or `tests/helpers.ts` to explain a wait, never grep the state machine for a missing event, and never rerun the same suite with your change to test whether it was a flake. A pin placed after an earlier failing wait never runs, and you must not move that wait.
- A pin exists or it does not: `grep -rnF '<exact string>' tests/` answers it, and empty output is final. Read the first `AssertionError` line, implement to green, and do not re-run for the message. No pin and none named: no test edit. A shared literal ripples into every exact-output assert: count the sites with `grep -rn '<literal>' tests/ | wc -l`, replace them in one `perl -pi -e` pass, then count the new literal and compare. A scratch test is only for an observed failure or a value the Specs do not give, never for a negative claim a `grep` already proves. Copy `fixture()`, `runDaemon()`, `waitFor()`, `cleaned` and `daemons` from the nearest daemon test, keep the daemon in `try`/`finally` with `daemon.kill("SIGTERM")`, run `timeout 140 node tests/_scratch.test.ts > /tmp/scratch.out 2>&1`, read the file after it exits, and delete the scratch file in the final call. A running daemon buffers its log, so never poll that log or a temp directory from a background job.

## Shell traps

- Chain recon reads with `;`, not `&&`, or put the step that can fail last, and end a recon call with `; true`. A bare `grep` with no match exits 1 and fails the whole call. Grep the bare symbol, not a guessed declaration: `grep -n 'fixture'` finds both `export function fixture` and `export const fixture`. An empty variable silently removes its argument, so `git -C "$dir"` with an empty `dir` runs in the cwd and `ls "$dir"/x` lists `/x`: assert it is non-empty or set a literal fallback.
- Never truncate the only useful output with `head`, escape a literal dot in `grep`, and never `grep -m` a test run. A tool result truncates long output near 8 KB, so never `cat` a whole diff or a long file: use `git diff --stat`, `git diff --unified=0`, `git diff | grep '^+'`, or `read` with a range. One argv over 131072 bytes fails with E2BIG. `ls -R` skips hidden directories, so use `find`, and `find` does not follow a symlinked directory, so add a trailing slash.

## Delivery and board

- On a code run, run every Acceptance check that counts modified files before the commit, because after it the tree is clean: `git diff --stat` for the "exactly N files" line. Then write `# Notes`, kill any leftover `fake-agent` child in the same call, and make one commit so the notes and the code land together. Stage only source, test and doc files, never the board or `AGENTS.md`. Refer to the commit by subject, not by SHA. End with `git show --stat --oneline HEAD`, then stop. No source or test diff means no commit: the `# Notes` write is the deliverable, and you never make an empty commit. The final chat message is one short line with the outcome and the next action.
- Resolve the board from the symlink: `board=$(dirname "$(readlink -f SPECS.md)")`. `.kanban`, `SPECS.md` and `AGENTS.md` are gitignored symlinks into the main checkout. Append `# Notes` through `SPECS.md` with `cat >>`, under the existing heading, and one `##` subheading is enough. Never write `AGENTS.md` and never stage board files. `.kanban/` is live shared state with concurrent writers: read a file once, do not poll it. Fixture HOME: `~/.pi`, `~/.config` and `~/.gnupg` are read-only, so `delete process.env.X` and never `= undefined`, drop `XDG_CONFIG_HOME` too, keep fixture daemons inert with long rescan and poll intervals and `--no-webui`, and use `git -c commit.gpgsign=false commit` in fixture repos.
