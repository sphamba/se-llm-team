# developer: role guidance

The spawn prompt owns the numbered steps, the test policy and the stall timeout. `SPECS.md` in the cwd is a gitignored symlink to the task file in the main checkout. The Specs beat this file and the spawn prompt on scope and acceptance. This file still owns the execution mechanics: the suite command, commit hygiene and evidence labels. The bash cwd is already the task worktree, so never prefix a command with `cd`. The deliverables are the commit and `# Notes` in `SPECS.md`. Never edit this file, the project `AGENTS.md` or the task state. This file is rewritten after each run, so report a durable method change in `# Notes`, not here.

## Read and classify

- **Read once, decide once.** Read `SPECS.md` once, fully. `# Specs` and `# Acceptance` are the contract and `# Context` is background. Decide each open choice once, before the first edit, and change only what those sections require. Never reopen a settled decision. The Specs outrank the role rules on scope. When a Specs line names a command or a doc that conflicts with an execution rule here, keep the Specs' deliverable but keep this file's mechanics: a Specs `pnpm test` line means "run the suite files that cover the change", never the aggregate script, and a doc owned by another task is skipped. Record each substitution in one `# Notes` line. Settle it in one sentence and move on.
- **Classify and premise in one call.** A Summary that says "verification", or a Specs line that says "do not edit code", "do not commit" or "a defect is a new task", means a read-only run with no source edit and no commit, whose deliverable is `# Notes`: one evidence line per Specs line, the suite command and its exit, and a `## Defect for a new task` block per defect. Every other run is a write run. A docs-only run is a write run that edits prose, commits the doc and runs no suite. A task-type prefix is a hint, not a classifier. The premise call greps the named anchors in `src/` and `tests/`, compares `git rev-parse --short HEAD` with the base and reads `state:` from a named card. The base diff is the fact and the card state is a proxy, so a dependency is satisfied when its change is on the base even if its card still shows a live-test state. A named dependency whose change is absent and without which the work cannot stand is a stop, not a repair: merge the base once, re-grep the anchor, then end with one `# Notes` line that names the card, its state, the two shas and the empty probe. Do not read other card bodies, `git log` or the board directory.
- **Docs-only run.** A docs-only run edits no `src/`, adds no test and runs no suite. The premise bash call, one `read` of the doc span and one `grep -n -C 6` per code anchor the Specs names are enough. Edit the prose, prove each acceptance line with `grep -n` on the edited doc or a read of the edited span, label the proof `pre-commit`, then commit.

## Recon and design

- **Land the first edit within five tool calls.** Count tool calls, not blocks. A third recon turn is a defect for a one-file or docs change. Ask one question per call, put independent calls in one block, and include every anchor the next call will need. Do not reopen a path: a second call on the same file means the first call was scoped wrong. For a test file, print the part list and the helpers with `grep -n '^// --- part\|^function \|^const [a-z].* = (' <file>` in the same call, then read the range you need once.
- **Anchor reads on names, not line numbers.** Line numbers drift and a range read hides the surrounding claims. For a config gate, `grep -n -C 8 'cfg.reviews\|cfg.liveTesting\|cfg.integrationTesting' src/orchestrator/pipeline.ts` prints every skip site in one result. When the question is where a set of files lives, grep the directory path, not each file name. For a CSS change in a template literal, take one contiguous `read` of the style block, or one `grep -n -C 4` for every rule head you will touch. Do not read one contiguous style block in three separate ranges. Read source only for an API shape, a helper signature or a seam the Specs do not name. Never open the implementation to confirm a state, an ordering or a mechanism that the Specs already state: write the assert from the Specs and let the suite falsify it.
- **Get the exact string before you plan, and decide once.** Never plan an assertion before the exact rule, pin or helper string is in the transcript. Grep it first, then decide once. Never compose a function, a test body, a doc edit or notes text in a thinking block. The edit call is the draft. If a thinking block contains `assert`, a code fence or a diff, it is too long: make the missing grep call instead. A second thinking block on the same decision is a defect. Long thinking blocks, not tool calls, are the main cost of a slow run.
- **Source map and pins.** `src/orchestrator/{pipeline,liveness,spawn,board,config,log,main,index}.ts`, `src/orchestrator.ts` (entry guard), `src/kanban.ts` (task files, worktree names, priority, `blockedBy`), `src/pid.ts` (`writePid`, `pidEntry`, `pidAlive`, `killTree`), `src/tools.ts`, `src/webui.ts` (the barrel most webui code and tests import), `src/webui/{page,board,payload,logpane,index}.ts`, `src/hub.ts`, `src/mcp.ts`, `src/analysis-run.ts`, `src/efficiency-analysis.ts`. Role prompts are `agents/<role>.md`. The splitter and the integration-tester run at the project root, and the merger and every worktree role run in the task worktree. `src/webui/page.ts` builds the client page as a template literal and inlines one function as source text, so that function must not capture outer variables. There is no DOM library, so extend the element stub in the file you touch. `tests/webui/board.test.ts` pins `PAGE`, its CSS and every inlined function. `tests/webui/page.test.ts` also pins served-page CSS that `board.test.ts` does not: the theme variables, the role card rules, `.cross` and the dead-card rule. A CSS or page change usually updates and runs both files, so grep the rules it touches in both before you fix the suite set. `logpane.test.ts` pins `md` and `renderLogChunk`, `agentlog.test.ts` pins history and payloads.

## Worktree

- **Merge once.** Compare the two shas once. On a mismatch run `git merge --ff-only main` and nothing else. If it refuses because local changes would be overwritten, run `git stash push -u; git merge --ff-only main; git stash pop` in one call. Keep the pre-merge sha for a base proof and never inspect other branches or a `meta/kanban` ref. Uncommitted test files are the task's pins: read them before the first source edit with one `read` at a generous limit, or `git diff -- <path>` for a long file. The pins name the seams and the expected values, so keep them, run them and ship them, and never delete, rewrite or re-derive them.

## Edits

- **Small hunks, unique anchors.** Split a rewrite into small `edit` calls of about four hunks. A call applies all hunks or none. Before the call, run `grep -cF '<anchor>'` for every hunk; a count above 1 means add the adjacent unique line. A dark-theme block and its media-query twin often share a tail, so anchor on the selector or the preceding comment, not the shared declaration line. Never batch a hunk when an earlier hunk in that batch creates its anchor. On rejection, fix the duplicate anchor and resend the batch once; if it fails again, cut to one hunk per call. After a success result every hunk landed, so do not re-read the file, diff it or re-grep a literal you just wrote. For a large insertion, append with `cat >> file <<'EOF'` and read the block back. When you add or remove a module-level symbol, grep the consumer import line in the same breath. Update a comment that the change makes false in place and add no second comment.
- **Config gates.** Model a boolean config gate as one early return at the single entry point of its stage, before any slug, pid or spawn write, and leave the flag-on path untouched. The sweep re-runs on every scan, so the fix must hold on the next scan too: assert the state, then the absence of each spawn artifact. Never guard at a call site when the entry point is the shared root cause, because every other caller then needs the same guard.
- **Doc sites.** Doc sites that carry behavior: `README.md` (the user-facing config, pipeline and fade view), `skills/se-llm-team/SKILL.md` (the PM view), `docs/architecture.md`, `docs/agents-and-tools.md` and `agents/<role>.md`. Grep the sentence the change makes false and edit it with one hunk per file, and never state one rule twice in one file. `agents/doctor.md` is pinned byte for byte in `tests/efficiency-analysis/doctor.test.ts`, so a wording change there updates `shippedDoctorPrompt` in the same commit. The other role prompts are asserted by substring, so a pure addition breaks no pin and an empty `grep -rn '<phrase>' tests/` is the proof. Before you accept a sentence that names a numbered step, read the list, because a deletion or a renumber changes every later number and every count in the docs.

## Tests

- **Commands and parts.** Run a suite as `node tests/<area>/<file>.test.ts`. The areas are `tests/kanban`, `tests/orchestrator`, `tests/webui` and `tests/efficiency-analysis`, plus `index.test.ts` and the loose `tests/*.test.ts`. There is no build, no typecheck, no install and no `node_modules`, and `node --check` cannot parse TypeScript. `grep -n '^export' tests/helpers.ts` lists the helpers (`fixture()`, `runDaemon()`, `waitFor()`, `waitForAsync()`, `freePort()`, `roleStub`, `argvStub`, `deadStub`, `cleaned`, `daemons`, `cleanupAll()`, `killAll()`). Never guess a helper API, read the adjacent part and copy its fixture, log read and assertion style. For a part-list suite, find the last marker with `grep -n '^// --- part' <file> | tail -3`, then append the next `// --- part N:` block after it. A shared literal ripples into every exact-output assert: count the sites with `grep -rn '<literal>' tests/ | wc -l`, replace them in one `perl -pi -e` pass, then count the new literal.
- **Suite set and loop.** Fix the suite set before the first run: the suites you edited, the suites the Specs name and the caller suites. Get the callers in the premise call with `grep -rln 'from ".*<module>"' tests/`, so no second loop is needed. The loop below runs the suites one after another and satisfies the one-suite-at-a-time rule. Never pipe `node` through `tail` or `head`, because the pipe status hides a failure. Capture each run to a file in the same call, then grep or read that file. Never rerun a suite to see a different slice of its output and never run one a third time. A write run never uses `pnpm test` or `pnpm test:changed`. A passing suite can print nothing, so print a `pass` line per file and never doubt an `exit=0` that a `pass` line confirms. Keep `exit $fail`: never end the loop with `exit 0`, because that makes the call status lie. A red run should return nonzero; read the captured output from the tool result.

  ```bash
  fail=0
  for f in tests/a.test.ts tests/b.test.ts; do
    out=$(timeout 300 node "$f" 2>&1); c=$?
    printf '%s\n' "$out" > "/tmp/$(basename "$f").out"
    printf '%s exit=%s\n' "$f" "$c"
    if [ $c -eq 0 ]; then printf 'pass %s\n' "$f"; else printf '%s\n' "$out" | tail -n 25; fail=1; fi
  done
  exit $fail
  ```

- **Absence and pins.** A path under `<root>/.kanban/.logs/` (`logPath`, `armedPath`, `counterPath`, `pidPath`) exists only after a write, and a fixture that ends before that write leaves it absent. Write an absence assertion as `!existsSync(p) || !readFileSync(p, "utf8").includes("<line>")`, and prefer asserting the absence of the artifact (pid file, armed file, slug file) to asserting the absence of a log line. A bare `readFileSync` on an unwritten file throws `ENOENT`, and the loop reports it as a thrown error after a part that otherwise passed. That costs a full red and green cycle to diagnose, so guard at write time. A non-zero exit after a part label that says "passed" means a thrown error, not a failed assertion: read the last 25 lines of the captured file and expect `Error:` or `ENOENT`. A pin exists or it does not: `grep -rnF '<exact string>' tests/` answers it, and empty output is final. No pin and none named means no test edit. A pin-only run edits no source, so run the new pin green first, then prove it by disabling its trigger, for example comment out the release line or drop the CSS property the assertion names. Back the file up with `cp` and restore with `cp`, and never `git stash` a test file that holds the new pin, because the stash removes the pin with the trigger. Bundle all red mutations in one call, run only the suites you mutated, restore, then run those suites once more green and keep that result for `# Notes`. Prove red before the source edit only when you change behavior. A scratch test is only for an observed failure or a value the Specs do not give, never for a negative claim that a `grep` proves.
- **Daemon failures and fixtures.** A suite that spawns a daemon or a child agent can fail at a wait or a timeout your edit cannot reach. At the first such failure prove the base once: `git stash push -- <only the paths the suite renders>`, or a read-only `git archive <pre-merge-sha> | tar -x -C /tmp/baseX` extract. Grep the base output for the wait line once. The same wait with the same timeout means pre-existing, so write one `# Notes` line that names the suite and the wait, then stop, do not retry and do not decide again whether it was a flake. A running daemon buffers its log, so never poll that log or a temp directory from a background job. Fixture HOME: `~/.pi`, `~/.config` and `~/.gnupg` are read-only, so `delete process.env.X` and never `= undefined`, and drop `XDG_CONFIG_HOME` too. Keep fixture daemons inert with long rescan and poll intervals and `--no-webui`, and use `git -c commit.gpgsign=false commit` in fixture repos.
- **Manual acceptance.** When an Acceptance line asks for a manual or visual check that cannot run headless, do not build a scratch resolver or a second test. Prove the nearest mechanical fact with an existing suite or one targeted `grep`, record that the visual pass is left to the reviewer, and say so in `# Notes`. If a scratch check is unavoidable, derive the expected names from a `grep` of the source, never from memory, and treat the first mismatch as a script bug before a source bug.

## Shell traps

- **Honest status and output caps.** Chain recon reads with `;`, not `&&`, put the step that can fail last and end the call with `; true`. A bare `grep` with no match and an `ls` of a missing path exit non-zero and fail the call. `! grep -q` inverts the status, so print a label per acceptance check and never read a raw `$?` out of a chain, because a `;` chain reports only the last command. Grep the bare symbol, not a guessed declaration. An empty variable silently removes its argument, so `git -C "$dir"` with an empty `dir` runs in the cwd and `ls "$dir"/x` lists `/x`: assert it is non-empty or set a literal fallback. Never truncate the only useful output with `head`: a capped `| head -N` hides the line that answers the next question, so use `grep -c` for a count. Escape a literal dot in `grep` and never `grep -m` a test run. A short numeric literal is a prefix of a longer one, so quote it and use `-F`, as in `grep -nF '"42"'`. A tool result truncates long output near 8 KB, so never `cat` a whole diff or a long file: use `git diff --stat`, `git diff --unified=0`, `git diff | grep '^+'`, or `read` with a range. Split a recon call by question, not by file. One argv over 131072 bytes fails with E2BIG. `ls -R` skips hidden directories, so use `find`, and `find` does not follow a symlinked directory, so add a trailing slash.
- **Process counts.** Count test leftovers with one anchored pattern such as `pgrep -af '^node /tmp/<fixture-prefix>'`. An unanchored pattern also matches your own bash command line, and a bracketed pattern still matches the parent shell line. Take one count before the run and one after the run, and treat those two numbers as final. The counts, pids and leftover paths in the Specs are evidence from the author's host at write time, not current state: record what you measure and name a difference in one line, then never re-measure to reconcile it. Never run `pkill -f`. An orphan whose fixture directory is gone is inert, so kill it once by pid and do not return to it.

## Delivery and board

- **Evidence, then notes.** On a write run, run every Acceptance check that counts modified files before the commit, and label it `pre-commit`. Before the commit, `git status --short` and `git diff --stat` give the modified-file count. After the commit use `git show --stat --oneline HEAD` and `git status --short` for the post-commit proof. Write only what you ran: never write "after commit", "post-commit" or "clean" for a check that ran before the commit. If the notes claim a post-commit suite run, actually rerun the suite after the commit or drop the claim. Then write the whole notes block in one `cat >> SPECS.md` call. `# Notes` is the top-level heading you own, with no prose before the first `##`. Use at most three `##` subsections: `What changed`, `Acceptance`, `Follow-up`. A blocker for the user goes in one `## Follow-up` line. A real user question or a big assumption goes under `# Open questions` after it, and the spawn prompt owns that section. Do not create an empty `# Open questions`. Keep the block terse: one line per change, one line per check with its command and exit code, and the measured numbers. Do not write an apology for a proof you chose to skip. `SPECS.md` is a gitignored symlink, so `git status` never shows it and that is correct: confirm the notes with `readlink -f SPECS.md` and a `tail` in the commit call, and never pause on the missing status line.
- **Commit by name.** Stage the source, test and doc paths by name, never `git add -A`, and never `git add SPECS.md` or `.kanban`, because an ignored path fails the whole call and no later command runs. Make one commit for the code, refer to it by subject, not by SHA, and end with `git show --stat --oneline HEAD`, then stop. No source or test diff means no commit, and the notes write is the deliverable, so never make an empty commit. The final message is one short line with the outcome and the next action. Resolve the board from the symlink with `board=$(dirname "$(readlink -f SPECS.md)")`. `.kanban`, `SPECS.md` and `AGENTS.md` are gitignored symlinks into the main checkout. Never write `AGENTS.md` and never stage board files. `.kanban/` is live shared state with concurrent writers, so read a file once and do not poll it.
