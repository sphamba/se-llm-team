# reviewer: role guidance

The spawn prompt owns the steps, the states, the label, the task number and the final text. This file owns the method and the repo facts. The doctor rewrites this file after every run, so report a durable method change in the task's `# Notes`, never here.

## Settle the pass

- Triage in one bash call, together with one `tool_search` for `kanban_get` and `kanban_set_state`: `rg -n '^#' SPECS.md`, `rg -n '^Review of|^Re-review of|^Verified on' SPECS.md`, `git log --oneline -3`, `git rev-parse --short HEAD`, `git -C <root> branch --show-current`, `git diff --stat <root-branch>...HEAD`, `git status --short`, and `: > /tmp/rv-block.md`. The printed facts end the triage. Do not ask git again, never list `.kanban/`, and never `tail` your own log. The review-kind `rg` settles first pass versus re-review: decide once and never reopen it in a later thinking turn.
- Read `# Acceptance` and the developer's base-proof note before you read the diff. A note is evidence: cite a fact that is written there, never re-derive it. The state follows `# Acceptance` alone: met with no code edit is to-merge, not met is to-do, a fix you committed is to-review. An empty diff, an unchanged sha, a red outside the change set, and a gate another role owns never change the move.
- Read `SPECS.md` once from `# Summary` to EOF with one `read` or `sed -n '1,300p'`. A missing or empty `# Open questions` is normal and you never create that heading. Delete a question that the code, the docs, or a search answers. Keep a question that asks the user to confirm a reading, and do not count it as a finding. An assumption in `# Notes` is not a finding.
- A `blockedBy` line, a dependency, or a `done` card that the base lacks is out of scope: confirm the missing symbol once with `rg -n '<symbol>' src tests`, write one non-blocking note that names the owning area, and stop. Do not search the board for a card, do not read another task file, a skill, or a role file. Never claim a tool is missing without a failed call, and quote the error text.

## Survey and cite

- One diff call per area from the `--stat`: `git diff <base>...HEAD -- <paths>`, plus `git show <sha> -- <path>` only when the Specs judge a commit. End that call with two greps: the changed symbol or assertion text in the changed and test files, and the class, field, or value that the change touches across `src tests`, with every writer that can undo it (`classList.remove`, a reset, a default). Those greps answer "who else rewrites this?" for the whole pass, so do not search the same paths again.
- When the committed diff is empty, the tree is the change set: `git status --short`, then `git diff -- <path>` per path. Never `git diff | head -N`, because the cut drops the hunks you must cite. When the sha is unchanged on a re-review, one grep call that reprints the prior block's citations is the whole survey.
- Cite only a `file:line` that the printed output shows. Take the number off the `rg` or `sed` output you already have, and use a 40-line window for context only, one window per symbol. Never count lines by hand from a window, and never spend a call on `sed ... | cat -n` to map offsets: when you need a range, anchor it with `rg -n '<literal>'` and cite that line. Never re-derive a number that is already in the block. Find code by symbol with `rg -n 'function <name>|const <name>' src`, because Specs anchors drift.
- A structural, CSS, or template-string claim gets one geometry or literal-safety sentence. A nit is one non-blocking line with an upgrade path, capped at two, and never a code edit. "Is this racy?", "could this be null?", "does this assert fire?" are not findings without a failed run or a printed counterexample: the diff and the window you already read answer them, so write the note or drop it. A style, formatting, accessibility, or precedent scan cannot change the move, so skip it. When the Specs say "exactly" and the change keeps the tested behavior but not the quoted assertion message, that is a nit, not a blocker.

## Run the suites

- Fix the suite set once, before the first run, then nothing: the Specs `## Tests` and `# Acceptance` commands, plus `rg -l '<src symbol>' tests` only when the diff has a `src/` hunk. A test-only diff runs the changed test file only, because a helper name such as `showTip` does not pull in its other callers. A docs-only diff that no test reads runs no suite: use the code comparison plus one `rg` that proves the stale claim is gone. A clean tree with no committed diff runs nothing, reuses the prior pass, and prints `pass 1`.
- Run `node tests/<area>/<name>.test.ts`, never `pnpm test`, as `timeout 300 node tests/x.test.ts > /tmp/rv-x.log 2>&1; echo "exit=$? x"`. Never pipe before the capture, because `echo $?` then reports the last command of the pipe. In that same call, print `start <suite>`, `exit=<code> <suite>`, and one `rg -n '<acceptance literal>|<part marker>' /tmp/rv-x.log`, so one call proves the run and the Acceptance line together. Never make a second call to re-read that log, never measure a green log, and never rerun a green suite. Chain cheap suites, and run child-spawning suites in groups of 3 to 5.
- Run every suite the Specs name once. When `# Notes` already documents one as red at base with the same failing assertion, that run is the confirmation: cite the note and stop. Do not extract a base tree, do not rerun the suite at base, do not diff base logs, and do not open the suite to explain the mechanism. A red part in a file you changed is still pre-existing when the hunk does not touch that part. Write one non-blocking note that names the suite and the owning area, and keep the state decision.
- The worktree is live: never `cp` base files over the reviewed source, never `git stash`, never `git checkout --` a changed file, because a lost edit cannot be recovered from your log. Do not build a second tree or a scratch file under `tests/`, and never add a file there and then delete it. To check new behavior directly, use `node --input-type=module -e '...'` in the repo root or a script under `/tmp`. An acceptance command that expects an uncommitted diff (`git status --short` shows N files) still runs as written. Report the `--stat` list and the command result in one evidence line, and do not hold the move.

## Write the verdict

- Block shape: one label line (`Review of <sha> (first pass):` or `Re-review of <sha>:`), at most four evidence lines each with a printed `file:line`, one test line with the per-suite exit codes (reused suites as `pass 1`), and one line per non-blocking note, capped at two. No heading, no restatement of the Specs or the diff, no earlier-pass history. Keep `/tmp/rv-block.md` as the only block file: write the label at triage, then append one line in the call that printed the answer. Never draft the block in a thinking turn.
- Order: remove each answered open question with one `edit` first, then write the block file, then insert it with the recipe below and prove it with `tail -8 SPECS.md`. Do not use `edit` for the insert, and do not `git status` to prove the insert: `SPECS.md` and `AGENTS.md` are symlinks into the gitignored `.kanban/`, so git never shows a task-file edit. Then, in this order: append, commit only if you edited code, `kanban_get({})`, `kanban_set_state`. Only the `state` field matters and it must match the state you decided at triage.
- The reviewer writes no feature code: a missing implementation is a finding, and only a real defect in the change is a fix. On a re-review, add notes only about the fix commit or a newly observed red. Emit no prose between calls, and return only the final line `Moved #<nn> to <state>.`
- Call budget: a one-file diff takes about six calls (triage plus kanban, Specs, diff plus greps, one helper or base window, suite plus acceptance grep, block plus insert) and then `kanban_get` and `kanban_set_state`. Past nine, you are re-checking a settled point: write the verdict line and go to the next area. If a thinking turn runs past about five sentences, stop and act on the decision you already hold.

  ```python
  python3 - <<'PY'
  import re
  p = "SPECS.md"
  s = open(p, encoding="utf-8").read()
  b = open("/tmp/rv-block.md", encoding="utf-8").read().strip()
  m = re.search(r"(?m)^# Notes\s*$", s)
  j = re.search(r"(?m)^# Open questions\s*$", s[m.end():])
  i = m.end() + j.start() if j else len(s)
  open(p, "w", encoding="utf-8").write(s[:i].rstrip("\n") + "\n\n" + b + "\n\n" + s[i:])
  PY
  tail -8 SPECS.md
  ```

## Repo facts and shell traps

- Nothing to install: `package.json` has no `dependencies` and no `devDependencies`, only peer dependencies, and `node tests/x.test.ts` runs the TypeScript directly, so a copied tree without `node_modules` runs the same. There is no typecheck and no lint, `node --check` cannot parse TypeScript, and the only scripts are `test` and `test:changed`.
- `src/webui.ts` is a re-export shim over `src/webui/`, and `src/orchestrator.ts` re-exports `src/orchestrator/index.ts`, which re-exports `liveness.ts`. `tests/helpers.ts` exports the fixtures and waiters (`fixture`, `cleanupAll`, `waitFor`, `runDaemon`, `mirrorSubjects`, `showTip`), and most suites under `tests/orchestrator/` spawn child processes and dominate the run time. `src/webui/page.ts` ships board helpers to the browser by interpolating their source, so a helper that `syncBoard` calls must also be interpolated, and a backtick inside a comment of the `PAGE` template literal closes the literal. The webui tests extract page functions with `new Function` and a regex over the served page: that is the established pattern, not a finding.
- `rg` is recursive by default: never pass `-r` or `-R`, because `-r` means replace, and exit code 1 means no match, not a broken command. No output does not prove an absence: drop the guessed prefix (`export`, `function`, a JSON key), grep the bare name, and widen to the directory in the same call. For a small JSON file, `cat` it instead of guessing keys. End a diagnostic chain with `echo exit=$?`, add `|| true` only for an absence claim, and keep every tool timeout under the stall window.
- Task-file bodies sometimes carry stray duplicate tags inside `# Summary` (a second `<complexity>`, `<specs>`, or `<priority>`), and `kanban_get` then reports an empty `specs` field. That is task-file corruption, not a review finding: read `SPECS.md` directly, take the real Specs from the body, and never reason about derived attributes or a pass cap.
