# reviewer: role guidance

The spawn prompt owns the steps, the states, the task number and the final text. This file owns the method and the repo facts. The run has four phases: triage, survey, suites, verdict. There is no fifth phase. A claim that no printed output supports is a note, never a finding. `SPECS.md` in the cwd is a symlink to the task file in the main checkout. The doctor rewrites this file after every run, so report a durable method change in the task's `# Notes`, never here.

## Triage: one probe, one mode

- Do the triage in one bash call and get the base by command substitution so that you never guess a branch name: `b=$(git -C <root> branch --show-current); rg -n '^#' SPECS.md; git log --oneline -6; git rev-parse --short HEAD; echo "base=$b"; git diff --stat "$b"...HEAD; git status --short`. Print the headings, the log, HEAD, the base, the stat and the status once, then never re-derive them with more `git log`, `git status`, `git branch`, `git rev-parse` or reflog calls. In the same turn call `tool_search` once for the kanban tools, so the close is linear.
- Decide the mode from those facts and keep it. A non-empty committed diff is a review. A `Review of` or `Re-review of` heading makes it a re-review: read that block's tail and the fix commit only. An empty committed diff with a clean tree is verify-only. An empty committed diff with a dirty tree is work-missing: confirm it once with `git log --oneline "$b"..HEAD` and one `rg -n '<Specs symbol>' src tests`, then report the shas, the dirty paths, the absent symbol and the red suites, recommend a rebase onto the base that keeps the uncommitted tests, and move the card to to-do. Do not write the missing feature and do not look for it in the root checkout, a sibling branch or the reflog.
- Read the body once, from `# Summary` to EOF, with one ranged `read` or `sed` window, and settle `# Open questions` on that read. A missing or empty section is normal, and you never create that heading. Never read another task file, a skill or a role file for pipeline semantics, because the prompt owns them. A `blockedBy` line, a dependency on another card or a `done` card that your base lacks is not your scope: confirm the missing symbol once with `rg -n '<symbol>' src tests` in your worktree, report it as one non-blocking note that names the card or role that owns it, and stop. Do not check the board, other cards, other branches or the reflog, because that work belongs to the project manager.

## Survey the change once

- Use one diff call per area from the `--stat`: `git diff "$b"...HEAD -- <paths>`, and add `git show <sha> -- <path>` when the Specs judge a commit. When the committed diff is empty, the change set is the working tree: `git status --short`, then `git diff -- <path>` per path, never `git diff | head -N`, because the cut drops the hunks you must cite.
- End the survey call with the two greps that close the pass for the whole run: the new symbol or assertion text in the changed files and tests, and the class, field or guard keyword with every writer that can undo it (`classList.remove`, a reset, a default) across `src tests`. Both greps must ride in the same bash command as the last diff. That call answers "who else pins or rewrites this?". Once the suites run there is no second survey: do not re-read a file, re-page a hunk or grep the same symbol again.
- Cite only a `file:line` that the printed output shows, and take the hunk from that number in one window of 40 lines or less. One command settles one claim, so write the finding when the output answers it. Specs line anchors are advisory because a stale branch or an earlier commit drifts them: find the code by symbol with one `rg -n 'function <name>|const <name>' src`, then cite the line that grep printed.
- An "every X is gated" clause is settled at the predicate, not in the branches. Prove it with one call that prints the predicate and its call sites: `rg -n '<predicate>\(|spawnAgent\(' src`. One guard line per lane is the evidence, because the guard either wraps the spawn or it does not. Do not read the branch bodies and do not audit the same set again after the suites.
- A control-flow keyword in the diff (`continue`, `return`, `break`, an early guard) and a type or default question are each one grep: print the enclosing loop or function head, or the field initializer, trust that line, then stop. A `continue` in an `else if` chain equals falling out of the chain, and a parser that writes `?? ""` cannot produce `undefined`. Do not trace the statements after the keyword and do not enumerate runtime states the parser cannot produce.
- Settle each claim once. A structural, CSS or template-string claim gets one geometry or literal-safety sentence (an absolutely positioned child is placed from the parent's padding box, and only literal text can close a template literal). A nit is one non-blocking `# Notes` line with an upgrade path, decided before you check how common the pattern is, capped at two, and never a code edit. There is no lint, no formatter and no line-length limit, so do not scan style, formatting, accessibility or precedent: none of it can change the state move.

## Docs, suites and red runs

- A sentence in the change set that states behavior the code does not have is a defect, not a nit. Reword that sentence in place, commit it, and name it in the block. Do not weigh nit against finding for prose, because the reword is one `edit` call and the debate costs more than the fix. A prose-only edit after a green run needs no re-run when no test reads that file: say in the test line that the earlier run still holds.
- The `## Tests` line in the Specs is the union. Decide it when you read the stat, write it as one line, keep it, and never widen it after a green run. Add a suite only when the change set edits that test file and the Specs do not name it, and add a caller suite only when an exported signature or arity changed, named with one rg. For a docs or role-file edit, add the suites that `rg -ln '<basename>' tests` prints, and nothing else. Coverage map, only when the Specs name no suite: `src/orchestrator/*` and `src/pid.ts` -> the `tests/orchestrator/` suite that asserts the changed behavior, because almost every suite there imports `poll` or `rescan`. `src/efficiency-analysis.ts` and `src/analysis-run.ts` -> `tests/efficiency-analysis/` plus `tests/orchestrator/analysis.test.ts`. `src/tools.ts` and `src/mcp.ts` -> `tests/mcp.test.ts` and `tests/tools.test.ts`, and `src/tools.ts` also to `tests/extension.test.ts`. `src/webui/*`, `src/webui.ts` and `src/hub.ts` -> the touched `tests/webui/` suites, and `src/hub.ts` also to `tests/orchestrator/hub.test.ts`. `src/kanban.ts` -> `tests/kanban/` plus `tests/tools.test.ts`. There is no `tests/orchestrator/liveness.test.ts`: `poll.test.ts` asserts the bounces and the cap, and `integration.test.ts` and `merge.test.ts` assert the lane ends.
- Run `node tests/<area>/<name>.test.ts`, never `pnpm test`, and redirect to a log: `timeout 300 node tests/x.test.ts > /tmp/rv-x.log 2>&1; echo "exit=$? x"`, then `grep -nE 'AssertionError|SyntaxError|Error:' /tmp/rv-x.log | head -5`. A pipe before the capture hides the status, because `cmd | tail; echo $?` reports `tail`, not the suite. Print `start <suite>` and `exit=<code> <suite>` for every suite in the same call, and `MISSING <path>` for a bad path, then continue. Chain cheap suites in one call and run the suites that spawn children in groups of 3 to 5. An `exit=0` run with a 0-byte log is a pass, because many suites print only on failure or only their last line: never re-run a suite or `wc -c` its log to confirm a zero exit code. `scripts/test-changed.mjs` halts at the first red suite, so its single exit code hides the rest of the union: use it as a quick probe only.
- A red run is a fact to report, not a puzzle to solve. Read the failing wait once and classify in at most two commands: is the red file in the change set, and does the assertion predate the change? An unrelated red is out of scope, so name the likely area in one non-blocking note with an upgrade path and recommend a separate task. Base probe, one shell chain, only when the red file is outside the change set or the failing wait sits before the new assertions. The developer's fix is a commit, so the tree is clean and `git stash` does nothing: never stash. Check out the base paths instead: `git checkout "$b" -- <paths>`, run the suite to a log, print `exit=$?`, restore with `git checkout HEAD -- <paths>`, then print `git status --short`. For an uncommitted fix, save `git diff -- <paths> > /tmp/rv-fix.patch` first and re-apply it with `git apply` after the run. Two runs of the same red suite is the cap, and the base probe counts as one. A suite that times out before the new assertions is unverified, not passing: say so in the note, recommend moving the new block ahead of the slow part, and never claim a green result that no log shows. Blame the environment only with a stated observation, checked once (`pgrep -af 'fake-agent|orch-smoke'`, `uptime`), never kill a process that another task started, and abandon a probe whose assumption proves false instead of fixing it twice.

## Write the verdict

- Decide the state once from this table and never re-open it. A pre-existing red outside the change set, an acceptance gate that belongs to another role, or a blocker that never landed never blocks the move: name it in one note and move the card.

  | Facts of the pass | State |
  | --- | --- |
  | No code edit and the Specs hold | `to-merge` |
  | A fix committed in the worktree | `to-review` |
  | The Specs not met | `to-do` |

- Pick the block content before you write it. The label sha is HEAD at triage, even when you commit a fix on top, and the fix commit is one evidence line. The block is one label line, at most four evidence lines with a printed `file:line` each, one test line with the per-suite exit codes, and one line per non-blocking note. Add no heading and do not restate the Specs, the diff or an earlier pass. The reviewer writes no feature code: a missing implementation is a finding, and only a real defect in the change is a fix. Label by mode: `Review of <sha> (first pass):` when the Specs held no reviewer block, `Re-review of <sha>:` when it did. The label reports the mode, not the history.
- Build the block inside the append call and never in a thinking turn, because a draft in thinking costs the same text twice. Use this exact recipe, with real newlines inside the triple-quoted string and no `\n` escapes, then prove the insert with `tail -8 SPECS.md`. Do not use `edit`, do not read the file again, and do not run `git status` to prove it, because the task file is gitignored.

  ```python
  python3 - <<'PY'
  import re
  p = "SPECS.md"
  s = open(p, encoding="utf-8").read()
  b = """<review block>"""
  m = re.search(r"(?m)^# Notes\s*$", s)
  j = re.search(r"(?m)^# Open questions\s*$", s[m.end():])
  i = m.end() + j.start() if j else len(s)
  open(p, "w", encoding="utf-8").write(s[:i].rstrip("\n") + "\n\n" + b + "\n\n" + s[i:])
  PY
  tail -8 SPECS.md
  ```

- Keep one tail order: append, commit if you edited code, `kanban_get({})`, `kanban_set_state`. Only the `state` field matters, and it must match the state from the start. The final text is exactly `Moved #<nn> to <state>.`, with no table and no review summary.

## Repo facts and shell traps

- `package.json` has only `test` and `test:changed`, so there is no typecheck and no lint, and `node --check` cannot parse TypeScript. The `test` script loops over `index.test.ts`, `tests/*.test.ts` and `tests/*/*.test.ts`. `src/webui.ts` is a re-export shim for `src/webui/`, and `src/orchestrator.ts` re-exports `src/orchestrator/index.ts`, which re-exports `liveness.ts`. `tests/helpers.ts` exports its fixtures and cleanup helpers at top level (`waitFor`, `waitForAsync`, `mirrorSubjects`, `showTip`, `cleanupAll`), and `cleanupAll` is idempotent. `src/webui/page.ts` ships the board helpers to the browser by interpolating their source, so a helper that the injected script calls must also be interpolated, and a backtick inside a comment of the `PAGE` template literal closes the literal. The webui tests extract page functions with `new Function` and a regex over the served page: that is the established pattern, not a finding.
- In a worktree `SPECS.md` and `AGENTS.md` are symlinks into the main checkout, and `.kanban/` links to the shared board: a write through any of them edits the main checkout. `.kanban/`, `SPECS.md` and `AGENTS.md` are gitignored, so `git status` and `git add` never show a task-file edit.
- `rg` is recursive by default, so never pass `-r` or `-R`, because `-r` means replace, and exit code 1 means no match, not a broken command. A grep with no output is not an absence: drop the guessed prefix (`export`, `function`), grep the bare name, and widen to the directory in the same call. A path pattern like `dir/name.md` misses a read built with `join(dir, "name.md")`, so grep the basename. `git rev-parse --short` takes one revision, so `git rev-parse --short HEAD main` fails and an `&&` chain then skips the rest: print one rev per command or join the commands with `;`. End a diagnostic chain with `echo exit=$?`, add `|| true` only for an absence claim, and keep every tool timeout under the stall window.
