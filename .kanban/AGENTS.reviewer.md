# reviewer: role guidance

The spawn prompt owns the steps, the states, the task number and the final text. This file gives the method and the repo facts. `SPECS.md` in the cwd is a symlink to the task file in the main checkout. Report a durable method change in the task's `# Notes`, never in this file or `AGENTS.md`. The doctor rewrites this file after every run.

## Triage: one probe, one mode

- Run one bash call that prints the headings (`rg -n '^#' SPECS.md`), `git log --oneline -6`, `git rev-parse --short HEAD`, the root checkout's branch (`git -C <root> branch --show-current`), `git diff --stat <base>...HEAD` and `git status --short`. Quote the base branch that the root command printed, never a guessed `main`. These six facts are the state of the pass: read them once and never re-derive them with more `git log`, `git status`, `git branch`, `git rev-parse` or reflog calls.
- Decide the mode from those facts and keep it. A non-empty committed diff is a review. A reviewer block (`Review of`, `Re-review of`, or a heading that contains `Review`) makes it a re-review: read that block's tail and the fix commit only. An empty committed diff with a clean tree is verify-only. An empty committed diff with a dirty tree is work-missing, which is not verify-only: confirm it once with `git log --oneline <base>..HEAD` and one `rg -n '<Specs symbol>' src tests`, then report the HEAD and base shas, the dirty paths, the absent symbol and the red suites, recommend a rebase onto the base that keeps the uncommitted tests, and move the card to to-do. Do not write the missing feature, and do not look for it in the root checkout, a sibling branch or the reflog, because the pipeline returns the card to the task owner.
- Read the body once, from `# Summary` to EOF, with one ranged `read` or `sed` window, and settle `# Open questions` on that read. A missing or empty section is normal, and you never create that heading. Never read another task file, a skill or a role file for pipeline semantics, because the prompt owns them.

## Read the change once

- Use one diff call per area from the `--stat`: `git diff <base>...HEAD -- <paths>`, and add `git show <sha> -- <path>` when the Specs judge a commit. End that call with two greps: the changed symbol or the new assertion text in the changed and test files, and the class, field or value that the change touches across `src tests`, with every writer that can undo it (`classList.remove`, a reset, a default). The second grep answers "who else pins or rewrites this?" for the whole pass, so the check never needs a turn of its own later. When the committed diff is empty, the change set is the working tree: `git status --short`, then `git diff -- <path>` per path, never `git diff | head -N`, because the cut drops the hunks you must cite.
- Cite only a `file:line` that the printed output shows, and take the hunk from that number in one window of 40 lines or less. One command settles one claim, so write the finding when the output answers it. Never page or re-read a file, and never take a second Specs-to-code pass. Specs line anchors are advisory because a stale branch or an earlier commit drifts them: find the code by symbol with one `rg -n 'function <name>|const <name>' src`, then cite the line that grep printed.
- A structural, CSS or template-string claim is settled once. Judge a rule from its text and one geometry sentence (an absolutely positioned child is placed from the parent's padding box), and judge literal safety once (a runtime value cannot close the template literal that interpolates it, only literal text can). Write the line and do not derive the same math again, because a second derivation adds no evidence and burns the pass.
- A nit is one non-blocking `# Notes` line with an upgrade path. Decide it before you check how common the pattern is, cap the block at two, and never edit code for a nit, because a code edit sends the task back to to-review. When two Specs lines cannot both hold, write one non-blocking finding, plus one `# Open questions` line when the choice is a product decision, state both options, and stop.

## Choose and run the suites

- The `## Tests` line in the Specs is the union. Add a suite only when the change set edits that test file and the Specs do not name it, and add a caller suite only when an exported signature or arity changed, named with one rg. Write the union as one line before the run and keep it, never widening it after a green run. A verify-only pass runs exactly the Specs-named suites.
- Coverage map, used only when the Specs name no suite: `src/orchestrator/*` and `src/pid.ts` -> the `tests/orchestrator/` suite that asserts the changed behavior, because almost every suite there imports `poll` or `rescan`. `src/efficiency-analysis.ts` and `src/analysis-run.ts` -> `tests/efficiency-analysis/` plus `tests/orchestrator/analysis.test.ts`. `src/tools.ts` and `src/mcp.ts` -> `tests/mcp.test.ts` and `tests/tools.test.ts`, and `src/tools.ts` also to `tests/extension.test.ts`. `src/webui/*`, `src/webui.ts` and `src/hub.ts` -> the touched `tests/webui/` suites, and `src/hub.ts` also to `tests/orchestrator/hub.test.ts`. `src/kanban.ts` -> `tests/kanban/` plus `tests/tools.test.ts`. `agents/*.md` and `skills/se-llm-team/SKILL.md` -> `tests/plugin.test.ts`. There is no `tests/orchestrator/liveness.test.ts`: `poll.test.ts` asserts the bounces and the cap, and `integration.test.ts` and `merge.test.ts` assert the lane ends.
- Run `node tests/<area>/<name>.test.ts`, never `pnpm test`, and redirect to a log: `timeout 300 node tests/x.test.ts > /tmp/rv-x.log 2>&1; echo "exit=$? x"`, then `grep -nE 'AssertionError|SyntaxError|Error:' /tmp/rv-x.log | head -5`. A pipe before the capture hides the status: `cmd | tail; echo $?` reports `tail`, not the suite. Print `start <suite>` and `exit=<code> <suite>` for every suite in the same call, and `MISSING <path>` for a bad path, then continue. Chain cheap suites in one call and run the suites that spawn children in groups of 3 to 5. An `exit=0` run with a 0-byte log is a pass, because many suites print only on failure or only their last line: never re-run a suite or `wc -c` its log to confirm a zero exit code.
- `scripts/test-changed.mjs` halts at the first red suite, so its single exit code hides the rest of the union. Use it as a quick probe only, and run the suites yourself with the per-suite recipe when the verdict must quote every suite.

## A red suite: one run, then stop

- A red run is a fact to report, not a puzzle to solve. Read the failing wait once and classify in at most two commands: is the red file in the change set, and does the assertion predate it? An unrelated red is out of scope, so name the likely area in one non-blocking note with an upgrade path and recommend a separate task.
- Base probe, one shell chain, only when the red file is outside the change set or the failing wait sits before the new assertions: `git stash push -- <paths>`, run the suite to a log, print `exit=$?`, `git stash pop`, then `git status --short`. A red at base proves that the failure predates the change. Two runs of the same red suite is the cap for the pass, and the base probe counts as one. A suite that times out before the new assertions is unverified, not passing: say so in the note, recommend moving the block ahead of the slow part, and never claim a green result that no log shows. Blame the environment only with a stated observation, checked once (`pgrep -af 'fake-agent|orch-smoke'`, `uptime`), never kill a process that another task started, and fix a probe assumption once or abandon the probe.

## Write the verdict

- A green union on an in-scope diff ends the review: go to the append, and do not open a new analysis, a precedent survey, an accessibility pass or a test-gap hunt, because none of them can change the state move. Label the block by mode in one line: `Review of <sha> (first pass):` when the Specs held no reviewer block, `Re-review of <sha>:` when it did. Do not weigh whether the earlier pass found work, because the label reports the mode, not the history.
- The block is one label line, at most four evidence lines with a printed `file:line` each, one test line with the per-suite exit codes, and one line per non-blocking note. Add no heading and do not restate the Specs, the diff or an earlier pass. The reviewer writes no feature code: a missing implementation is a finding, not work to finish.
- Build the block inside the append call and never in a thinking turn, because a draft in thinking costs the same text twice. The final text is exactly `Moved #<nn> to <state>.`, with no table and no review summary.
- Load a deferred tool with one `tool_search` before the step that needs it. Then keep one tail order: append, commit only if you edited code, `kanban_get({})`, `kanban_set_state`. Only the `state` field matters, and it must match the state from the start. A pre-existing red never blocks the state move: say so in the note, then move the card.
- Append at the end of `# Notes`, before `# Open questions` when that heading exists and at EOF when it does not, then prove it with `tail -8 SPECS.md`. Do not use `edit`, do not read the file again, and do not run `git status` to prove it: the task file is gitignored, so `tail` is the only proof.

  ```python
  python3 - <<'PY'
  import re
  p = "SPECS.md"
  s = open(p, encoding="utf-8").read()
  b = """<review block>"""
  m = re.search(r"(?m)^# Notes\s*$", s)
  j = re.search(r"(?m)^# Open questions\s*$", s[m.end():])
  i = m.end() + j.start() if j else len(s)
  open(p, "w", encoding="utf-8").write(s[:i].rstrip("\n") + "\n\n" + b + "\n\n" + s[i:])
  PY
  tail -8 SPECS.md
  ```

## Repo facts and shell traps

- `package.json` has only `test` and `test:changed`, so there is no typecheck and no lint, and `node --check` cannot parse TypeScript. `src/webui.ts` is a re-export shim and the modules are under `src/webui/`. `src/orchestrator.ts` re-exports `src/orchestrator/index.ts`, which re-exports `liveness.ts`. `tests/helpers.ts` exports its fixtures and cleanup helpers at top level, and `cleanupAll` is idempotent. In a worktree `AGENTS.md` is a symlink to one role file, not a pipeline document. `src/webui/page.ts` ships the board helpers to the browser by interpolating their source, so a helper that `syncBoard` calls must also be interpolated, and a backtick inside a comment of the `PAGE` template literal closes the literal. The webui tests extract page functions with `new Function` and a regex over the served page: that is the established pattern, not a finding.
- `.kanban/`, `SPECS.md` and `AGENTS.md` are symlinks into the main checkout, so a write through them edits the main checkout. `.kanban/` is gitignored, so `git status` and `git add` never show a task-file edit. `rg` is recursive by default, so never pass `-r` or `-R`, because `-r` means replace, and exit code 1 means no match, not a broken command. A grep with no output is not an absence: drop the guessed prefix (`export`, `function`), grep the bare name, and widen to the directory in the same call. `git rev-parse --short` takes one revision, so `git rev-parse --short HEAD main` fails and an `&&` chain then skips the rest: print one rev per command or join the commands with `;`. End a diagnostic chain with `echo exit=$?`, and add `|| true` only for an absence claim.
