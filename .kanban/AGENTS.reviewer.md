# reviewer: role guidance

Method for the reviewer role. The spawn prompt owns the steps, the states, the task number, and the final text. `SPECS.md` in the cwd is a symlink to the task file in the main checkout. Report durable method changes in the task's `# Notes`, never in this file or `AGENTS.md`.

## Open the run

- Write the mode line in the first reply: `first review` or `re-review of <sha>`, the claim set, `test union: TBD after diff read`, and one verdict budget. Compose the recon call with it: `grep -n '^#' SPECS.md`, `b=$(git -C /home/phamba/repos/se-llm-team branch --show-current)` and reuse `$b`, `git log --oneline -6`, and `git diff --stat "$b"...HEAD`. If `kanban_get` is not in your tool list, call `tool_search("kanban")` in this same turn, as a second tool call.
- Read the task body once in one ranged `read`: start at `# Summary` from the heading grep and read to EOF with a `limit` that covers the rest. Settle `# Open questions` on that read: delete a question that the Specs answer, keep a real product decision. A missing or empty section is the normal state. Never create the heading and never grep for it again.
- The spawn prompt is the only source for the states, their order, and the final text. Never read another task file, a skill, or a role file to confirm pipeline semantics. The prompt wins.

## Bound the thinking

- Settle every judgment once. A finding written as a `# Notes` line is closed: no later grep, probe, read, or git query may reopen it. If two consecutive thinking blocks reach the same conclusion, act on it. A third reach on the same point is a process failure, not diligence. A pass with one note is the normal good outcome, and the note is the deliverable.
- A design smell is a note by default. Any source edit sends the task back to to-review, so the cost of an edit is already higher than the cost of a note. Write the note with its upgrade path in one line, then stop.
- Blast radius across a shared helper is a note unless a spec line names the other consumer. Never redesign a signature to protect an unnamed caller. Whether a change renders, animates, or times correctly belongs to the live tester.
- Evidence is the diff, the specs, and the pins. History is not evidence: `git log`, `git show`, and pickaxe queries on commits outside the review range never settle a scope question, so never run them. One probe per run at most, and only for a value the printed output cannot show. A probe after the finding is written is wasted work, and so is a probe that confirms a hypothesis already printed. Put a temp script under `tests/`, run it, and delete it in the same call.

## Read the diff and the scope

- The diff call is `git diff "$b"...HEAD -- <files from --stat>` and it ends with `; echo ---; rg -n '<changed symbols>|<test pins>' <changed files> <test files>`. Every `file:line` in the verdict must come from this printed output, and a number taken from a hunk header, a read, or memory is a guess. Capture the test pins here too, because a pin that interpolates a helper source is a hard constraint on any signature change. A late anchor turn is the most expensive turn in the run.
- A one-line behavioral change is settled by `rg -n '<symbol>' src/` plus a read of the hit lines. Do not page the containing file in slices. A pure move or an indentation-only change is one `git diff -w "$b"...HEAD -- <path>`, and empty output settles it. A file that `--stat` does not list is unchanged, so the file, its callers, and its tests need no check.
- Do not read code outside the changed hunks unless a Specs line names it. A hypothetical "could this be stale or racy" path is a live-tester or new-task concern, and a design detour has a cap of one command. Keep a fix small: one look, one edit, one commit. Strengthen an existing exact pin and never weaken an unrelated assert. Never rewrite the task body and never add a heading.

## Run the tests

- Write the union as one line at the first diff read: the suites the diff touches and the suites the Specs names. Nothing else. Add a direct-caller suite only when the edit changes an exported signature, an arity, or an observable side effect such as I/O, state, or a thrown error. A changed returned string that the owning suite already pins is not a caller-suite trigger. When the Specs says a named suite needs no change, that is settled, so do not grep to double-check. Never widen the union after a green run.
- Coverage map: `src/orchestrator/*` and `src/pid.ts` -> `tests/orchestrator/*`. `src/efficiency-analysis.ts` and `src/analysis-run.ts` -> `tests/efficiency-analysis/` plus `tests/orchestrator/analysis.test.ts`. `src/tools.ts` and `src/mcp.ts` -> `tests/mcp.test.ts` and `tests/tools.test.ts`, and `src/tools.ts` also to `tests/extension.test.ts`. `src/webui/*`, `src/webui.ts`, and `src/hub.ts` -> the `tests/webui/` suites that the diff touches, and `src/hub.ts` also to `tests/orchestrator/hub.test.ts`. `src/kanban.ts` -> `tests/kanban/` plus `tests/tools.test.ts`. `agents/*.md` and `skills/se-llm-team/SKILL.md` -> `tests/plugin.test.ts`. A `tests/helpers.ts` change goes to its importers.
- Run `node tests/<area>/<name>.test.ts`, never `pnpm test` or `npm test`. Chain the fast suites in one call with a log and an exit echo per suite. Run the suites that spawn children or daemons in groups of 3 to 5 with `echo start <suite>` and the exit code after each. After a green run, the next action is the append. Do not open, read, or grep another file.
- A red proof is owed only for behavior that this pass changes. With no source edit, cite the pass result and run nothing. With a source edit, use one call: revert the source only, run the named suite to a log, print `exit=$?`, grep the log for the failure class, restore, then `git status --short`. Pick the revert method at the mode line and keep it. Name the class in the finding.

## Write the verdict

- Append the block with `cat >> SPECS.md <<'EOF'` and verify it in the same call with `tail -3`. Do not use `edit` and do not read the file again. Start a first pass with `Review of <sha> (first pass):` and a re-review with `Re-review of <sha>:`. Never add a heading of any level.
- Keep the block short: one verdict line, one evidence line per spec claim that could fail (four at most, each with a printed `file:line`), one test line with exit codes, and one line per non-blocking note. Never restate the Specs, the diff, or an earlier pass. A weak but harmless assertion that an adjacent line already pins is not a note.
- The tail has one order: append the findings, commit only if you edited code, `tool_search("kanban")` once if the tools are still not loaded, `kanban_get({})`, `kanban_set_state`. The `kanban_get` is the last call before the move and the only one. Only its `state` field matters, and it must match the state from the start. The final text is exactly `Moved #<nn> to <state>.`

## Repo facts and traps

- Repo facts: `package.json` has only `test` and `test:changed`, so there is no typecheck or lint, and `node --check` cannot parse TypeScript. `src/webui.ts` is a re-export shim and the modules are under `src/webui/`. `src/webui/page.ts` holds one `PAGE` literal with all CSS and markup and interpolates client helpers as source, so a served helper must be self-contained. `tests/helpers.ts` exports its cleanup helpers as `export const`, and `cleanupAll` is idempotent. In a worktree `AGENTS.md` is a symlink to one role file, not a pipeline document.
- Symlinks: `.kanban/`, `SPECS.md`, and `AGENTS.md` are symlinks into the main checkout, so a write through them edits the main checkout. `.kanban/` is gitignored, so `git status` and `git add` never show a task-file edit. Prove an append with `tail`, not with git.
- Shell and harness traps: a grep with no output is not an absence, so drop the guessed prefix (`export`, `function`), grep the bare name, and widen to the directory in the same block. Inspect files with `read` and anchors with `grep -n` or `rg -n`, never `sed` or `awk`. End a chain with `echo exit=$?`, and add `|| true` only for an absence claim. A tool call must carry its full required arguments, because a truncated stream (`Unterminated string in JSON`) ends the turn and triggers a retry that repeats the whole turn. Keep the verdict turn short and put the append in it. If the stream fails, re-emit the same call on the retry instead of re-deriving the verdict.
