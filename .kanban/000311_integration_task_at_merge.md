# Summary
Move the integration-task trigger from the live test's success to the merge fast-forward, so the single integration run starts while the covered task's live test still runs. Today `ensureIntegrationTask` runs in the `live-testing -> done` hook (`src/orchestrator/liveness.ts:214-222`); it must run in `sweepToMerge` at the `to-live-test` move (`src/orchestrator/pipeline.ts:311`).

# Specs
## Target behavior

- Hook the merge pass, not the live test. In `sweepToMerge`, at the `setState(root, task, "to-live-test")` call (`src/orchestrator/pipeline.ts:311`, after `stripContextSymlinks`), call `ensureIntegrationTask(root, fresh)` with `fresh = getTask(root, task.file) ?? task`. Put the call after the `fast-forwarded ... set to-live-test` log line.
- Remove the old hook and its comment from `src/orchestrator/liveness.ts:214-222`. The `live-testing -> done` move keeps only the state move and its log.
- Keep the hook non-fatal exactly as today: wrap the call in try/catch and log `integration task for <slug> failed: <message>`. The base is already fast-forwarded, so a hook failure must not fail the merge, revert the state, or send the task back to to-merge.
- Do not change `ensureIntegrationTask` (`src/orchestrator/pipeline.ts:109-142`) or the task fields. It still skips a ref that a waiting or running lane task already names, appends to the oldest `to-integration-test` task, and otherwise creates a task. `createIntegrationTask` keeps priority `low`, complexity `simple`, issuer `auto`, no `blockedBy`, no worktree, and state `to-integration-test`.
- Change the generated notes line (`src/orchestrator/pipeline.ts:97`) from `Generated by the orchestrator when #<num> reached done.` to `Generated by the orchestrator when #<num> was merged to the base branch.`
- The lane may spawn on the next rescan (10 s by default) because the new task is not in the current rescan snapshot. That delay is expected, not a defect.
- These paths must create nothing: a task with no worktree or an unmerged branch (moved to done at `src/orchestrator/pipeline.ts:250-255`, before the fast-forward), a PM move into to-live-test, a failed rebase (`:281-294`), and a failed fast-forward (`:302-305`).
- No bounce tracking. A ref whose live test later fails keeps its entry; the PM decides what to file. If that ref merges again while its entry is waiting or running, the dedupe skips it. If the entry already reached done, the hook creates a new entry, because the lane no longer names the ref.
- Two merges close together keep the current queue rule: the second appends to the task waiting in `to-integration-test`, or creates its own entry when the first is already `integration-testing` and waits for the single lane slot.
- The covered task still reaches done on its own live-test pass, without waiting for its integration run.

## Splitter: no split

This task stays whole. The hook move in `src/orchestrator/pipeline.ts` and the removal in `src/orchestrator/liveness.ts` share one trigger contract, and both test files assert through the same merge helper that `tests/orchestrator/integration.test.ts` must introduce. One developer pass, one review, one merge, one live test.

Guidance for future Splitters: a hook relocation with its test rewrite is one unit. Split only when the pieces write disjoint files and each piece passes its own acceptance checks without the other.

### Assumptions

- The lane pid file `.kanban/.pids/integration-tester.pid` held the driver's live pid, so the waiting entry kept its `to-integration-test` state while the covered live test ran. The Specs allow the lane to start on the next rescan, so the hold only removes that expected delay. The 25 ms sampler recorded the entry with the covered task in `to-live-test`, and the entry appeared 1103 ms before the first live-tester spawn, so the match does not depend on the hold.
- One fixture root per tree. Fixture config: `pollMinutes 0.01`, `backlogIdleMinutes 0`, `retryIdleMinutes 0`, `maxParallel 0`. The fake live-tester exits 0, so the poll owns the `live-testing -> done` move.
- The analysis runs that follow each exit-0 run hung in the fixture HOME because that HOME has no LLM config. The cleanup killed them, and the run proved no leftover process. This is a fixture property, not the change under test.
