# splitter: append project-specific guidance for this role below (e.g. how to run the project, how to live-test) so future agents of your kind start faster.

- The cwd SPECS.md is a symlink into .kanban/. Omit the file argument on all kanban tools. The parent num comes from the symlink target (ls -l SPECS.md).
- Read the touched code before you split. Check what the client reads from each payload field. Task 000242 had a tension: the light-row contract excluded agent history, but the board cards read t.agents/t.doctors for stats lines and the poll cadence. Such cross-cutting tensions are cheaper for one developer than for two split subtasks.
- tests/webui.test.ts is one shared 2000-line hub test file. Subtasks that both add tests there conflict at merge. Count that cost in the split decision.
- Run: pnpm test (full), pnpm test:changed (touched files only).
- tests/ has no payload-specific test file: payload/doctorHistory and aliveness tests also live in the shared tests/webui.test.ts. Any task touching payload.ts conflicts at merge with any task touching page.ts/board.ts tests. Count that in every split decision.
- After creating subtasks, kanban_update WITHOUT a file argument resolved to a newly created subtask (picked #256, not the SPECS.md symlink target #254) and the self-block guard rejected the parent rewrite with a confusing "#N blocks itself" error. Pass the parent's file explicitly on the parent rewrite (kanban_update + kanban_set_state), and verify the num before retrying a rejected update.
- Parallel test-split pattern (task 000254, 2026-10-16): attach ALL shared files (tests/helpers.ts, package.json, scripts/test-changed.mjs + its test) to ONE subtask with a glob-based contract that tolerates the other areas not having landed yet; the other subtasks never touch them, so merges stay trivial. A subtask that moves its test file sees pnpm test fail in its worktree until the glob loop lands: say so in its Specs ("expected, do not fix; your check is per-file standalone runs"). Pin the per-file assertion baselines (grep -c "assert\.") in each subtask's Specs and the parent's verification Specs so reviews and the final check catch dropped assertions mechanically.
- Conflict-free test-split variant (task 000256, 2026-10-17): when a split task owns the destructive step itself, make every subtask produce ONLY new files (never edit the old file or any shared file) and let the PARENT delete the old file at verification. Subtasks own disjoint old-file ranges, so zero shared writes and merges are trivial. Measured seams of tests/webui.test.ts (2,379 lines, 739 asserts): logpane 43-313 (61), hub 14-42 + 315-421 + 2277-2380 (76), board 422-797 (153), page 798-1513 (270), agentlog 1514-2275 (179); ranges sum to 739 exactly. Do not split a continuous fixture run (page 798-1513, agentlog 1514-2275) further: state is written and rmSynced in sequence.
- Reconfirmed gotcha (000256): the cwd SPECS.md symlink gets re-pointed to a freshly created subtask, so fileless kanban_update/kanban_set_state after creating subtasks targets the wrong task. Always pass the parent's file explicitly on the parent rewrite; a rejected update is atomic, so verify state with kanban_get before retrying.
- Parallel-splitter race (000256, 2026-10-17): two Splitter sessions worked the same parent at once and both created subtask sets. Before creating subtasks, check .kanban/ for sibling tasks from the same issuer (ls .kanban/ or kanban_list all scopes); if a split already exists, delete your duplicates with kanban_delete and repair, never add a second decomposition.
- A fileless kanban_update can SILENTLY CLOBBER a sibling task: the parallel session re-pointed the cwd SPECS.md symlink mid-run and the update overwrote the sibling's Summary, Specs and complexity with no error. Resolve the parent file name once at start (readlink SPECS.md) and pass that explicit file to every kanban_update/kanban_set_state.
- Recovery of clobbered task content: kanban_create and kanban_delete commit whole-board mirror snapshots to meta/kanban. git show <create-commit>:.kanban/<file>.md restores the original frontmatter (complexity included) and body; pass complexity back in the restore update, not only Summary/Specs.
- Concurrent-splitter race (000256, 2026-10-17): two Splitter instances ran on one to-do parent at once. The second minted a parallel decomposition (#263-#266) and briefly rewrote a sibling (#262) as its verification task, then rolled itself back (deleted its own duplicates). Lesson: before minting subtasks, re-list the board for existing sibling subtasks of the same parent and adopt or delete duplicates instead of stacking a second decomposition.
- Contract-split pattern for webui server/client features (task 000252, 2026-10-17): when a feature is one endpoint + one client consumer, split it into a server subtask and a client subtask with the endpoint contract pinned verbatim in BOTH specs (exact path, query params, response shape, error cases). The client builds against a stubbed fetch, so neither side blocks the other and merge order does not matter; state in the client spec that a 404 before the server merges is expected, do not fix. Parent becomes verification-only (the pinned contract held end to end) blocked by both.
- Pin disjoint test anchors when both subtasks add asserts to the one shared test file: one subtask extends the fixture block it naturally belongs to (e.g. the 000245 taskPayload block), the other appends at the very end before cleanup(); BOTH rules: never edit the shared import lines, add a NEW import line for new exports. Pin the assert baseline (grep -c "assert\.") in both specs so reviews catch dropped assertions.
- Keep the client-side testable logic in board.ts as exported doc-injected functions (inject storage the same way), interpolated into PAGE like syncBoard/syncCardStats - client flow inside the PAGE template is not directly testable; page.ts only wires handlers and CSS.
- A parent moved to backlog may carry a worktree attribute the daemon set in anticipation of the Developer. Verify with git worktree list whether it is real; a stale attribute on a verification parent is safe to clear with kanban_set_worktree "".
- No-split decision (000264, 2026-10-17): a client feature that adds exported logic to one module, wires it in the page module, and appends end-of-file asserts to the shared test file does not parallelize. All pieces share both source files and the test file tail, so subtasks conflict at merge and serialize on the shared asserts. Split only when one piece can own a disjoint file range or produce only new files.
- Contract-split outside webui (000268, 2026-10-17): the PM-processed-marker feature split into #269 (marker surface: kanban.ts helper + tools.ts tool + scope enum + NEW tests/tools.test.ts) and #270 (orchestrator consumers: report.ts catch-up + board.ts removeTask + sweep.test.ts part N extension). The one coupling, the marker path convention, was pinned verbatim in BOTH specs; the consumer subtask reads it inline with taskSlug (already exported by kanban.ts), so it depends on no helper from the sibling and merge order does not matter. Files fully disjoint, no shared test file.
- tools-record gotcha (000268): tests/mcp.test.ts pins the exact TOOLS names array (12 names at lines ~96-110) - any subtask that adds a tool to the TOOLS record MUST extend that array in the same subtask, or its pnpm test fails. Pin this in the tool subtask's Specs.
- Facade paths lie (000268): the parent specs said removeTask lives in src/orchestrator.ts, but that file is only a facade; the real definition is src/orchestrator/board.ts:135. Resolve every facade re-export to its real file before pinning file ownership in subtask Specs.
- Helper placement (000268): a .logs side-file helper consumed by kanban.ts (listTasks) or tools.ts must live in kanban.ts, NOT orchestrator/log.ts (the armedPath precedent) - log.ts imports kanbanDir back, so the helper there would cycle. A kanban.ts-owned helper is importable by tools.ts, report.ts and the orchestrator modules with no new wiring.
- sweep.test.ts part N (lines 12-54) is the report-channel part; assert baseline at split time: 45 "assert." occurrences (grep -c "assert\\."). Its imports already cover existsSync/writeFileSync/join, so a marker test extension needs no new import lines.
- listTasks/Scope consumers: only src/tools.ts kanban_list (the webui does not use listTasks) - a Scope union extension is additive-safe and needs no webui change.
- Verification-parent worktree reconfirmed (000268): the daemon had already created feat/268-... for the parent before the split; the branch sat at pre-split main, so a verification developer there would never see the subtasks' merged changes. Cleared the attribute with kanban_set_worktree "" after the parent moved to backlog (the addendum's stale-attribute rule).
- No-split decision (000269, 2026-10-17): a subtask whose two modules form an import pair (tools.ts imports the new pmProcessedPath export from kanban.ts) plus one new test file covering both sides does not split: no cut avoids a shared source file, and the consumer-side subtask does not compile until the producer-side piece merges. Same family as 000264; check the import graph between the two files before minting a producer/consumer split.
- No-split decision (000272, 2026-10-17): a config-key feature whose consumer module (pipeline.ts) already imports type Config from the producer (config.ts) and reads the new field does not split by config-vs-consumer: the consumer's cap tests write the key into fixture JSON, but unchanged loadConfig never parses it, so cfg.<key> stays undefined and every cap test fails in the consumer's worktree until the producer merges. Same import-pair family as 000269, but note the sharper test: 000268's contract split worked because the consumer inlined the coupled convention with an already-exported helper; a typed interface field cannot be inlined without touching the shared producer file. Before minting a producer/consumer split, check both the import graph AND whether the consumer's runtime behavior (not just its types) needs the producer's change - tsx runs untyped, so a missing field fails silently at test time, not at compile time.
- No-split decision (000275, 2026-10-18): a popup recolor whose 6 change items all land in one contiguous CSS block + two render call-sites of src/webui/page.ts, with all test work as pinned edits in one contiguous region of tests/webui/page.test.ts, does not split. Count-of-changes is not parallelism: only disjoint file ranges or new-file-only subtasks parallelize; a contiguous CSS block and a contiguous test-pin region are single seams. Same family as 000264; string-pin pairs between code and tests fail the 000272 way (asserts on strings that do not exist yet).
